# Точки интеграций сервис Договоров и Заявок

Редакция 2 от 22.10.2026. Действующее описание обмена сервиса Договоров с сервисом Заявок и с 1С:УСК; первая редакция документа — без даты. Части, которые сервис Договоров ещё не реализовал (оплата, передача оплаченного договора КМ в 1С:УСК и её результат), описаны как в первой редакции с учётом уже принятых решений и помечены «будет на этапе оплаты, уточняется при реализации».

Документ описывает обмен сервиса Договоров с сервисом Заявок и с 1С:УСК в части выпуска договоров КМ и полисов ЛМ: семь асинхронных точек по RabbitMQ и перечень синхронных вызовов. Три точки обслуживают обмен с сервисом Заявок, четыре — обмен с 1С:УСК двумя независимыми парами очередей: по договорам КМ и по полисам ЛМ.

Сервис Договоров — бэкенд без пользовательского интерфейса. Внутри контура РВЛ ОНЛАЙН его единственный собеседник — сервис Заявок. Контракты ИП-01…ИП-06 сервиса Заявок с 1С:УСК согласованы и настоящим документом не изменяются.

## Бизнес-процесс

Сервис Договоров включается в работу после того, как заявка прошла согласования и суммы зафиксированы. До этого момента ни договор, ни полис не выпускаются: отклонение ЦКЗ или ответственного от страхователя делает выпуск ненужным.

### Фаза 1. Постановка задачи

- Сервис Заявок получил согласование ЦКЗ и согласование ответственного от страхователя, суммы по участникам зафиксированы.
- Сервис Заявок публикует ДГ-01 с полным составом участников, суммами, датами поездки и персональными данными участников.
- Сервис Договоров разбирает состав: по каждому участнику определяет, выпускается договор КМ, полис ЛМ или не выпускается ничего.
- Сервис Договоров сохраняет полученные персональные данные как снимок сторон договора.

### Фаза 2. Полисы ЛМ

- По родственникам без доплаты сервис Договоров публикует ДГ-06 в 1С:УСК.
- 1С:УСК выпускает полис по корпоративному договору и возвращает ДГ-07: идентификатор полиса, номер, период действия и ссылки на печатные формы.

### Фаза 3. Договоры КМ: проект и акцепт

- По участникам с доплатой сервис Договоров присваивает номер договора и сразу делает договор готовым к акцепту: проект договора — это его данные (номер, стороны, премия, даты); печатных форм сервис Договоров не формирует.
- Застрахованное лицо знакомится с данными договора в личном кабинете; сервис Заявок читает их синхронным вызовом СЭ-01.
- Застрахованное лицо проставляет отметку об акцепте. Факт акцепта фиксируется с привязкой к версии договора — тем данным, которые застрахованное лицо видело.

### Фаза 4. Счёт и оплата

Будет на этапе оплаты, уточняется при реализации.

- Сервис Договоров передаёт номер договора и сумму в Ordering Service и получает ссылку на оплату.
- Ссылка отдаётся застрахованному лицу через сервис Заявок. Оплата выполняется в Ordering Service, там же формируется фискальный документ.
- Факт оплаты поступает в сервис Договоров.

### Фаза 5. Выпуск и обратная связь

- Будет на этапе оплаты, уточняется при реализации. Сервис Договоров публикует ДГ-04 в 1С:УСК с данными оплаченного договора и справками 070/у участника в base64; печатные формы договора формирует 1С:УСК.
- 1С:УСК регистрирует договор, выпускает полис, формирует печатные формы и возвращает ДГ-05: идентификаторы, номера и постоянные ссылки на документы.
- Когда по всем участникам заявки работа завершена, сервис Договоров публикует ДГ-03 с результатом: полисы по каждому участнику, статусы оплаты и ссылки на документы.
- Сервис Заявок обновляет проекцию по участникам — km_contract_state, km_policy_id, payment_status, а для полисов ЛМ также policy_id, — проверяет условия готовности и публикует ИП-04 с ready_for_booking = true.

Прочие события обмена: ДГ-02 — прекращение работы по заявке при её аннулировании в сервисе Заявок, отдельный сокращённый контракт.

## Ограничения ТЗ

### В границах документа

- Обмен между сервисом Заявок и сервисом Договоров: состав и формат сообщений, топология очередей.
- Обмен сервиса Договоров с 1С:УСК по договорам КМ и полисам ЛМ.
- Граница между асинхронным и синхронным обменом, перечень синхронных вызовов.

### Вне границ документа

- Контракт взаимодействия с Ordering Service — согласуется отдельно, ОВД-12.
- Оплата как процесс, эквайринг и фискализация — выполняются в Ordering Service.
- Возвраты — на первом этапе выполняются вручную.
- Синхронизация справочников Дата-референса.
- Справка 070/у — хранится в сервисе Договоров (S3 контура): сервис Заявок передаёт её синхронной загрузкой по участнику, сервис Договоров отправляет её в 1С:УСК вместе с оплаченным договором КМ. Формат загрузки — ТЗ «Сервис Договоров. Синхронные эндпоинты».

### Принятые ограничения

| **№** | **Ограничение** |
|---|---|
| 1 | Сервис Договоров не взаимодействует с фронтом и БФФ. Все обращения пользователя проходят через сервис Заявок, который проксирует их в сервис Договоров синхронными вызовами. |
| 2 | Задача на выпуск передаётся одним сообщением на индивидуальную заявку и содержит полный состав участников. Разбор состава на договоры КМ и полисы ЛМ выполняется в сервисе Договоров. |
| 3 | Правило выпуска: застрахованное лицо без доплаты — ничего не выпускается, застрахованное лицо с доплатой — договор КМ, родственник без доплаты — полис ЛМ, родственник с доплатой — договор КМ. Доплата есть, если amount_due не меньше 0.01; 0.00 — доплаты нет. Правило принадлежит домену Договоров и в контракт не выносится. |
| 4 | Задача передаётся только после прохождения согласований ЦКЗ и ответственного от страхователя и фиксации сумм. Состав, суммы, даты и персональные данные участников передаются одним сообщением ДГ-01: расщепление на два транспорта создавало бы состояние, в котором задача принята, а данных для неё ещё нет. |
| 5 | По каждому направлению действует один универсальный контракт на создание и изменение с полным состоянием объекта в теле и отдельный сокращённый контракт на прекращение. |
| 6 | Ключом сообщений между сервисами служит идентификатор индивидуальной заявки, присвоенный в сервисе Заявок. Ключом сообщений с 1С:УСК служит идентификатор договора либо полиса, присвоенный в сервисе Договоров. |
| 7 | Номер договора КМ присваивается в сервисе Договоров при создании договора, формат DKM-ГГГГ-NNNNNN (латиница; год и счёт — по часовому поясу контура, по умолчанию московскому; счёт с 1 каждый год). Обмен с 1С:УСК выполняется в один раунд: передаётся готовый документ, обратно приходят идентификаторы и постоянные ссылки. |
| 8 | Печатные формы договора КМ и полисов формирует 1С:УСК и возвращает постоянными ссылками; срок их действия не ограничен. Сервис Договоров хранит только ссылки. В 1С:УСК в base64 в теле сообщения передаются справки 070/у. |
| 9 | Источник персональных данных — сервис Заявок. Сервис Договоров хранит снимок сторон договора; до акцепта снимок обновляется вслед за задачей на выпуск, после акцепта — нет. Персональные данные передаются в ДГ-01 между сервисами и в ДГ-04 и ДГ-06 наружу; ДГ-02 и ДГ-03 обезличены. Контракты ИП-01…ИП-06 остаются обезличенными. |
| 10 | Обе стороны применяют Outbox при публикации и Inbox при потреблении. |
| 11 | Все идентификаторы сущностей — GUID (UUID; записи сервиса Договоров — договор, полис, документ — получают UUID v7, упорядоченный по времени; message_id — UUID v4; получатель на версию UUID не полагается). Идентификаторы договора страхования, полиса страхователя, программы и выпущенного полиса в обмене с сервисом Заявок — идентификаторы Дата-референса; идентификаторы 1С:УСК (external_id) сервис Договоров берёт у Дата-референса сам при формировании ДГ-04 и ДГ-06. |

## Карта точек интеграции и очереди

### Точки интеграции

| **№** | **Направление** | **Событие** | **Когда публикуется** |
|---|---|---|---|
| ДГ-01 | Заявки → Договоры | ContractTaskUpserted | Согласования пройдены и суммы зафиксированы, либо состав или суммы изменились |
| ДГ-02 | Заявки → Договоры | ContractTaskCancelled | Индивидуальная заявка аннулирована, работу по договорам необходимо прекратить |
| ДГ-03 | Договоры → Заявки | ContractStatusChanged | Изменилось состояние выпуска по заявке, в том числе достигнуто завершение по всем участникам (правила — в описании ДГ-03) |
| ДГ-04 | Договоры → 1С:УСК | KmContractSubmitted | Договор КМ оплачен (будет на этапе оплаты) |
| ДГ-05 | 1С:УСК → Договоры | KmContractRegistered | Договор зарегистрирован, полис выпущен либо возникла ошибка (будет на этапе оплаты) |
| ДГ-06 | Договоры → 1С:УСК | LmPolicyRequested | Требуется выпуск полиса ЛМ родственнику без доплаты |
| ДГ-07 | 1С:УСК → Договоры | LmPolicyIssued | Полис ЛМ выпущен либо возникла ошибка |

ДГ-01 использует один контракт на создание и на изменение. Различие определяется на стороне сервиса Договоров: если работа по заявке ещё не начата — она начинается, иначе состояние сверяется с текущим. Порядок применения обновлений контролируется полем entity_version: оно общее для ДГ-01 и ДГ-02 одной заявки.

### Очереди

| **Источник** | **Очередь** | **Точки** |
|---|---|---|
| Сервис Заявок | rvl_requests_to_rvl_contracts_task-changes | ДГ-01, ДГ-02 |
| Сервис Договоров | rvl_contracts_to_rvl_requests_status-changes | ДГ-03 |
| Сервис Договоров | rvl_contracts_to_1c-usk_km-contract-changes | ДГ-04 |
| 1С:УСК | 1c-usk_to_rvl_contracts_km-contract-changes | ДГ-05 |
| Сервис Договоров | rvl_contracts_to_1c-usk_lm-policy-changes | ДГ-06 |
| 1С:УСК | 1c-usk_to_rvl_contracts_lm-policy-changes | ДГ-07 |

Договоры КМ и полисы ЛМ разведены по разным очередям: у них разный состав сообщения, разный объём тела и разные потребители на стороне 1С:УСК. Проблемное сообщение по договору не блокирует выпуск полисов. Обе очереди в сторону 1С:УСК несут персональные данные, требования к их защите согласуются с ИБ — ОВД-05.

Все очереди, в том числе те, которые читает сервис Договоров, заводят сервис Заявок (межсервисный брокер) и 1С:УСК (брокер 1С:УСК); сервис Договоров очереди не объявляет и публикует в обменник по умолчанию с ключом маршрутизации, равным имени очереди. Имена очередей у сервиса Договоров — настройки (переменные окружения).

### Параметры обмена

- Очереди durable, сообщения persistent (delivery_mode = 2).
- Обе стороны применяют Outbox при публикации и Inbox при потреблении: сообщение фиксируется в таблице собственной БД в одной транзакции с изменением данных, отправка и обработка выполняются отдельным процессом.
- Входящее сообщение подтверждается брокеру только после записи в Inbox. Сообщение с непригодным конвертом (тело не JSON; нет или неверно поле message_id, correlation_id, entity_version; topic пустой или длиннее 100 знаков, event_type — пустой или длиннее 50; в тексте символ \u0000 или непарный суррогат UTF-16) подтверждается и теряется с записью в журнале сервиса и счётчиком — повторять его бессмысленно.
- Повторная обработка выполняется из таблицы Inbox: первая попытка и 3 повтора с задержкой 1 / 5 / 15 минут при временном сбое (база, Дата-референс); нарушение контракта (нет обязательного поля, неизвестный event_type) отклоняется сразу. Сообщение, не обработанное после исчерпания попыток, помечается как ошибочное и выносится на разбор ответственным.
- Идемпотентность обеспечивается таблицей Inbox по message_id. Порядок сообщений по объекту — по entity_version: сообщение с версией не выше обработанной отбрасывается. Правило действует для ДГ-01 и ДГ-02 (по заявке); ответы 1С:УСК по версии не упорядочиваются.
- Публикация — с подтверждением брокера: нет подтверждения или отказ — повтор через 1 / 5 / 15 минут, затем окончательный отказ; брокер вернул сообщение «нет маршрута» (очереди нет) — окончательный отказ с первой попытки. message_id присваивается при записи в Outbox и не меняется, поэтому получатель может получить одно сообщение дважды с тем же message_id и отбрасывает повтор. Сообщения публикуются в порядке записи, но отложенное до повтора может прийти после более поздних: порядок снимков ДГ-03 получатель определяет по entity_version. Пока к брокеру нет соединения, попытки не считаются, сообщения ждут.
- Бизнес-ошибка не считается сбоем обработки: сообщение помечается обработанным, результат возвращается ответным сообщением с error_code и error_message.
- Payload — JSON, UTF-8. Даты — ISO 8601 с часовым поясом; сервис Договоров пишет моменты в UTC с Z, даты без времени — yyyy-mm-dd. Суммы — с двумя знаками после запятой, валюта RUB.
- Содержимое файлов передаётся в base64 в поле content_base64. В таблице Outbox содержимое не хранится: тело сообщения собирается на публикации из таблицы вложений.
- Тела сообщений в Outbox и Inbox стираются по сроку (по умолчанию 30 суток): в Inbox — при любом исходе, в Outbox — у опубликованных и отклонённых; запись сохраняется ради истории и идемпотентности. Окончательный срок согласуется с ИБ — ОВД-05.

| topic | string | Да | Топик сообщения, соответствует типу события (до 100 знаков) |

| source | string | Да | Система-источник: RVL-REQUESTS, RVL-CONTRACTS или 1C-USK |

### Синхронные вызовы

Асинхронно передаются команды, меняющие состояние объекта, вместе со всеми данными, необходимыми для их выполнения. Синхронно выполняются чтение, загрузка справок 070/у и действия пользователя, результат которых нужен в момент отрисовки интерфейса. Все вызовы к сервису Договоров выполняет сервис Заявок: прямых обращений фронта к сервису Договоров нет.

Состав запросов и ответов, коды ошибок и нефункциональные требования описаны в ТЗ «Сервис Договоров. Синхронные эндпоинты».

| **Вызов** | **Направление** | **Назначение** |
|---|---|---|
| СЭ-04 POST /requests/{individual_request_id}/participants/{participant_id}/attachments | Заявки → Договоры | Загрузка справки 070/у участника |
| СЭ-01 GET /requests/{id}/package | Заявки → Договоры | Состояние пакета по заявке: договоры, статусы, ссылка на оплату, ссылки на документы |
| СЭ-02 GET /documents/{id}/content | Заявки → Договоры | Не реализуется: проектов печатных форм нет, финальные формы доступны по постоянным ссылкам 1С:УСК |
| СЭ-03 POST /contracts/{id}/acceptance | Заявки → Договоры | Приём акцепта оферты. Синхронный, поскольку от результата сразу зависит выставление счёта |
| GET /programs/{id}, /policies/{id}/contract-view, /policies/contract-view?external_id=, /insurance-contracts/{id} | Договоры → Дата-референс | Чтение справочников: программы страхования, полисы без персональных данных, договоры страхования |
| POST /orders | Договоры → Ordering Service | Создание заказа на оплату по номеру договора, получение ссылки на оплату (будет на этапе оплаты) |
| Факт оплаты | Ordering Service → Договоры | Способ доставки не определён — ОВД-12 |

### Статусы договора и события интеграции

Внутренние статусы сервиса Договоров в сервис Заявок не транслируются. Наружу передаётся агрегированное состояние по заявке.

| **Статус договора КМ** | **Событие** |
|---|---|
| NEW | не публикуется; договор в этом статусе живёт только внутри обработки задачи и сразу становится DRAFT_READY |
| DRAFT_READY | ДГ-03, состояние заявки IN_PROGRESS, km_contract_state = DRAFTED; публикуется, когда договор впервые стал готов к акцепту |
| ACCEPTED | не публикуется |
| INVOICE_ISSUED | ДГ-03, состояние заявки IN_PROGRESS, payment_status = PENDING (будет на этапе оплаты) |
| PAID | не публикуется |
| SUBMITTED | ДГ-04 в 1С:УСК (будет на этапе оплаты) |
| ISSUED | устанавливается по входящему ДГ-05. ДГ-03 публикуется, когда завершены все участники заявки |
| ERROR | ДГ-03, состояние заявки ERROR; ошибка — не только регистрации в 1С:УСК, но и в данных участника из ДГ-01 |
| CANCELLED | ДГ-03, состояние заявки CANCELLED — при ДГ-02; прекращение одной записи (участник исключён, сменился вид документа) публикуется с состоянием заявки по остальным участникам |

Полис ЛМ: NEW (задача принята) → SUBMITTED (запрос ДГ-06 записан в Outbox) → ISSUED по ДГ-07; ERROR — справочник отказал, запрос не доставлен в 1С:УСК или 1С:УСК вернула ошибку; CANCELLED — по ДГ-02 или когда родственник исключён из поездки либо у него появилась доплата. Публикуются ERROR и CANCELLED; выпуск полиса виден в ДГ-03, когда завершена вся заявка.

### ДГ-01. Постановка и изменение задачи на выпуск

| **Параметр** | **Значение** |
|---|---|
| Направление | Сервис Заявок → Сервис Договоров |
| Очередь | rvl_requests_to_rvl_contracts_task-changes |
| Событие | ContractTaskUpserted |
| Триггер | Получены согласования ЦКЗ и ответственного от страхователя, суммы зафиксированы; любое последующее изменение состава или сумм |
| Реакция | Разбор состава участников, определение выпускаемых документов, сохранение снимка персональных данных, присвоение номеров договоров, договор КМ сразу готов к акцепту. Ответ — ДГ-03 по правилам публикации ДГ-03 |

Единственное сообщение между сервисами, несущее персональные данные. Они передаются здесь, а не отдельным вызовом: сервис Заявок и так является их владельцем, а разделение на два транспорта оставляло бы задачу принятой без данных, необходимых для её выполнения.

Участник, отсутствующий в массиве participants, считается исключённым из поездки: работа по нему прекращается (причина OTHER, комментарий «участник исключён из состава поездки»), в том числе по акцептованному договору.

Нарушение контракта (нет обязательного поля, значение не того типа, не GUID, отрицательная доплата, нет застрахованного лица или их два) отклоняет сообщение целиком без ответа — его разбирает дежурный. Значения gender, document.type, relation_type и program_id проверяются только у участников, которым что-то выпускается, и дают ошибку по участнику в ДГ-03, а не отказ сообщения; для договора КМ проверяются данные и участника, и застрахованного лица (страхователя).

Повторная задача (версия выше обработанной) сверяется с текущим состоянием: те же данные — ничего не меняется, ответа нет; новый участник — заводится выпуск; сменился вид документа — прежняя запись прекращается (OTHER, «вид документа по участнику изменён»), заводится новая; договор КМ до акцепта — премия, даты, программа и стороны обновляются, версия договора растёт, ответа нет (данные читаются вызовом СЭ-01); ошибка в данных у договора до акцепта переводит его в ERROR; договор КМ после акцепта и полис ЛМ, переданный в 1С:УСК, — изменения не применяются, ответа нет; после ДГ-02 задача с большей версией начинает работу заново новыми записями (новый номер договора). После ошибки любая задача с большей версией — исправленная или та же — заводит новую запись (для полиса ЛМ — и новый ДГ-06), запись с ошибкой остаётся в истории; та же ошибка ответа не даёт. ### ДГ-02. Прекращение работы по заявке

| **Параметр** | **Значение** |
|---|---|
| Направление | Сервис Заявок → Сервис Договоров |
| Очередь | rvl_requests_to_rvl_contracts_task-changes |
| Событие | ContractTaskCancelled |
| Триггер | Индивидуальная заявка аннулирована: отклонение ЦКЗ, отказ ответственного от страхователя, отказ застрахованного, истечение срока оплаты |
| Реакция | Прекращение работы по всем договорам и полисам заявки, кроме выпущенных и уже прекращённых (в том числе акцептованного договора, полиса, переданного в 1С:УСК, и записи в ошибке). Отдельный сокращённый контракт: состояние заявки в теле не передаётся. entity_version — общий с ДГ-01 той же заявки: задача с версией не выше прекращения после него пропускается.

|---|---|---|---|

| cancel_comment | string | Нет | Текстовый комментарий |

### ДГ-03. Результат выпуска по заявке

| **Параметр** | **Значение** |
|---|---|
| Направление | Сервис Договоров → Сервис Заявок |
| Очередь | rvl_contracts_to_rvl_requests_status-changes |
| Событие | ContractStatusChanged |
| Триггер | Запись участника впервые перешла в ошибку или прекращена; договор КМ впервые стал готов к акцепту; работа по заявке завершена по всем участникам (впервые или с другим составом); обработано ДГ-02. Не публикуется: по задаче, после которой у участников только новые полисы ЛМ; по задаче без изменений; по пропущенному или отклонённому входящему; по повторной задаче с той же ошибкой; по изменению данных договора до акцепта; по акцепту. Выставление счёта и оплата — будут на этапе оплаты. |
| Реакция | Обновление проекции договора и оплаты по участникам, проверка условий готовности и публикация ИП-04 с ready_for_booking = true при status = COMPLETED |

### ДГ-06. Запрос на выпуск полиса ЛМ

| **Параметр** | **Значение** |
|---|---|
| Направление | Сервис Договоров → 1С:УСК |
| Очередь | rvl_contracts_to_1c-usk_lm-policy-changes |
| Событие | LmPolicyRequested |
| Триггер | В составе поездки есть родственник без доплаты, не имеющий полиса; запрос готовит отдельный проход по расписанию (по умолчанию каждые 10 секунд) после чтения справочников — один запрос на запись полиса ЛМ |
| Реакция 1С | Выпуск полиса по корпоративному договору, размещение печатной формы. Ответ — ДГ-07 |

Родственник, стоимость поездки которого полностью покрывается лимитом, договор КМ не заключает, но должен быть застрахован. Оферта, счёт и оплата в этом сценарии не участвуют: полис оплачивается страхователем в рамках корпоративного договора. Печатная форма формируется в 1С:УСК, содержимое файлов в запросе не передаётся.

Перед запросом сервис Договоров читает у Дата-референса программу, договор страхования и полис страхователя и берёт их идентификаторы 1С:УСК. Дата-референс недоступен — запрос ждёт следующего прохода; записи нет или она в архиве — полис ЛМ в ERROR с кодом по участнику, запрос не уходит. Полис считается переданным (SUBMITTED) с момента записи запроса в Outbox. Запрос не доставлен или его доставка не подтверждена (очереди нет или исчерпаны попытки публикации) — полис в ERROR с кодом LM_POLICY_REQUEST_UNDELIVERED; если 1С:УСК всё же получила запрос и выпустила полис, её ответ запись не меняет, а следующая задача заводит новый запрос — риск второго полиса принят. Повторного запроса по той же записи нет; задача с большей версией после ошибки заводит новую запись и новый запрос. Ответа ждут без ограничения; дольше часа (настройка) — видно в метриках сервиса.

### ДГ-07. Результат выпуска полиса ЛМ

| **Параметр** | **Значение** |
|---|---|
| Направление | 1С:УСК → Сервис Договоров |
| Очередь | 1c-usk_to_rvl_contracts_lm-policy-changes |
| Событие | LmPolicyIssued |
| Триггер | Полис выпущен либо выпуск невозможен |
| Реакция | Сохранение полиса и ссылок, перевод записи в ISSUED. Публикация ДГ-03 при завершении работы по всем участникам заявки; при status = ERROR — полис в ERROR, ДГ-03 с ошибкой по участнику |

| **Поле** | **Тип** | **Обяз.** | **Описание** |
|---|---|---|---|
| id | guid | Да | Идентификатор полиса ЛМ из ДГ-06 в сервисе Договоров, возвращается без изменений |
| policy_usk_id | guid | Условно | Идентификатор документа в 1С:УСК. Обязательно при status = ISSUED |
| policy_usk_number | string | Нет | Номер документа в 1С:УСК |
| status | string | Да | ISSUED / ERROR |
| policy | object | Условно | Выпущенный полис: external_id, number, date_from, date_to. Обязательно при status = ISSUED; обязательны external_id и number, date_from и date_to не читаются — период полиса равен датам поездки из ДГ-01 |
| documents[] | array | Нет | Печатные формы полиса: doc_type (CONTRACT / POLICY / APPENDIX, обязательно), file_url (обязательно), file_size (необязательно, целое) |
| error_code | string | Условно | Обязательно при status = ERROR; хранится и передаётся в ДГ-03 как пришло, перечень — ОВД-09 |
| error_message | string | Условно | Обязательно при status = ERROR |

Обработка. ISSUED: сервис находит выпущенный полис в Дата-референсе по policy.external_id — его идентификатор уходит в ДГ-03 как policy_id. Полис может ещё не дойти до Дата-референса (404 POLICY_NOT_FOUND): сервис повторяет поиск ограниченное число раз, затем откладывает сообщение на 1 / 5 / 15 минут; не нашёл и тогда — сообщение отклоняется, полис остаётся SUBMITTED, вернуть сообщение в разбор может дежурный. Полис найден, но в архиве Дата-референса, или поиск отклонён с другим кодом — сообщение отклоняется сразу. Повтор с тем же message_id отбрасывается; ответ с новым message_id по уже выпущенному, ошибочному или прекращённому полису обрабатывается, но запись не меняется. Ответ по полису, запрос по которому ещё не отправлялся, по неизвестному id, с неверным status или doc_type, без обязательного поля — нарушение контракта, сообщение отклоняется сразу. Порядок по entity_version для ДГ-07 не применяется: ответы по разным полисам заявки независимы.
