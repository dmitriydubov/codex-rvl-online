# Сервис Договоров. Синхронные эндпоинты

Редакция 2 от 22.10.2026. Действующее описание синхронной части обмена сервиса Договоров; первая редакция документа — без даты. В редакцию перенесены и правки 2026-10-05 к разделу о чтении справочников Дата-референса, сверенные с кодом сервиса. Оплата (Ordering Service) ещё не реализована и описана как в первой редакции с пометкой «будет на этапе оплаты, уточняется при реализации».

Документ описывает синхронную часть обмена сервиса Договоров: эндпоинты, которые он предоставляет сервису Заявок, чтение справочников Дата-референса и обращение к Ordering Service. Асинхронные точки ДГ-01…ДГ-07 описаны в ТЗ «Точки интеграции Заявки — Договоры» и здесь не повторяются.

Разделение простое: асинхронно передаются команды, меняющие состояние объекта, вместе со всеми данными для их выполнения. Синхронно выполняются чтение, загрузка справок и действия пользователя, результат которых нужен в момент отрисовки интерфейса.

## Общие положения

### Контур и маршрутизация

Сервис Договоров не имеет внешнего контура. Обращения к нему выполняет только сервис Заявок. Фронтенд и BFF доступа к нему не имеют: всё, что застрахованное лицо видит по договору и оплате, проходит через сервис Заявок, который проксирует вызов и возвращает ответ без изменения смысла.

Эндпоинты размещены под префиксом /internal и на внешнем периметре не публикуются. Ограничение доступа обеспечивается сетевой политикой контура; межсервисной аутентификации нет.

### Общие правила

| **Параметр** | **Значение** |
|---|---|
| Базовый путь | https://{contracts-service}/internal/v1 |
| Версионирование | В пути: /v1. Несовместимые изменения выпускаются новой версией, старая поддерживается до перевода потребителя |
| Формат | JSON, UTF-8, имена полей в snake_case. Исключение — загрузка справки: запрос multipart/form-data, ответ JSON |
| Даты | ISO 8601 с часовым поясом; моменты в ответах сервис Договоров пишет в UTC с Z; даты без времени — yyyy-mm-dd |
| Суммы | Число с двумя знаками после запятой, валюта RUB |
| Идентификаторы | GUID (UUID; записи сервиса Договоров получают UUID v7, на версию UUID клиент не полагается) |
| Аутентификация | Нет: доступ ограничивает сетевая политика контура |
| Трассировка | Заголовок X-Request-Id передаётся сквозняком и возвращается в ответе и в теле ошибки. Принимается значение из 1–64 знаков A–Z a–z 0–9 . _ -; другое или отсутствующее заменяется новым UUID, оно и возвращается |
| Таймаут вызова | 5 секунд для чтения состояния; для приёма акцепта — больше 5 секунд: договор, занятый обработкой задачи, сервис ждёт до таймаута блокировки базы (по умолчанию 5 с) и отвечает 503; для загрузки справки — больше 20 секунд (общий таймаут вызова хранилища по умолчанию) |
| Повторы | Допустимы только для GET. POST повторяется исключительно с тем же ключом идемпотентности: у загрузки справки — attachment_id, у акцепта — договор и contract_version. На 503 — повторить тот же запрос позже |

### Коды ответов

| **Код** | **Когда возвращается** |
|---|---|
| 200 OK | Запрос выполнен |
| 400 Bad Request | Нарушен формат запроса: неверный тип, отсутствует обязательное поле |
| 401 Unauthorized | Не используется |
| 403 Forbidden | Не используется |
| 404 Not Found | Объект с переданным идентификатором отсутствует |
| 409 Conflict | Состояние объекта не допускает операцию: договор уже акцептован, передана устаревшая версия договора, работа по заявке прекращена, вложение уже принято с другим содержимым |
| 422 Unprocessable Entity | Не используется |
| 500 Internal Server Error | Внутренняя ошибка сервиса |
| 503 Service Unavailable | Сервис временно недоступен либо недоступен внешний контрагент (хранилище файлов); договор занят другой операцией |

### Формат ошибки

Единый для всех эндпоинтов. Текст message предназначен для журнала, а не для показа пользователю: решение о том, что показать застрахованному лицу, принимает сервис Заявок.

| **Поле** | **Тип** | **Обяз.** | **Описание** |
|---|---|---|---|
| error.code | string | Да | Машиночитаемый код ошибки из перечня в п. 5 |
| error.message | string | Да | Описание на русском языке |
| error.details | array | Да (может быть пустым) | Перечень нарушений по полям: field, reason . reason — «обязательное поле не передано», «неверный формат», для файла — «тип файла не допускается», «размер файла вне допустимого», «размер файла больше допустимого»; у DOCUMENT_VERSION_MISMATCH — «актуальная версия договора — N» |
| error.request_id | string | Да | Значение X-Request-Id, по которому ошибку можно найти в журнале |

```json
{
  "error": {
    "code": "DOCUMENT_VERSION_MISMATCH",
    "message": "акцептуется не актуальная версия договора КМ",
    "details": [
      { "field": "contract_version", "reason": "актуальная версия договора — 2" }
    ],
    "request_id": "a41f8c02-7d3b-4e19-9a55-2c7e0b6f1d84"
  }
}
```

### СЭ-01. Состояние пакета по заявке

| **Параметр** | **Значение** |
|---|---|
| Метод и путь | GET /internal/v1/requests/{individual_request_id}/package |
| Назначение | Вернуть актуальное состояние договоров, полисов, документов и оплаты по индивидуальной заявке |
| Когда вызывается | Открытие застрахованным лицом раздела документов и оплаты, обновление экрана после действия |
| Идемпотентность | Запрос без побочных эффектов, повторы допустимы |

Сервис Заявок ссылки на документы и на оплату у себя не хранит: они читаются этим вызовом при каждом обращении. В базе данных сервиса Заявок сохраняется только проекция — km_contract_state, km_policy_id, payment_status и другие поля участника, поддерживаемые сообщением ДГ-03.

404 REQUEST_NOT_FOUND — по заявке не было ни задачи на выпуск, ни прекращения. Если прекращение пришло раньше задачи — 200 со status = CANCELLED и пустым items.

### СЭ-02. Выдача содержимого документа

Не реализуется. Проектов печатных форм у сервиса Договоров нет: договор КМ акцептуется по его данным (СЭ-03), а финальные формы договора и полисов формирует 1С:УСК и отдаёт постоянными ссылками (ДГ-05, ДГ-07), которые приходят в ДГ-03 и СЭ-01. Текст первой редакции ниже сохранён для истории и не действует.

| **Параметр** | **Значение** |
|---|---|
| Метод и путь | GET /internal/v1/documents/{document_id}/content |
| Назначение | Вернуть содержимое печатной формы для ознакомления застрахованного лица |
| Когда вызывается | Открытие проекта договора до его размещения в 1С:УСК |
| Ответ | Поток байтов. Content-Type: application/pdf, Content-Disposition: inline, Content-Length, ETag — контрольная сумма файла |
| Идемпотентность | Запрос без побочных эффектов, повторы допустимы |

Документ версии FINAL этим вызовом не выдаётся: после размещения в 1С:УСК он доступен по постоянной ссылке, полученной в ДГ-05 или ДГ-07, и проксировать его через два сервиса незачем. Запрос содержимого финального документа возвращает 409 со ссылкой в теле ошибки.

Сервис Заявок передаёт поток застрахованному лицу без сохранения. Заголовок ETag равен полю file_hash и позволяет убедиться, что пользователь видит ровно ту версию, которая будет акцептована.

| **Код HTTP** | **error.code** | **Когда** |
|---|---|---|
| 404 | DOCUMENT_NOT_FOUND | Документ с переданным идентификатором отсутствует |
| 409 | DOCUMENT_IS_FINAL | Запрошено содержимое финального документа. Постоянная ссылка возвращается в error.details |
| 503 | STORAGE_UNAVAILABLE | Внутреннее хранилище файлов недоступно |

### СЭ-03. Приём акцепта оферты

| **Параметр** | **Значение** |
|---|---|
| Метод и путь | POST /internal/v1/contracts/{contract_id}/acceptance |
| Назначение | Зафиксировать акцепт оферты застрахованным лицом |
| Когда вызывается | Застрахованное лицо проставило отметку в личном кабинете |
| Реакция | Создание записи акцепта, перевод договора в ACCEPTED; создание заказа в Ordering Service и получение ссылки на оплату — будут на этапе оплаты, уточняется при реализации. ДГ-03 акцепт не публикует |
| Идемпотентность | По contract_id. Повторный вызов с тем же contract_version возвращает 200 и ранее созданную запись, состояние не меняется |

Вызов синхронный, поскольку от его результата сразу зависит следующий шаг пользователя: появление кнопки оплаты. Сейчас ответ всегда без ссылки на оплату (state = ACCEPTED). На этапе оплаты: ссылка на оплату возвращается в том же ответе, если Ordering Service ответил в пределах таймаута; иначе возвращается состояние ACCEPTED без ссылки, и ссылку следует получить вызовом СЭ-01.

Проекта договора в PDF нет — печатные формы формирует 1С:УСК после регистрации, поэтому акцептуется версия данных договора (номер, стороны, премия, даты), которую застрахованное лицо видело в СЭ-01. После акцепта данные договора вслед за задачами сервиса Заявок не меняются. Запись акцепта неизменяема; адрес и клиент хранятся только в ней и в журнал сервиса не пишутся.

Тело запроса

| **Поле** | **Тип** | **Обяз.** | **Описание** |
|---|---|---|---|
| contract_version | int | Да | Версия договора, которую акцептовали (contract_version из СЭ-01). Должна быть актуальной |
| document_hash | — | — | Удалено |
| accepted_by | guid | Да | Пользователь, выполнивший акцепт: GUID пользователя сервиса Заявок, хранится как пришёл |
| accepted_at | datetime | Да | Дата и время акцепта на стороне сервиса Заявок; без часового пояса — 400 |
| channel | string | Да | WEB / MOBILE |
| ip_address | string | Нет | IP-адрес пользователя (IPv4 или IPv6; другое — 400) |
| user_agent | string | Нет | Клиент, из которого выполнен акцепт |

Тело ответа

| **Поле** | **Тип** | **Обяз.** | **Описание** |
|---|---|---|---|
| contract_id | guid | Да | Идентификатор договора |
| state | string | Да | ACCEPTED; INVOICE_ISSUED, если ссылка на оплату уже получена, — будет на этапе оплаты |
| accepted_at | datetime | Да | Зафиксированное время акцепта — момент из первой записи акцепта, в UTC |
| payment | object | Нет | Оплата, если заказ создан: status, amount, payment_url, expires_at (будет на этапе оплаты) |

Коды ошибок

| **Код HTTP** | **error.code** | **Когда** |
|---|---|---|
| 400 | VALIDATION_ERROR | Нарушен формат тела или пути: нарушение по полю в details; тело не JSON — без details |
| 404 | CONTRACT_NOT_FOUND | Договор с переданным идентификатором отсутствует |
| 409 | ALREADY_ACCEPTED | Договор уже акцептован по другой версии договора |
| 409 | DOCUMENT_VERSION_MISMATCH | Акцептуется не актуальная версия договора (данные изменились). Актуальная версия — в error.details: field = contract_version |
| 409 | DOCUMENT_HASH_MISMATCH | Не используется: контрольной суммы файла нет |
| 409 | INVALID_STATE | Состояние договора не допускает акцепт: работа прекращена или договор уже выпущен; договор в ошибке; прекращён и акцептованный ранее договор |
| 503 | SERVICE_UNAVAILABLE | Договор занят другой операцией (обработкой задачи) дольше таймаута блокировки базы; повторить тот же запрос |
| 503 | ORDERING_UNAVAILABLE | Акцепт зафиксирован, заказ на оплату создать не удалось. Повторное получение ссылки — вызовом СЭ-01 (будет на этапе оплаты) |

ORDERING_UNAVAILABLE возвращается кодом 503, но акцепт при этом уже сохранён: повторять вызов не нужно, достаточно получить ссылку позже. Это единственное место, где код ответа не описывает состояние объекта полностью.

### СЭ-04. Загрузка справки 070/у

Новый раздел. Контракт согласован с разработчиком сервиса Заявок.

| **Параметр** | **Значение** |
|---|---|
| Метод и путь | POST /internal/v1/requests/{individual_request_id}/participants/{participant_id}/attachments, Content-Type: multipart/form-data |
| Назначение | Принять справку 070/у участника заявки и сохранить её в хранилище S3 контура |
| Когда вызывается | Застрахованное лицо загрузило справку по себе или по родственнику; справка — на каждого участника, файлов по участнику может быть несколько, каждый под своим attachment_id |
| Идемпотентность | По attachment_id: повтор с тем же содержимым по тому же участнику — 200 и прежняя запись; другое содержимое или другой участник — 409 ATTACHMENT_CONFLICT |

| **Часть запроса** | **Обяз.** | **Описание** |
|---|---|---|
| attachment_id | Да | GUID вложения в сервисе Заявок; ключ идемпотентности |
| file | Да | Файл справки. Тип — из заголовка Content-Type части: image/jpeg, image/png или application/pdf; размер — от 1 байта до 5 МБ (запрос целиком — до 10 МБ). Содержимое файла не проверяется; имя файла не хранится |

Проверки по порядку: формат запроса — 400 VALIDATION_ERROR; тип и размер файла — 400 VALIDATION_ERROR с field = file; задачи на выпуск по заявке ещё не было — 404 REQUEST_NOT_FOUND (повторить позже); участника нет в последней задаче — 404 PARTICIPANT_NOT_FOUND (в том числе если пришло только прекращение без задачи); работа по заявке прекращена — 409 INVALID_STATE; тот же attachment_id уже принят — 200 и прежняя запись или 409 ATTACHMENT_CONFLICT; хранилище недоступно — 503 STORAGE_UNAVAILABLE (повторить позже). Справка не попадает ни в СЭ-01, ни в ДГ-03; ни файл, ни его имя не пишутся в журнал сервиса.

## Чтение справочников Дата-референса

Сервис Договоров читает справочники синхронно, в момент формирования исходящего сообщения (ДГ-06; ДГ-04 — будет на этапе оплаты) и при поиске выпущенного полиса по ДГ-07. Данные нужны на момент формирования сообщения, кэширование на стороне сервиса Договоров не выполняется: справочники ведутся в Дата-референсе и там же изменяются.

| **Вызов** | **Назначение** | **Что берётся** |
|---|---|---|
| GET /internal/v1/programs/{id} | Программа страхования | Наименование, external_id для 1С:УСК, перечень услуг, is_archive |
| GET /internal/v1/policies/{id}/contract-view и /internal/v1/policies/contract-view?external_id={uuid} | Полис без персональных данных | id, external_id, number, begin_date, end_date, is_archive |
| GET /internal/v1/insurance-contracts/{id} | Договор страхования страхователя | Номер, external_id, страхователь (краткое и полное наименование; null, если страхователь — физическое лицо), is_archive |

Идентификаторы external_id подтягиваются из справочников при формировании сообщений ДГ-04 и ДГ-06 и в таблицах сервиса Договоров не дублируются. Недоступность Дата-референса блокирует выпуск: сообщение не формируется, задача остаётся в текущем состоянии и повторяется по общим правилам.

Правила клиента. Даты у Дата-референса — yyyy-mm-dd, открытая дата 1С — null. Таймаут соединения — 2 с, ответа — 7 с: при отказе своей базы Дата-референс отвечает 503 SERVICE_UNAVAILABLE в худшем случае примерно через 5 с, и клиент не обрывает запрос раньше. Ответ 503, таймаут, обрыв соединения и ответ не из контракта повторяются ограниченное число раз (по умолчанию 3 повтора с паузой 1 с), затем — «справочник недоступен». 404 по id программы, договора или полиса и ответ is_archive = true — ошибка выпуска по участнику (PROGRAM_NOT_FOUND, PROGRAM_ARCHIVED, INSURANCE_CONTRACT_NOT_FOUND и т. д.), другой отказ 4xx с кодом — ошибка по участнику с этим кодом. Полис, только что выпущенный в 1С:УСК, может ещё не дойти до Дата-референса — 404 POLICY_NOT_FOUND при поиске по external_id повторяется ограниченно, затем входящее сообщение откладывается по лестнице 1 / 5 / 15 минут. X-Request-Id передаётся сквозняком: при разборе входящего сообщения — его message_id, при подготовке запроса полиса ЛМ — идентификатор записи полиса ЛМ, иначе новый UUID.

## Обращение к Ordering Service

Будет на этапе оплаты, уточняется при реализации.

Ordering Service — существующий внутренний сервис. Он ничего не знает о страховании: получает номер договора и сумму, возвращает ссылку на оплату. Эквайринг, фискализация и возвраты выполняются в нём.

| **Вызов** | **Направление** | **Назначение** |
|---|---|---|
| POST /orders | Договоры → Ordering | Создание заказа: номер договора, сумма. В ответе — идентификатор заказа и ссылка на оплату |
| GET /orders/{id} | Договоры → Ordering | Чтение состояния заказа. Используется при расхождении и при отсутствии факта оплаты |
| Факт оплаты | Ordering → Договоры | Способ доставки не определён: вебхук, очередь или опрос — ОВС-02 |

Контракт Ordering Service принадлежит его владельцу и в настоящем документе не фиксируется: приведён состав данных, необходимый сервису Договоров. Детальное согласование — ОВС-02.

Номер договора выступает ключом связи: он присваивается в сервисе Договоров до создания заказа, и по нему же адресуется факт оплаты. Идентификатор заказа сохраняется в payment_orders.external_order_id.

## Нефункциональные требования

- Время ответа СЭ-01 и СЭ-03 — не более 1 секунды на 95 процентах запросов, без учёта времени ответа Ordering Service.
- Время ответа СЭ-04 определяется размером файла (до 5 МБ) и записью в хранилище.
- Недоступность сервиса Договоров не должна блокировать работу сервиса Заявок: раздел документов отображается с сообщением о временной недоступности, остальные функции заявки сохраняются.
- Журналирование: каждый вызов фиксируется с X-Request-Id, путём и кодом ответа. Тела запросов, содержащие персональные данные, в журнал не записываются; файл справки и его имя — тоже.
- Удалено

## Открытые вопросы

| **№** | **Вопрос** | **Приоритет** |
|---|---|---|
| ОВС-01 | Закрыт: межсервисной аутентификации нет, доступ ограничивает сетевая политика контура | Высокий |
| ОВС-02 | Контракт Ordering Service: состав запроса на создание заказа, способ доставки факта оплаты, срок жизни ссылки, поведение при повторной оплате | Высокий |

| ОВС-04 | Нужен ли сервису Заявок отдельный вызов на принудительное обновление ссылки на оплату, если срок её действия окажется ограниченным | Средний |
| ОВС-05 | Закрыт: акцепт выполняет застрахованное лицо за всех, одна запись акцепта на договор | Средний |
