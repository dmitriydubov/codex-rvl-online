# Структура данных (Сервис договоров)

Редакция 2 от 22.10.2026. Действующая структура данных сервиса Договоров — по схеме базы сервиса; первая редакция документа — без даты. Таблицы этапа оплаты (payment_orders) описаны как в первой редакции с пометкой «будет на этапе оплаты, уточняется при реализации».

Документ описывает структуру данных сервиса Договоров: выпуск договоров КМ и полисов ЛМ, хранение ссылок на печатные формы 1С:УСК и справок 070/у, фиксацию акцепта оферты и взаимодействие с Ordering Service. Формат сообщений обмена описан в ТЗ «Точки интеграции Заявки — Договоры».

## Схема данных

### Область и границы

В границах документа

- Перечень таблиц сервиса Договоров, состав полей, индексы и связи.
- Перечисления, реализуемые нативными типами PostgreSQL.
- Таблицы интеграции: Outbox, Inbox и хранение вложений сообщений.

Вне границ документа

- Оплата как процесс и фискализация — выполняются в Ordering Service.
- Справка 070/у как документ сервиса Заявок; сервис Договоров хранит её файл в S3 контура и ведёт реестр в contract_documents.
- Справочники: программы страхования, полисы, договоры страхования, услуги прейскуранта — читаются из Дата-референса.
- Возвраты — на первом этапе выполняются вручную вне системы.
- Контракты обмена — в ТЗ «Точки интеграции Заявки — Договоры».

### Принятые ограничения

| **№** | **Ограничение** |
|---|---|
| 1 | Сервис Договоров — бэкенд без пользовательского интерфейса. С фронтом и БФФ он не взаимодействует. Единственный собеседник внутри контура РВЛ ОНЛАЙН — сервис Заявок. |
| 2 | Выпускаемый документ определяется участником и наличием доплаты: застрахованное лицо без доплаты — ничего не выпускается, застрахованное лицо с доплатой — договор КМ, родственник без доплаты — полис ЛМ по корпоративному договору, родственник с доплатой — договор КМ. Доплата есть при amount_due от 0.01. |
| 3 | Страхователем по договору КМ всегда выступает застрахованное лицо по корпоративному договору. Застрахованным может быть как оно само, так и родственник. |
| 4 | Номер договора КМ присваивается в сервисе Договоров при создании записи. Обмен с 1С:УСК выполняется в один раунд. |
| 5 | Печатные формы договора КМ и полисов формирует 1С:УСК; обратно приходят постоянные ссылки, сервис хранит только их. Справки 070/у участников сервис хранит в S3 контура и передаёт в 1С:УСК в base64 вместе с оплаченным договором. |
| 6 | Источник персональных данных — сервис Заявок. Они приходят в теле сообщения ДГ-01. Сервис Договоров хранит снимок сторон договора; до акцепта снимок обновляется вслед за задачей на выпуск, после акцепта — не обновляется, поскольку договор должен соответствовать акцептованным данным. |
| 7 | Даты договора равны датам поездки; до акцепта они обновляются вслед за задачей, после акцепта — не меняются. |
| 8 | Акцепт оферты выполняется проставлением отметки в личном кабинете. Факт акцепта фиксируется в базе данных с привязкой к версии договора (entity_version). |
| 9 | Все идентификаторы сущностей — GUID (UUID; записи сервиса получают UUID v7 — упорядоченный по времени, удобный для индексов). |
| 10 | Идентификаторы объектов сервиса Заявок (индивидуальная заявка, участник) хранятся значением. Внешние ключи между базами данных разных сервисов не устанавливаются — в том числе на справочники Дата-референса. |

Внешние ключи на справочники ссылаются на первичные ключи Дата-референса: insurance_programs.id, policies.id, insurance_contracts.id — логически: значения — идентификаторы Дата-референса, ограничения внешнего ключа нет (другая база). Идентификаторы 1С:УСК в справочниках не дублируются: при формировании исходящего сообщения значение external_id подтягивается по связи.

### contracts — договор КМ

Одна запись на участника поездки, у которого amount_due больше нуля, среди незавершённых (не ISSUED, ERROR, CANCELLED). Договор выпускается однократно, после прохождения согласований и фиксации сумм.

| **Поле** | **Тип** | **Обяз.** | **Описание** |
|---|---|---|---|
| id | UUID | Да | Первичный ключ. Сквозной идентификатор объекта в интеграции |
| number | VARCHAR(50) | Да | Номер договора КМ, уникален. Присваивается в сервисе Договоров при создании записи в формате DKM-ГГГГ-NNNNNN (латиница, год и счёт — по часовому поясу контура) |
| status | contract_status | Да | Статус договора. Перечень значений — в п. 9 |
| individual_request_id | UUID | Да | Идентификатор индивидуальной заявки в сервисе Заявок |
| insured_participant_id | UUID | Да | Идентификатор участника-застрахованного в сервисе Заявок |
| policyholder_participant_id | UUID | Да | Идентификатор участника-страхователя. Всегда застрахованное лицо по корпоративному договору. Может совпадать с insured_participant_id |
| insurance_contract_id | UUID | Да | Идентификатор Дата-референса (insurance_contracts.id). Корпоративный договор страхования |
| insurer_policy_id | UUID | Да | Идентификатор Дата-референса (policies.id). Полис страхователя по корпоративному договору. Передаётся в 1С:УСК для связи |
| program_id | UUID | Нет | Идентификатор Дата-референса (insurance_programs.id). Программа страхования участника из ДГ-01 |
| date_from | DATE | Да | Дата начала действия договора. Равна дате заезда |
| date_to | DATE | Да | Дата окончания действия договора. Равна дате выезда |
| insured_amount | NUMERIC(15,2) | Нет | Страховая сумма — размер страхового покрытия. Источник значения не определён, ОВД-01; сейчас не заполняется |
| premium_amount | NUMERIC(15,2) | Да | Страховая премия. Равна amount_due участника, полученному из сервиса Заявок |
| issued_policy_id | UUID | Нет | Идентификатор Дата-референса (policies.id). Полис, выпущенный по договору. Заполняется по результату регистрации в 1С:УСК, возвращается в сервис Заявок (будет на этапе оплаты) |
| issued_policy_number | VARCHAR(50) | Нет | Номер выпущенного полиса |
| contract_usk_id | UUID | Нет | Идентификатор документа в 1С:УСК. Первоначально не заполняется |
| contract_usk_number | VARCHAR(50) | Нет | Номер документа в 1С:УСК |
| payment_order_id | UUID | Нет | FK payment_orders.id. Заказ на оплату. Пусто до выставления счёта (колонки ещё нет — будет на этапе оплаты) |
| error_code | VARCHAR(50) | Нет | Код ошибки: в данных участника из ДГ-01 или регистрации в 1С:УСК |
| error_message | TEXT | Нет | Текст ошибки (без персональных данных) |
| cancel_reason | contract_cancel_reason | Нет | Причина прекращения работы по договору |
| cancel_comment | TEXT | Нет | Комментарий к прекращению (из ДГ-02 или служебный: «участник исключён из состава поездки», «вид документа по участнику изменён», «неизвестный код причины …») |
| cancelled_at | TIMESTAMPTZ | Нет | Дата и время прекращения |
| entity_version | INT | Да | Версия объекта. Увеличивается при каждом изменении; до акцепта — версия, которую акцептуют в СЭ-03 |
| created_at | TIMESTAMPTZ | Да | Дата и время создания |
| updated_at | TIMESTAMPTZ | Да | Дата и время последнего изменения |

Индексы: UQ по number; по individual_request_id; UQ по insured_participant_id среди незавершённых записей (статус не ISSUED, ERROR, CANCELLED); по status; по contract_usk_id.

Страховая сумма и страховая премия — разные величины: премия равна сумме доплаты застрахованного, страховая сумма описывает объём покрытия по программе.

### contract_number_counters — счётчик номеров

Одна строка на год: last_number — последний выданный номер. Номер договора — DKM-&lt;год&gt;-&lt;last_number + 1, шесть цифр&gt;; год — по часовому поясу контура (по умолчанию московскому) на момент создания договора. Номер не переиспользуется: новая запись после ошибки или прекращения получает новый номер.

| **Поле** | **Тип** | **Обяз.** | **Описание** |
|---|---|---|---|
| year | INT | Да | Год, первичный ключ |
| last_number | INT | Да | Последний выданный номер в году |

### contract_documents — документы

В таблице два вида документов. Печатные формы 1С:УСК (договор, полис, приложение) — финальные, только ссылкой: файл хранит 1С:УСК. Справки 070/у участников — файл в S3 контура, запись — реестр (ключ объекта, хэш, тип, размер). Проектов печатных форм нет.

| **Поле** | **Тип** | **Обяз.** | **Описание** |
|---|---|---|---|
| id | UUID | Да | Первичный ключ |
| contract_id | UUID | Условно | FK contracts.id. Заполняется для документов по договору КМ |
| lm_policy_id | UUID | Условно | FK lm_policies.id. Заполняется для документов по полису ЛМ |
| individual_request_id | UUID | Условно | FK issuance_requests.individual_request_id. Заполняется для справки 070/у |
| participant_id | UUID | Условно | Участник заявки. Заполняется для справки |
| attachment_id | UUID | Условно | Идентификатор вложения в сервисе Заявок, уникален. Заполняется для справки; ключ идемпотентности загрузки |
| kind | printed_form_kind | Да | DRAFT — проект, FINAL — финальный документ; сейчас всегда FINAL |
| doc_type | printed_form_type | Да | Тип документа: договор, полис, приложение, справка 070/у |
| version | INT | Да | Версия документа; сейчас всегда 1 |
| file_key | TEXT | Условно | Ключ объекта в S3 контура. Обязателен для справки |
| file_hash | VARCHAR(64) | Условно | SHA-256 содержимого файла. Обязателен для справки: по нему повторная загрузка отличается от конфликтующей |
| file_size | BIGINT | Нет | Размер файла в байтах; обязателен для справки, у формы 1С:УСК — как прислала 1С:УСК |
| content_type | VARCHAR(100) | Условно | MIME-тип файла. Для справки — image/jpeg, image/png или application/pdf |
| usk_file_url | TEXT | Нет | Постоянная ссылка на документ, полученная из 1С:УСК. Заполняется для печатных форм 1С:УСК |
| created_at | TIMESTAMPTZ | Да | Дата и время записи |

Ограничение: ровно одно из полей contract_id, lm_policy_id и individual_request_id должно быть заполнено. individual_request_id, participant_id и attachment_id заполнены вместе; у справки обязательны file_key, file_hash, file_size, content_type, и только у неё doc_type = MEDICAL_CERTIFICATE. Индексы: по contract_id; по lm_policy_id; составной по (contract_id, doc_type, kind, version); UQ по attachment_id; по (individual_request_id, participant_id).

Ссылки из 1С:УСК постоянные, срок действия не ограничен. Поле expires_at, в отличие от гарантийных писем сервиса Заявок, не требуется.

Имя файла справки не хранится; объект в S3 лежит под уникальной папкой {uuid}/ внутри базового пути, повторная загрузка с другим attachment_id создаёт новый объект.

### contract_acceptances — акцепт оферты

Договор КМ заключается акцептом оферты: застрахованное лицо знакомится с данными договора и проставляет отметку в личном кабинете. Запись об акцепте неизменяема и хранит привязку к версии договора.

| **Поле** | **Тип** | **Обяз.** | **Описание** |
|---|---|---|---|
| id | UUID | Да | Первичный ключ |
| contract_id | UUID | Да | FK contracts.id |
| contract_version | INT | Да | Версия договора (contracts.entity_version), которую акцептовали |
| document_hash | — | — | Удалено |
| accepted_by | UUID | Да | Пользователь, выполнивший акцепт. GUID пользователя сервиса Заявок, хранится как пришёл |
| accepted_at | TIMESTAMPTZ | Да | Дата и время акцепта на стороне сервиса Заявок |
| channel | acceptance_channel | Да | Канал: WEB или MOBILE |
| ip_address | INET | Нет | IP-адрес, с которого выполнен акцепт |
| user_agent | TEXT | Нет | Клиент, из которого выполнен акцепт |
| created_at | TIMESTAMPTZ | Да | Дата и время создания записи |

Индексы: UQ по contract_id; по document_id.

Акцепт за родственников выполняет застрахованное лицо; отдельного согласия совершеннолетнего родственника нет, одна запись акцепта на договор.

### lm_policies — полисы ЛМ

Родственник, стоимость поездки которого полностью покрывается лимитом, договор КМ не получает, но должен быть застрахован. Для него в 1С:УСК выпускается полис по корпоративному договору. Цикл короткий: задача принята, запрос отправлен, полис получен. Оферта, счёт и оплата в нём не участвуют.

| **Поле** | **Тип** | **Обяз.** | **Описание** |
|---|---|---|---|
| id | UUID | Да | Первичный ключ. Сквозной идентификатор объекта в интеграции |
| status | lm_policy_status | Да | Статус выпуска. Перечень значений — в п. 9 |
| individual_request_id | UUID | Да | Идентификатор индивидуальной заявки в сервисе Заявок |
| participant_id | UUID | Да | Идентификатор участника в сервисе Заявок. Родственник без доплаты |
| policyholder_participant_id | UUID | Да | Идентификатор застрахованного лица, к которому относится родственник |
| insurance_contract_id | UUID | Да | Идентификатор Дата-референса (insurance_contracts.id). Корпоративный договор, по которому выпускается полис |
| insurer_policy_id | UUID | Да | Идентификатор Дата-референса (policies.id). Полис застрахованного лица, для связи |
| program_id | UUID | Нет | Идентификатор Дата-референса (insurance_programs.id). Программа страхования из ДГ-01 |
| date_from | DATE | Да | Дата начала действия — дата заезда |
| date_to | DATE | Да | Дата окончания действия — дата выезда |
| issued_policy_id | UUID | Нет | Идентификатор Дата-референса (policies.id) выпущенного полиса, найденный по его external_id из ДГ-07, возвращается в сервис Заявок |
| issued_policy_number | VARCHAR(50) | Нет | Номер выпущенного полиса |
| policy_usk_id | UUID | Нет | Идентификатор документа в 1С:УСК |
| policy_usk_number | VARCHAR(50) | Нет | Номер документа в 1С:УСК |
| error_code | VARCHAR(50) | Нет | Код ошибки выпуска: данные участника, справочник, недоставленный запрос или код 1С:УСК как пришёл |
| error_message | TEXT | Нет | Текст ошибки выпуска |
| cancel_reason | contract_cancel_reason | Нет | Причина прекращения |
| cancel_comment | TEXT | Нет | Комментарий к прекращению |
| cancelled_at | TIMESTAMPTZ | Нет | Дата и время прекращения |
| entity_version | INT | Да | Версия объекта; передаётся в meta.entity_version ДГ-06 |
| created_at | TIMESTAMPTZ | Да | Дата и время создания |
| updated_at | TIMESTAMPTZ | Да | Дата и время последнего изменения |

Индексы: по individual_request_id; UQ по participant_id среди незавершённых записей; по status; по policy_usk_id.

Полис ЛМ для родственника оплачивается страхователем в рамках корпоративного договора. Счёт застрахованному не выставляется, обращение к Ordering Service не выполняется.

### contract_persons — стороны договора

Снимок персональных данных, на основании которого заключается договор КМ или запрашивается полис ЛМ. Источник данных — сервис Заявок, таблица participant_personal_data. Данные приходят в теле сообщения ДГ-01 вместе с постановкой задачи на выпуск.

До акцепта снимок обновляется вслед за задачей на выпуск. После акцепта не обновляется: договор должен соответствовать тем данным, которые были акцептованы; изменения из задачи не применяются. У полиса ЛМ снимок не обновляется после передачи запроса в 1С:УСК.

| **Поле** | **Тип** | **Обяз.** | **Описание** |
|---|---|---|---|
| id | UUID | Да | Первичный ключ |
| contract_id | UUID | Условно | FK contracts.id. Заполняется для сторон договора КМ |
| lm_policy_id | UUID | Условно | FK lm_policies.id. Заполняется для застрахованного по полису ЛМ |
| role | person_role | Да | POLICYHOLDER — страхователь, INSURED — застрахованный |
| participant_id | UUID | Да | Идентификатор участника в сервисе Заявок |
| last_name | VARCHAR(100) | Да | Фамилия |
| first_name | VARCHAR(100) | Да | Имя |
| middle_name | VARCHAR(100) | Нет | Отчество |
| birth_date | DATE | Да | Дата рождения |
| gender | gender | Да | Пол |
| relation_type | VARCHAR(50) | Условно | Степень родства. Обязательно для родственника |
| document_type | identity_doc_type | Да | Тип документа, удостоверяющего личность |
| document_series | VARCHAR(20) | Нет | Серия документа |

Состав полей и срок хранения после завершения поездки подлежат согласованию с ИБ — ОВД-05; до ответа данные не стираются.

### issuance_requests и request_participants — заявка и её состав

Сервис Договоров отвечает сервису Заявок снимком по всем участникам последней задачи, в том числе тем, кому ничего не выпускается: для них записей в contracts и lm_policies нет. Поэтому состав последней обработанной задачи хранится отдельно — без персональных данных. Запись заявки создаёт первая обработанная ДГ-01 или ДГ-02.

## Таблицы интеграции

Реализуют паттерны Outbox и Inbox по тем же правилам, что приняты в сервисе Заявок. Запись в outbox_messages выполняется в одной транзакции с изменением данных, публикация — отдельным процессом. Входящее сообщение сначала сохраняется в inbox_messages, затем обрабатывается; повторная доставка с тем же message_id отсекается по уникальному индексу.

### message_attachments

Таблица создана, будет использоваться на этапе оплаты (ДГ-04), уточняется при реализации.

Целостность обеспечивается контрактами обмена.

Обратная проекция в сервисе Заявок уже предусмотрена согласованной структурой данных: поля km_contract_id, km_contract_state, km_policy_id, km_policy_number и payment_status таблицы individual_request_participants поддерживаются входящим сообщением ДГ-03. Сумма премии, срок и способ оплаты, реквизиты и файлы печатных форм в сервисе Заявок не хранятся.
