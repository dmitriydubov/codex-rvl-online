# История изменений contract-service

Здесь записаны заметные изменения сервиса по версиям, новые сверху. Формат — [Keep a Changelog 1.1.0](https://keepachangelog.com/en/1.1.0/),
номера версий — по [Semantic Versioning 2.0.0](https://semver.org/spec/v2.0.0.html):

- **MAJOR** — ломается контракт синхронных вызовов `/internal/v1`, контракт очередей с сервисом Заявок или 1С:УСК или
  эксплуатация: удалена или переименована переменная окружения, появилась обязательная переменная без умолчания,
  миграция базы без обратной совместимости.
- **MINOR** — новая возможность без поломки, в том числе новая переменная с умолчанием и миграция, которая только добавляет.
- **PATCH** — исправление без новых возможностей.

Рубрики версии: Добавлено, Изменено, Устарело, Удалено, Исправлено, Безопасность и Перенос — что нужно сделать на контуре
при установке версии.

## [Не выпущено]

### Добавлено

- Каркас сервиса: приложение на Spring Boot 4.0.7 и Java 21, подключение к PostgreSQL с миграциями Liquibase (схема
  пока пустая), журнал в JSON (ECS), метрики Prometheus и health на порту управления, пробы `/livez` и `/readyz` на
  порту API, версия сервиса в `/actuator/info`.
- Образ (`Dockerfile`) и локальный контур с базой и двумя брокерами (`docker-compose.yml`).
- Подключения к двум брокерам RabbitMQ — межсервисному брокеру контура (сервис Заявок) и брокеру 1С:УСК: у каждого
  свои настройки (`projectx.brokers.internal`, `projectx.brokers.onec`), подключение с подтверждениями издателя и
  возвратами немаршрутизируемых сообщений, шаблон публикации (`mandatory`), фабрика контейнеров слушателей (ручное подтверждение, один потребитель, одно сообщение в работе,
  отказ запуска без очереди) и компонент здоровья `internalBroker` / `onecBroker` в `/actuator/health`. Недоступный
  брокер не роняет старт. Слушателей очередей и публикаций пока нет; очереди сервис не объявляет.
- Метрики подключений к брокерам `rabbitmq_*` с меткой `name` (`internalBroker`, `onecBroker`).
- Чтение справочников сервиса справочных данных по его внутреннему API: программа, договор страхования и полис без
  персональных данных по идентификатору справочника, полис — ещё и по идентификатору 1С:УСК. Адрес, таймауты и повторы
  — настройки `projectx.reference`; ответ 503, таймаут, обрыв соединения и ответ не из контракта повторяются
  ограниченно и после исчерпания повторов становятся ошибкой «справочник недоступен»; «не найдено» по идентификатору,
  запись в архиве и отказ справочника с его кодом (статус 4xx) — окончательные ошибки; «не найден» полис по
  идентификатору 1С:УСК повторяется, пока полис идёт в справочник. Каждый запрос несёт сквозной `X-Request-Id`. Кэша нет.
- Схема сервиса: перечисления PostgreSQL (`contract_status`, `lm_policy_status`, `contract_cancel_reason`,
  `person_role`, `gender`, `identity_doc_type`, `inbox_status`), таблицы договоров КМ (`contracts`) со счётчиком номеров
  по году (`contract_number_counters`), полисов ЛМ (`lm_policies`), сторон договора (`contract_persons`) и журнала
  входящих сообщений (`inbox_messages`); уникальность участника среди незавершённых записей — частичными индексами.
- Приём сообщений сервиса Заявок из очереди задач: сообщение сохраняется в журнал входящих целиком и подтверждается
  брокеру после фиксации, повтор по `message_id` подтверждается без второй записи, сообщение с непригодным конвертом
  или с символом, который `jsonb` не хранит (нулевой, непарный суррогат), подтверждается и теряется с записью ERROR,
  при любом другом отказе базы сообщение возвращается в очередь после паузы.
- Обработка журнала входящих отдельным проходом по расписанию: порядок по версии заявки (сообщение с версией не выше
  обработанной пропускается с причиной), временный отказ базы повторяется по лестнице пауз (`1m,5m,15m`), после
  исчерпания сообщение отклоняется окончательно с записью ERROR и счётчиком `contracts_inbox_failed_total{event_type}`;
  нарушение контракта отклоняется с первой попытки с причиной без значений; тела сообщений стираются по сроку хранения
  (`INBOX_PAYLOAD_RETENTION`, умолчание 30 суток), записи с исходом остаются.
- Задача на выпуск: по каждому участнику поездки сервис решает, что выпускается (застрахованное лицо без доплаты —
  ничего, с доплатой — договор КМ, родственник без доплаты — полис ЛМ, с доплатой — договор КМ), присваивает договору
  номер `DKM-ГГГГ-NNNNNN` со сквозным счётом в году по московскому времени, хранит даты поездки, премию и снимок сторон;
  повторная задача с большей версией добавляет новых участников, прекращает исчезнувших, меняет вид документа и
  пересчитывает реквизиты ещё не выпущенного договора; ошибка в данных участника даёт запись в ERROR с кодом
  (`RELATION_TYPE_REQUIRED`, `UNKNOWN_DOCUMENT_TYPE`, `UNKNOWN_GENDER`).
- Прекращение работы по заявке: договоры и полисы заявки переводятся в CANCELLED с причиной по словарю сервиса
  (`CKZ_REJECTED`, `HR_REJECTED` → `REQUEST_CANCELLED`; `INSURED_REFUSED`, `EXPIRED`, `OTHER` — одноимённо), комментарием
  и моментом аннулирования из сообщения; история сохраняется. Код причины вне словаря прекращение не отклоняет: оно
  применяется с причиной `OTHER`, код — в комментарии прекращения (значение не по формату кода заменяется пометкой),
  WARN в журнале и счётчик `contracts_cancel_reason_unknown_total{event_type}`.
- Настройки обработки и стирания (`INBOX_*`) и часового пояса нумерации (`CONTRACT_NUMBERING_ZONE`) — с умолчаниями;
  выключатель расписаний `projectx.scheduling.enabled` для тестов.
- Журнал исходящих сообщений (`outbox_messages`, перечисление `outbox_status`; таблица вложений `message_attachments`
  пока пустая): запись делается в одной транзакции с изменением данных, публикует её отдельный проход по расписанию
  пачками в порядке создания, с подтверждением брокера по каждому сообщению; доставлено — только подтверждение без
  возврата. Немаршрутизируемое сообщение (очереди нет, `NO_ROUTE` 312) отклоняется окончательно с первой попытки; отказ
  брокера и молчание дольше `OUTBOX_CONFIRM_TIMEOUT` повторяются по лестнице `OUTBOX_RETRY_BACKOFF`, после исчерпания —
  окончательный отказ с записью ERROR и счётчиком `contracts_outbox_failed_total{event_type}`; тела опубликованных и
  отклонённых сообщений стираются по сроку `OUTBOX_PAYLOAD_RETENTION`. Идентификатор сообщения присваивается записи при
  создании и не меняется — повтор не создаёт дубля у получателя.
- Ответ сервису Заявок о состоянии выпуска (`ContractStatusChanged` в очередь `INTERNAL_QUEUE_STATUS_CHANGES`):
  самодостаточный снимок по всем участникам последней задачи (вид документа, состояние договора КМ, его номер и
  идентификатор, статус оплаты, документы, код и текст ошибки) и статус заявки IN_PROGRESS / COMPLETED / ERROR /
  CANCELLED; уходит после разбора входящего, когда запись участника перешла в ошибку или прекращена, когда по всем
  участникам работа завершена и после каждого обработанного прекращения; `entity_version` конверта — порядковый номер
  снимка по заявке. Снимок с договором КМ без проекта откладывается до следующего публикуемого изменения; договор КМ с
  ошибкой в данных передаётся как аннулированный с кодом ошибки. Состав последней задачи хранится без персональных
  данных (`issuance_requests`, `request_participants`).
- Счётчик потерянных входящих сообщений `contracts_inbox_lost_total{reason}` (`unusable_envelope`, `unreadable_body`,
  `unstorable_text`).
- Настройки публикации и стирания исходящих (`OUTBOX_*`) — с умолчаниями.
- Программа страхования участника: задача на выпуск несёт `participants[].program_id` (идентификатор программы у
  сервиса справочных данных) у каждого участника, которому выпускается документ; программа сохраняется в договоре КМ и
  полисе ЛМ, у записи в состоянии «новый» повторная задача её меняет. Нет программы у такого участника — ошибка по
  участнику с кодом `PROGRAM_REQUIRED` (сообщение обработано, запись в ERROR); колонка `program_id` остаётся
  необязательной, пока сервис Заявок не подтвердит расширение задачи.
- Запрос на выпуск полиса ЛМ в 1С:УСК (`LmPolicyRequested` в очередь `ONEC_QUEUE_LM_POLICY_REQUESTS` брокера 1С:УСК):
  отдельный проход по расписанию берёт новые полисы ЛМ в порядке создания, читает у сервиса справочных данных внешние
  идентификаторы программы, договора страхования и полиса страхователя и в одной транзакции пишет запрос в журнал
  исходящих и переводит полис в SUBMITTED (версия растёт). Запрос несёт персональные данные родственника; тело стирается
  по сроку `OUTBOX_PAYLOAD_RETENTION`. Справочник недоступен — полис остаётся новым до следующего прохода, запись WARN и
  счётчик `contracts_reference_unavailable_total{kind}`; запись в архиве или не найдена — полис в ERROR с кодом
  справочника (`PROGRAM_ARCHIVED`, `INSURANCE_CONTRACT_ARCHIVED`, `POLICY_ARCHIVED`, `PROGRAM_NOT_FOUND`,
  `INSURANCE_CONTRACT_NOT_FOUND`, `POLICY_NOT_FOUND`) и ответ сервису Заявок. Повторная задача по переданному полису
  изменений не применяет (WARN); исчезнувший участник и прекращение работы прекращают и переданный полис, запрос в
  1С:УСК не отзывается.
- Результат выпуска полиса ЛМ из 1С:УСК (`LmPolicyIssued` из очереди `ONEC_QUEUE_LM_POLICY_ISSUES`): принимается в тот
  же журнал входящих тем же слушателем; порядок по версии — внутри своего типа события (объект результата — полис, не
  заявка). Выпущен — сервис находит свой полис у сервиса справочных данных по идентификатору 1С (не найден —
  повторы внутри обработки, после них сообщение откладывается по лестнице журнала), сохраняет `policy_usk_id`,
  `policy_usk_number`, номер и идентификатор выпущенного полиса и печатные формы (`contract_documents`, вид `FINAL`,
  постоянные ссылки 1С:УСК), полис переходит в ISSUED; ошибка — полис в ERROR с кодом и текстом 1С:УСК как пришли.
  Повторный или запоздавший результат по завершённому полису записи не меняет (WARN); результат по полису без
  отправленного запроса или по неизвестному идентификатору, без обязательных полей или с неизвестным статусом —
  нарушение контракта, окончательный отказ.
- Ответ сервису Заявок по участнику с полисом ЛМ: `policy_id` (идентификатор выпущенного полиса у сервиса справочных
  данных), `policy_number`, `documents` (печатные формы полиса: `document_id`, `doc_type`, `kind`, `url`).
- Счётчик `contracts_reference_unavailable_total{kind}` — обращения к сервису справочных данных, не получившие ответа
  после всех повторов.
- Настройки прохода запросов на выпуск полисов ЛМ (`LM_POLICY_REQUEST_INTERVAL`, `LM_POLICY_REQUEST_BATCH_SIZE`) — с
  умолчаниями.
- Приём справок по форме 070/у от сервиса Заявок: `POST /internal/v1/requests/{individual_request_id}/participants/{participant_id}/attachments`
  (multipart: `attachment_id`, `file`). Принимаются JPEG, PNG и PDF до 5 МиБ (`ATTACHMENT_MAX_FILE_SIZE`), содержимое не
  проверяется; файл ложится в хранилище S3 под уникальной папкой, запись — в реестр документов (`contract_documents`:
  хэш SHA-256, тип, размер, ключ объекта). Повтор того же вложения возвращает прежнюю запись; тот же идентификатор
  вложения с другим содержимым или по другому участнику — 409 `ATTACHMENT_CONFLICT`; неизвестная заявка — 404
  `REQUEST_NOT_FOUND`, участник не из состава — 404 `PARTICIPANT_NOT_FOUND`, прекращённая заявка — 409 `INVALID_STATE`;
  хранилище недоступно — 503 `STORAGE_UNAVAILABLE`.
- Общая основа синхронных вызовов: единый формат ошибки (`error.code`, `error.message`, `error.details[]`,
  `error.request_id`), 400 `VALIDATION_ERROR` с названным полем, 500 `INTERNAL_ERROR`; сквозной `X-Request-Id` — из
  запроса или новый UUID, в ответе, в теле ошибки и в журнале вызова.
- Состояние пакета документов по заявке для личного кабинета: `GET /internal/v1/requests/{individual_request_id}/package`
  — по каждому участнику последней задачи вид документа, номер и версия договора КМ, состояние (NOT_REQUIRED, DRAFTED,
  ACCEPTED, ISSUED, ERROR, CANCELLED), премия, номер выпущенного полиса, сведения об акцепте, оплата (после акцепта —
  PENDING на сумму премии без ссылки), постоянные ссылки на формы из 1С:УСК, код и текст ошибки; справки 070/у в пакет
  не попадают; неизвестная заявка — 404 `REQUEST_NOT_FOUND`.
- Акцепт оферты договора КМ: `POST /internal/v1/contracts/{contract_id}/acceptance` (`contract_version`, `accepted_by`,
  `accepted_at`, `channel` WEB или MOBILE, необязательные `ip_address` и `user_agent`) записывает акцепт и переводит
  договор в «акцептован»; повтор той же версии — 200 и прежняя запись; другая версия после акцепта — 409
  `ALREADY_ACCEPTED`, устаревшая версия до акцепта — 409 `DOCUMENT_VERSION_MISMATCH` с актуальной версией, прекращённый
  или ошибочный договор — 409 `INVALID_STATE`, неизвестный договор — 404 `CONTRACT_NOT_FOUND`, строка договора занята
  дольше таймаута блокировки — 503 `SERVICE_UNAVAILABLE`; нечитаемое тело JSON — 400 `VALIDATION_ERROR`.
- Акцептованный договор КМ не меняется повторной задачей: изменения не применяются, в журнал — WARN, ответа сервису
  Заявок нет; прекращение работы прекращает и акцептованный договор.
- Настройки хранилища S3 (`projectx.storage`: адрес, регион, бакет, начало ключа, ключи доступа, набор SSL с
  сертификатом внутреннего УЦ, таймауты соединения, чтения, записи и всего вызова) и приёма справок
  (`projectx.attachments`: предельный размер, допустимые типы).
- Счётчики `contracts_attachments_stored_total`, `contracts_attachments_rejected_total{reason}` и
  `contracts_storage_unavailable_total`.
- Правила кода сервиса записаны в `docs/code-style.md`; кодировку, концы строк и отступы задают `.editorconfig` и
  `.gitattributes` модуля.
- Окончательно не доставленный запрос на выпуск полиса ЛМ переводит полис в ERROR с кодом
  `LM_POLICY_REQUEST_UNDELIVERED`, и сервис Заявок получает ошибку по участнику; новый запрос уходит по новой записи
  после задачи с большей версией.
- Сводка полисов ЛМ, ждущих ответа 1С:УСК: метрики `contracts_lm_policies_awaiting_oldest_seconds` и
  `contracts_lm_policies_awaiting_overdue`, их пересчитывает отдельный проход; настройки
  `LM_POLICY_REQUEST_AWAITING_INTERVAL` и `LM_POLICY_REQUEST_AWAITING_THRESHOLD` — с умолчаниями.
- Процедура возврата отклонённого входящего сообщения в разбор с новым счётом попыток — в `docs/operations.md`.
- Проверка таймаутов сеанса базы при старте: расхождение `lock_timeout`, `statement_timeout` или
  `idle_in_transaction_session_timeout` пула с настройками даёт WARN, старт не останавливается.
- Запрос к сервису справочных данных несёт в `X-Request-Id` `message_id` обрабатываемого входящего сообщения или
  идентификатор полиса ЛМ, по которому готовится запрос в 1С:УСК.
- Передача оплаченного договора КМ в 1С:УСК (`KmContractSubmitted` в очередь `ONEC_QUEUE_KM_CONTRACT_SUBMISSIONS`):
  отдельный проход по расписанию берёт оплаченные договоры, читает у сервиса справочных данных внешние идентификаторы
  программы, договора страхования и полиса страхователя, берёт снимок обеих сторон, момент акцепта и справки 070/у
  застрахованного и в одной транзакции с блокировкой строки договора пишет передачу в журнал исходящих и переводит
  договор в «передан в 1С:УСК». Содержимое справок в журнале не хранится: по строке вложения на справку
  (`message_attachments`), публикатор читает объекты из хранилища при отправке и вставляет их в base64. Сообщение больше
  предела `KM_CONTRACT_MAX_MESSAGE_SIZE` не пишется — договор переходит в ERROR с кодом `KM_CONTRACT_MESSAGE_TOO_LARGE`.
  Хранилище недоступно при публикации — передача ждёт следующего прохода без потери попытки; объекта справки нет —
  передача отклонена окончательно.
- Момент оплаты договора КМ (`contracts.paid_at`, миграция `011-contract-payment`) и переход договора в оплаченный
  (`ContractPayments`); оплата через Ordering подключается следующим этапом. В ответе сервису Заявок у договора с
  моментом оплаты `payment_status` — `PAID`.
- Результат регистрации договора КМ из 1С:УСК (`KmContractRegistered` из очереди `ONEC_QUEUE_KM_CONTRACT_REGISTRATIONS`)
  принимается тем же журналом входящих: зарегистрирован — идентификатор и номер документа 1С, выпущенный полис (свой
  идентификатор ищется у сервиса справочных данных по `external_id` с повторами, как у полиса ЛМ), печатные формы с
  постоянными ссылками, договор в «выпущен»; регистрация невозможна — договор в ERROR с кодом и текстом 1С:УСК как
  пришли. Повторный и запоздавший результат записи не меняет; результат по договору, передача которого не отправлялась,
  и по неизвестному договору отклоняется как нарушение контракта.
- Ответ сервису Заявок по участнику с договором КМ после выпуска: `km_policy_id` и `km_policy_number` выпущенного
  полиса, `documents` — печатные формы договора из 1С:УСК; в состоянии пакета — `ISSUED`, номер полиса и формы.
- Окончательно не доставленная передача договора КМ переводит договор в ERROR с кодом

  отказы хранилища при чтении справок для публикации.

### Изменено

- README сокращён до короткого входа для эксплуатации: стек, таймауты, поведение при недоступности соседей,
  очереди, диагностика по базе. Причины решений перенесены в `docs/design.md`, сборка, запуск, все настройки, метрики и
  правила оповещения — в `docs/operations.md`.
- Договор КМ становится готовым к акцепту (DRAFT_READY) в той же обработке задачи на выпуск, в которой приняты
  стороны, суммы и даты: проекта договора в PDF у сервиса нет, печатные формы делает 1С:УСК. Сервис Заявок получает
  снимок с состоянием «проект сформирован» и пустым списком документов, в том числе по заявкам, где раньше снимок
  откладывался из-за договора без проекта. Изменение данных договора до акцепта оставляет его готовым к акцепту с новой
  версией и нового снимка не даёт.
- Запросы полисов ЛМ и передачи договоров КМ в 1С:УСК идут одним механизмом (`service/usk`): проход подготовки,
  запись в журнал исходящих, реакция на недоставку, сводка ожидания и приём результата общие, а вид записи описывает
  `IssuanceKind`; ответы 1С:УСК обоих видов разбирает один `UskResultParser` по раскладке полей (`UskResultLayout`),
  результат — `UskResult`. Классы `LmPolicyResult` и `LmPolicyIssuedParser` удалены, реквизиты документа 1С у
  выпущенного полиса названы `uskId` и `uskNumber`; очереди обоих видов читает тот же слушатель.
- Слушатель очередей и реестр его очередей переименованы: `TaskQueueListener` → `InboxQueueListener`,
  `TaskQueueEndpoints` → `InboxQueueEndpoints`; тот же слушатель принимает и задачи сервиса Заявок, и результаты
  выпуска полисов ЛМ из 1С:УСК, каждую очередь — на подключении своего брокера.
- Обработка журнала входящих разделена на подготовку вне транзакции и применение в транзакции: чтение справочников
  больше не попадает в транзакцию базы; временный отказ справочника откладывает сообщение по той же лестнице, что отказ
  базы.
- Пул планировщика расширен до шести потоков: добавились проходы подготовки запросов на выпуск полисов ЛМ и сводки
  полисов ЛМ, ждущих ответа 1С:УСК.

- У адреса сервиса справочных данных (`REFERENCE_URL`) больше нет умолчания: без него сервис не стартует и называет
  поле; адрес локального контура — в `docs/operations.md` и `.env.example`, профиль `app` compose задаёт его сам.
- Класс разбора кода ошибки справочника переименован: `ReferenceErrorBodies` → `ReferenceErrorCodes`.
- Пул планировщика расширен до четырёх потоков (`spring.task.scheduling.pool.size`): по потоку на каждый проход —
  разбор входящих, публикация исходящих и два стирания тел.

- Локальный контур (`docker-compose.yml`) публикует порты со сдвигом, чтобы подниматься рядом с локальным контуром
  сервиса справочных данных: база `5433`, межсервисный брокер `5674`/`15674`, брокер 1С:УСК `5675`/`15675`, сервис в
  контейнере `8082`, его актуатор `8083`. Умолчания `DB_URL`, `RABBITMQ_INTERNAL_PORT` и `RABBITMQ_ONEC_PORT` ведут на
  новые порты. Порты самого сервиса (`8080`, `8081`) не менялись. Профиль `app` подключается к сети локального контура
  data-reference (`data-reference_default`) и ждёт его стенд поднятым.

### Исправлено

- Выпущенный полис ЛМ не запрашивается в 1С:УСК повторно: следующая задача на выпуск по заявке видит выпущенный полис
  или договор КМ и его не перевыпускает. Задача без изменений по участнику ничего не делает; изменения, смена вида
  документа и исключение участника к выпущенной записи не применяются, в журнал сервиса уходит предупреждение. Заявка,
  по которой всё выпущено, остаётся завершённой.
- Полис ЛМ не теряет выпуск из 1С:УСК при одновременной последней попытке отправки запроса: реакция на недоставленный
  запрос и запись результата выпуска читают строку полиса с блокировкой и решают по её состоянию под блокировкой.
  Выпущенный полис отказ отправки не меняет, результат выпуска по полису в ошибке запись не меняет. Ожидание блокировки
  ограничено `DB_LOCK_TIMEOUT`, новых настроек нет.
- Запрос полиса ЛМ не уходит в 1С:УСК по участнику, работа по которому уже прекращена: подготовка запроса, разбор задачи
  на выпуск и прекращение работы по заявке берут строку полиса ЛМ с блокировкой (прекращение — и строку договора КМ) и
  решают по её состоянию под блокировкой; записи заявки блокируются в одном порядке, чтобы два разбора не ждали друг
  друга. Ожидание ограничено `DB_LOCK_TIMEOUT`, отказ по таймауту — временная ошибка, новых настроек нет.

### Безопасность

- У паролей базы и брокеров нет умолчания: без `DB_PASSWORD`, `RABBITMQ_INTERNAL_PASSWORD` и `RABBITMQ_ONEC_PASSWORD`
  сервис не стартует, а не подключается с известным паролем.
- TLS к брокерам по умолчанию проверяет сертификат и имя хоста; выключается только явно, переменными.
- Health подключений не показывает учётные данные брокеров.
- Текст ошибки базы не несёт значений строки (`logServerErrorDetail=false` у пула и в умолчании `DB_URL`).
- Порт управления отделён от порта API.
- Справка 070/у и имя её файла не попадают в журнал, метрики, тексты ошибок и ответы; имя файла не хранится. У ключей
  доступа к S3 нет умолчания, в журнал они не пишутся.
- IP-адрес и клиент принявшего оферту хранятся только в записи акцепта и не попадают в журнал, метрики и тексты ошибок.
