# contract-service — эксплуатация

Сборка, запуск и настройки сервиса Договоров, метрики и что делать при сбоях. Коротко о сервисе — в [README](../README.md),
почему он устроен так — в [design.md](design.md).

## Стек и версии

Java 21, Spring Boot 4.0.7 (Spring Framework 7.0.8, Spring Data JPA 4.0.6, Spring AMQP 4.0.4), Hibernate ORM 7.2.19,
Liquibase 5.0.3, PostgreSQL 16 (драйвер 42.7.11, пул HikariCP 7.0.2), RabbitMQ 4.1 (клиент 5.27.1), Jackson 3.1.4,
клиент S3 MinIO Java SDK 8.6.0,
Micrometer 1.16.6 с реестром Prometheus, встроенный Tomcat 11.0.22, сборка Gradle 8.14.3. Версии библиотек задаёт BOM
Spring Boot. Версия сервиса — в `gradle.properties` (`version=`), история изменений — в [CHANGELOG.md](../CHANGELOG.md).

## Порты

- `8080` — внутренний API для сервиса Заявок (`/internal/v1/…`: загрузка справки 070/у по участнику заявки, состояние
  пакета документов по заявке, акцепт оферты договора КМ) и пробы `/livez`, `/readyz`.
- `8081` (`MANAGEMENT_PORT`) — `/actuator/health`, `/actuator/info` (версия сервиса), `/actuator/prometheus`.
- Локальный контур (`docker-compose.yml`) публикует порты со сдвигом, чтобы рядом поднимался локальный контур сервиса
  справочных данных (у него база `5432`, брокер `5672`/`15672`, сервис `8080`, актуатор `8081`): база `5433`;
  межсервисный брокер `5674`, его панель `15674`; брокер 1С:УСК `5675`, его панель `15675`; сервис в контейнере
  (профиль `app`) — `8082`, его актуатор — `8083`. Внутри сети compose порты штатные.

| Переменная | Умолчание | Что задаёт |
|---|---|---|
| `REFERENCE_URL` | — | адрес внутреннего API справочников вместе с базовым путём, без слэша на конце; умолчания нет, локальный контур data-reference — `http://localhost:8080/internal/v1` |
| `REFERENCE_CONNECT_TIMEOUT` | `2s` | таймаут установки соединения |
| `REFERENCE_READ_TIMEOUT` | `7s` | таймаут ответа на запрос; не меньше 7 с — см. [design.md](design.md), «Таймаут чтения справочника» |
| `REFERENCE_MAX_RETRIES` | `3` | сколько раз повторить чтение после первой неудачи; `0` — без повторов |

Хранилище S3 контура — справки 070/у (см. [design.md](design.md), «Справки 070/у и хранилище»). Бакет создаётся
заранее, сервис его не создаёт; на бакете нужна политика жизненного цикла, которая убирает объекты без записи в реестре
(сироты после отказа базы).

| Переменная | Умолчание | Что задаёт |
|---|---|---|
| `S3_ENDPOINT` | — | адрес S3 со схемой и портом, без слэша на конце, например `https://s3.contour:9000` |
| `S3_REGION` | `us-east-1` | регион S3; без него клиент спрашивал бы регион бакета отдельным запросом |
| `S3_BUCKET` | — | бакет справок |
| `S3_INN` | `0000000000` | ИНН организации — 10 цифр, начало ключа объекта; умолчание — заглушка, на контуре задаётся настоящий ИНН |
| `S3_KPP` | `000000000` | КПП организации — 9 цифр, идёт в ключ объекта после ИНН; умолчание — заглушка, на контуре задаётся настоящий КПП |
| `S3_BASE_PATH` | `certificates` | папка справок без слэшей по краям; ключ объекта — `{ИНН}_{КПП}/{base-path}/{uuid}/{вложение}.{jpg\|png\|pdf}`, ссылка на файл в передаче договора КМ — `/{бакет}/{ключ}` |
| `S3_ACCESS_KEY` | — | ключ доступа; только из окружения |
| `S3_SECRET_KEY` | — | секретный ключ; только из окружения |
| `S3_SSL_BUNDLE` | пусто | имя набора SSL Spring Boot с сертификатом внутреннего УЦ; пусто — доверие JVM |
| `S3_CONNECT_TIMEOUT` | `2s` | таймаут соединения |
| `S3_READ_TIMEOUT` | `10s` | таймаут ожидания ответа |
| `S3_WRITE_TIMEOUT` | `10s` | таймаут передачи данных |
| `S3_CALL_TIMEOUT` | `20s` | предел всего вызова с повторами соединения; меньше 30 с, которые ждёт сервис Заявок |
| `ATTACHMENT_MAX_FILE_SIZE` | `5MB` | наибольший размер файла справки (5 МиБ); больше 10 МБ не поднимать — это предел контейнера сервлетов; выше 5 МиБ файл уходит в S3 частями, и `S3_CALL_TIMEOUT` действует на каждую |

Сертификат внутреннего УЦ для S3 задаётся набором SSL Spring Boot, например:
`SPRING_SSL_BUNDLE_PEM_STORAGE_TRUSTSTORE_CERTIFICATE=file:/etc/contract-service/s3-ca.pem` и `S3_SSL_BUNDLE=storage`.
Каждая одновременная загрузка держит файл в памяти, до 10 МБ: кучу считают от ожидаемого числа одновременных
загрузок справок. Допустимые типы файлов справки — `image/jpeg`, `image/png` и `application/pdf`, список с расширениями объектов — в `application.yml`
(`projectx.attachments.content-types`).

Брокеры настраиваются одинаково, у каждого свой префикс: `RABBITMQ_INTERNAL_*` — межсервисный брокер контура,
`RABBITMQ_ONEC_*` — брокер 1С:УСК.

| Переменная (`*` = `INTERNAL` или `ONEC`) | Умолчание | Что задаёт |
|---|---|---|
| `RABBITMQ_*_HOST` | `localhost` | хост брокера |
| `RABBITMQ_*_PORT` | `5674` у межсервисного, `5675` у 1С:УСК (локальные брокеры из `docker-compose.yml`) | порт брокера; с TLS в контуре — `5671` |
| `RABBITMQ_*_VHOST` | `/` | виртуальный хост |
| `RABBITMQ_*_USERNAME` | `contract_service` | логин брокера |
| `RABBITMQ_*_PASSWORD` | — | пароль брокера |
| `RABBITMQ_*_SSL_ENABLED` | `false` | TLS к брокеру |
| `RABBITMQ_*_SSL_VALIDATE_CERTIFICATE` | `true` | проверка сертификата брокера (центр сертификации — в `certs/`) |
| `RABBITMQ_*_SSL_VERIFY_HOSTNAME` | `true` | проверка имени хоста в сертификате; действует только вместе с проверкой сертификата |
| `RABBITMQ_*_LISTENER_AUTO_STARTUP` | `true` | запускать ли слушателей очередей этого брокера на старте |

Имена очередей заданы в `application.yml` значениями из документа «Точки интеграций сервис Договоров и Заявок» и
переопределяются переменными `INTERNAL_QUEUE_TASK_CHANGES`, `INTERNAL_QUEUE_STATUS_CHANGES`,
`ONEC_QUEUE_KM_CONTRACT_SUBMISSIONS`, `ONEC_QUEUE_KM_CONTRACT_REGISTRATIONS`, `ONEC_QUEUE_LM_POLICY_REQUESTS`,
`ONEC_QUEUE_LM_POLICY_ISSUES`; на новом контуре их сверяют со списком очередей брокера. Два свойства с одним именем
очереди или пустое имя не дают сервису запуститься.

Таймауты сеанса пишутся с единицами PostgreSQL (`ms`, `s`, `min`): число без единицы PostgreSQL читает как
миллисекунды. Почему настройки такие — в [design.md](design.md), переменные с описанием — в шаблоне `.env.example`.

## Сборка и локальный запуск

Нужны JDK 21 и Docker: тесты поднимают PostgreSQL, RabbitMQ и хранилище S3 (MinIO) в контейнерах. Образ MinIO задаёт
`TEST_MINIO_IMAGE` (по умолчанию `chainguard/minio`, закреплённый по хешу); в контуре — образ MinIO из корпоративного
реестра, префикс реестра — как у остальных образов, `TESTCONTAINERS_HUB_IMAGE_NAME_PREFIX`. Без Docker тесты берут базу из
`TEST_POSTGRES_URL` и брокер из `TEST_RABBITMQ_URL` (`amqp://логин:пароль@хост:порт/vhost`, отдельный тестовый брокер,
не рабочий); без Docker и без адресов они падают, а не пропускаются.

```shell
./gradlew build          # сборка и тесты
./gradlew bootJar        # только jar: build/libs/contract-service-<версия>.jar
```

Вне рабочего контура сборке нужны публичные репозитории: `./gradlew -PpublicRepositories=true …` или переменная
`ORG_GRADLE_PROJECT_publicRepositories=true`. По умолчанию сборка берёт зависимости только из Nexus контура.

Концы строк в git задаёт `.gitattributes` модуля: LF у текстовых файлов, CRLF у `*.bat`. Без него git на Windows с
`core.autocrlf=true` кладёт в рабочую копию CRLF, и `gradlew` и `certs/import-ca.sh` падают в Linux-контейнере на «\r».
Кодировку, концы строк и отступы для редактора задаёт `.editorconfig` модуля, правила кода —
[code-style.md](code-style.md).

Локально база и оба брокера поднимаются из `docker-compose.yml`, пароли — локального контура:

```shell
docker compose up -d
DB_PASSWORD=contract_service RABBITMQ_INTERNAL_PASSWORD=contract_service RABBITMQ_ONEC_PASSWORD=contract_service \
  REFERENCE_URL=http://localhost:8080/internal/v1 S3_ENDPOINT=http://localhost:9000 S3_BUCKET=contracts \
  S3_ACCESS_KEY=local S3_SECRET_KEY=local-secret LOGGING_STRUCTURED_FORMAT_CONSOLE= ./gradlew bootRun
curl http://localhost:8081/actuator/health
```

Пустая `LOGGING_STRUCTURED_FORMAT_CONSOLE` переключает журнал с JSON на обычный текст. Очередей соседей в локальных
брокерах нет: их заводят вручную в панелях брокеров, а пока их нет, слушателей выключают
(`RABBITMQ_INTERNAL_LISTENER_AUTO_STARTUP=false`, `RABBITMQ_ONEC_LISTENER_AUTO_STARTUP=false`; профиль `app` делает это
сам). Справочники сервис ждёт от локального контура сервиса справочных данных (`docker compose --profile stand up -d` в
его каталоге, адрес `REFERENCE_URL=http://localhost:8080/internal/v1`); без него старт проходит, а чтение справочника
заканчивается ошибкой «справочник недоступен». Сервис в контейнере — `docker compose --profile app up -d
--build`: API на `8082`, актуатор на `8083`, а до справочников контейнер ходит по сети локального контура
data-reference (`data-reference_default`, адрес `http://data-reference-stand:8080/internal/v1`), поэтому стенд
data-reference должен быть поднят раньше: на машине он слушает только 127.0.0.1, и из контейнера туда не попасть.
Другой адрес задаётся `REFERENCE_URL` в `.env`. Хранилища S3 в локальном контуре нет: настройки S3 обязательны для
старта, но к хранилищу сервис обращается только при загрузке справки, и без S3 загрузка отвечает 503
`STORAGE_UNAVAILABLE`. Профиль `app` задаёт S3 локальные значения (адрес `http://s3.local:9000`, бакет `contracts`);
своё хранилище подключается переменными `S3_*` в `.env`. Пароли локального контура известны всем,
поэтому порты по умолчанию открыты только на 127.0.0.1; открыть API и базу для других машин можно переменными
`SERVICE_BIND_ADDRESS` и `POSTGRES_BIND_ADDRESS` в `.env` (шаблон `.env.example`), брокеры и актуатор остаются
на 127.0.0.1.

### Образ

Образ собирается из `Dockerfile` модуля (нужен BuildKit). Откуда взять jar, задаёт аргумент `JAR_SOURCE`:

- `build` — собрать внутри образа, так собирает CI. Нужна сеть до Nexus и дистрибутива Gradle. Вне контура задайте
  `PUBLIC_REPOSITORIES=true`, чтобы зависимости брались из Maven Central.
- `host` — взять собранный на машине, когда у сборки нет сети:
  `./gradlew bootJar && docker build --build-arg JAR_SOURCE=host .`

В сети без выхода наружу базовые образы и Gradle берутся из зеркала Nexus (аргументы `JDK_IMAGE`, `JRE_IMAGE`,
`GRADLE_DISTRIBUTION_URL`). Сертификаты корпоративного центра сертификации кладутся в `certs/`: без них JVM не
доверяет Nexus при сборке. В слои образа они не попадают. Тесты при сборке образа не запускаются: им нужен Docker,
их прогоняет CI до сборки образа.

## Метрики и оповещения

Метрики отдаёт `/actuator/prometheus` на порту актуатора. Свои счётчики сервиса:

| Метрика | Что считает |
|---|---|
| `contracts_inbox_failed_total{event_type}` | входящее сообщение отклонено окончательно: нарушение контракта, постоянный отказ базы, внутренняя ошибка или исчерпана лестница повторов |
| `contracts_inbox_lost_total{reason}` | входящее сообщение потеряно без записи в журнал; `reason` — `unusable_envelope`, `unreadable_body`, `unstorable_text` |
| `contracts_outbox_failed_total{event_type}` | исходящее сообщение не доставлено: возврат `NO_ROUTE`, для типа события нет очереди или исчерпана лестница повторов |
| `contracts_usk_preparation_failed_total{event_type}` | передачу договора КМ (`KmContractSubmitted`) или запрос полиса ЛМ (`LmPolicyRequested`) в 1С:УСК нельзя подготовить из-за внутренней ошибки сервиса: запись переведена в ERROR |
| `contracts_cancel_reason_unknown_total{event_type}` | прекращение работы пришло с кодом причины вне словаря и применено с причиной OTHER; `event_type` — всегда `ContractTaskCancelled` |
| `contracts_lm_policies_awaiting_oldest_seconds` | сколько секунд ждёт ответа 1С:УСК самый старый переданный полис ЛМ; `0` — ждущих нет. Снимок, его пересчитывает проход раз в `LM_POLICY_REQUEST_AWAITING_INTERVAL` |
| `contracts_lm_policies_awaiting_overdue` | сколько полисов ЛМ ждут ответа 1С:УСК дольше `LM_POLICY_REQUEST_AWAITING_THRESHOLD`; снимок того же прохода |
| `contracts_km_contracts_awaiting_oldest_seconds` | сколько секунд ждёт ответа 1С:УСК самый старый переданный договор КМ; `0` — ждущих нет. Снимок, его пересчитывает проход раз в `KM_CONTRACT_SUBMISSION_AWAITING_INTERVAL` |
| `contracts_km_contracts_awaiting_overdue` | сколько договоров КМ ждут ответа 1С:УСК дольше `KM_CONTRACT_SUBMISSION_AWAITING_THRESHOLD`; снимок того же прохода |
| `contracts_reference_unavailable_total{kind}` | справочный сервис не ответил после всех повторов; `kind` — `program`, `insurance_contract`, `policy` |
| `contracts_attachments_stored_total` | справка 070/у впервые записана в реестр документов (повтор того же вложения не считается) |
| `contracts_attachments_rejected_total{reason}` | файл справки отклонён; `reason` — `content_type` (тип не JPEG, не PNG и не PDF), `size` (пустой, больше предела справки или больше предела контейнера) |
| `contracts_storage_unavailable_total` | обращение к хранилищу S3 за справкой не получило успешного ответа: загрузка справки получила 503 или проход подготовки передач не смог проверить файлы справок оплаченного договора КМ и отложил передачу до следующего прохода |

Пул соединений базы — метрики `hikaricp_*` с меткой `pool="application"`. Подключения брокеров — метрики `rabbitmq_*`
с меткой `name="internalBroker"` или `name="onecBroker"`. Состояние базы и брокеров — компоненты `/actuator/health`,
брокеры — `internalBroker` и `onecBroker`.

**Правила оповещения.** По счётчикам строятся правила дежурному; что делать, зависит от `event_type`.

- `contracts_inbox_failed_total` — входящее сообщение отклонено окончательно, разбор — по записи журнала входящих
  (`error_message`). Причина «повторы исчерпаны на попытке …» значит, что временный отказ держался дольше лестницы
  `INBOX_RETRY_BACKOFF`: «временный отказ базы данных, SQLSTATE …» — база; «временный отказ доступа к данным:
  java.sql.SQLTransientConnectionException» — пул не дождался свободного соединения за `DB_CONNECTION_TIMEOUT_MS`:
  без SQLSTATE в записи ERROR все соединения заняты или база не отвечает, с SQLSTATE (например, 28P01) база отказывает
  в новых соединениях (учётные данные, предел соединений); «…: org.springframework.dao.QueryTimeoutException» — запрос
  дольше `DB_STATEMENT_TIMEOUT`; «…: org.springframework.dao.CannotAcquireLockException» — строка занята дольше
  `DB_LOCK_TIMEOUT`; текст временной ошибки сервиса — справочник. После устранения причины сообщение возвращают в
  разбор. `ContractTaskUpserted` — задача сервиса Заявок: ответа по ней не будет, следующая задача по заявке
  разбирается как обычно. `KmContractRegistered` — результат регистрации договора КМ: договор остаётся «передан в
  1С:УСК», причина — в `error_message` (полис не получен справочником, справочник недоступен или нарушение контракта
  1С:УСК); после устранения причины сообщение возвращают в разбор. `ContractTaskCancelled` — **срочно**: прекращение не применено (нет обязательного поля,
  постоянный отказ базы), договоры и полисы заявки не прекращены, и запросы полисов ЛМ с персональными данными
  продолжат уходить в 1С:УСК; устранить причину и вернуть сообщение в разбор («Ручные операции»). Незнакомый код
  причины прекращение не отклоняет — его считает `contracts_cancel_reason_unknown_total`. `LmPolicyIssued` — результат
  1С:УСК: полис остаётся «передан в 1С:УСК» и сам не сдвинется; причина — в `error_message` (полис не получен
  справочником или справочник недоступен). Когда причина устранена, сообщение возвращают в разбор («Ручные
  операции»).
- `contracts_inbox_lost_total` — сообщение потеряно без записи в журнал, разбор — по записи ERROR журнала сервиса и у
  отправителя по времени.
- `contracts_outbox_failed_total` — исходящее сообщение не доставлено, разбор — по записи журнала исходящих; при
  возврате `NO_ROUTE` проверить очередь у брокера получателя. `ContractStatusChanged` — после этого сервис Заявок
  получит следующий снимок по заявке с полным состоянием. `LmPolicyRequested` — запрос полиса ЛМ в 1С:УСК не ушёл: полис
  переходит в ERROR с кодом `LM_POLICY_REQUEST_UNDELIVERED`, сервис Заявок получает ошибку по участнику, а новый
  запрос уйдёт по новой записи, когда сервис Заявок пришлёт задачу с большей версией. Сначала восстанавливают очередь
  1С:УСК: иначе и новый запрос не дойдёт. `KmContractSubmitted` — передача оплаченного договора КМ в 1С:УСК не ушла
  (нет очереди, исчерпана лестница или стёрто тело — причина в журнале исходящих):
  договор переходит в ERROR с кодом `KM_CONTRACT_SUBMISSION_UNDELIVERED`, сервис Заявок получает ошибку по участнику.
  Новой записи задачей не заводится — договор оплачен; после устранения причины дежурный возвращает договор в
  оплаченные («Ручные операции»), и ближайший проход передаёт его заново.
- `contracts_usk_preparation_failed_total` — **оповещение** на любой рост: это дефект сервиса или его данных, а не отказ
  соседа. Повтор не поможет, поэтому запись сразу переходит в ERROR, сервис Заявок получает ошибку по участнику, а проход
  передаёт остальные записи. Разбор — по записи ERROR журнала сервиса (тип отказа и SQLSTATE, без персональных данных).
  `KmContractSubmitted` — код `KM_CONTRACT_SUBMISSION_PREPARATION_FAILED`, после устранения причины дежурный возвращает
  договор в оплаченные («Ручные операции»). `LmPolicyRequested` — код `LM_POLICY_REQUEST_PREPARATION_FAILED`, новый запрос
  уйдёт по новой записи со следующей задачей сервиса Заявок. Рост сразу по многим записям говорит о системной причине
  (например, тип содержимого убран из `ATTACHMENT_CONTENT_TYPES`): её устраняют до возврата договоров.
- `contracts_cancel_reason_unknown_total` — сервис Заявок прислал прекращение с кодом причины вне словаря; работа по
  заявке прекращена с причиной OTHER, код — в комментарии прекращения (`cancel_comment`) и в записи WARN журнала
  сервиса с идентификатором заявки. Значение не по формату кода (латиница в верхнем регистре, цифры и подчёркивание, до
  50 знаков) не записывается нигде — вместо него пометка «не по формату кода». Срочности нет: словарь сверяют с
  сервисом Заявок.
- `contracts_lm_policies_awaiting_overdue` — **оповещение**, когда значение больше нуля дольше одного пересчёта, например
  `contracts_lm_policies_awaiting_overdue > 0` с `for: 5m`. 1С:УСК не ответила по полису ЛМ дольше порога. Сервис
  повторный запрос сам не отправляет: в 1С:УСК появился бы второй полис. Найти полисы — запрос «Полисы ЛМ, ждущие
  ответа 1С:УСК» ниже, по `id` полиса — запрос в журнале исходящих (`aggregate_id`) и его `message_id`; дальше — с 1С:УСК
  по `message_id` запроса. `contracts_lm_policies_awaiting_oldest_seconds` показывает, насколько всё плохо, и
  оповещения не требует. Если проход сводки не выполнился (база недоступна), метрики держат последнее значение, а в
  журнале — WARN «проход пересчёта сводки полисов ЛМ, ждущих ответа 1С:УСК не выполнен»; недоступность базы видна по
  health и метрикам `hikaricp_*`, поэтому в это время на ноль в сводке не полагаются.
- `contracts_km_contracts_awaiting_overdue` — **оповещение** по тому же правилу, что у полисов ЛМ
  (`contracts_km_contracts_awaiting_overdue > 0` с `for: 5m`): 1С:УСК не ответила по оплаченному договору КМ дольше
  порога. Повторную передачу сервис не отправляет — в 1С:УСК появился бы второй договор. Найти договоры — запрос
  «Договоры КМ, ждущие ответа 1С:УСК» ниже; дальше — с 1С:УСК по `message_id` передачи.
- `contracts_reference_unavailable_total{kind}` — справочный сервис не ответил после всех повторов. Единичный рост —
  проход повторит чтение сам; устойчивый рост (`increase()` за 15 минут больше числа проходов за то же время) значит,
  что запросы в 1С:УСК не уходят, а результаты 1С:УСК откладываются по лестнице `INBOX_RETRY_BACKOFF` и после неё
  отклоняются окончательно, — разбор начинается с health и журнала сервиса справочных данных.
- `contracts_storage_unavailable_total` — загрузка справки получила 503 `STORAGE_UNAVAILABLE` (сервис Заявок повторит
  её сам) или проход подготовки передач не смог проверить файлы справок оплаченного договора КМ: договор остаётся
  оплаченным, следующий проход проверяет снова. Единичный рост — сбой сети; устойчивый рост (больше нуля за 15 минут
  подряд) значит, что справки не принимаются и передачи договоров КМ стоят. Разбор — по записям WARN «хранилище справок
  …» журнала сервиса: код ошибки S3 `NoSuchBucket` — бакета нет
  (его заводят заранее), `AccessDenied` или `InvalidAccessKeyId` — ключи или права, тип `java.net.ConnectException`,
  `java.net.SocketTimeoutException` или `java.io.InterruptedIOException` (истёк `S3_CALL_TIMEOUT`) — сеть и адрес
  `S3_ENDPOINT`; при ошибке TLS — сертификат УЦ в наборе `S3_SSL_BUNDLE`.
  Записи по вызову находятся в журнале по `requestId` из ответа (`error.request_id`).

## Ручные операции

### Возврат отклонённого входящего сообщения в разбор

Сообщение журнала входящих, отклонённое окончательно (`FAILED`), сервис сам больше не разбирает. Когда причина
устранена — полис дошёл до справочного сервиса, база или справочник снова доступны, — дежурный возвращает сообщение
одним запросом по его `message_id`:

```sql
update inbox_messages
   set status = 'NEW', attempts = 0, error_message = null, next_attempt_at = null
 where message_id = '<message-id>'
   and status = 'FAILED'
   and payload is not null;
```

Ближайший проход разбора берёт его как только что принятое: с первой попытки и с полной лестницей
`INBOX_RETRY_BACKOFF`. Запрос возвращает только отклонённые сообщения с телом: обработанное, пропущенное или ждущее
разбора сообщение он не трогает, а сообщение со стёртым по сроку телом разобрать уже нечем — `update` сообщит
`0` строк. Задачу сервиса Заявок возвращать имеет смысл, только если по заявке не обработана задача с большей версией:
иначе разбор пропустит её как устаревшую. Возврат счётчик `contracts_inbox_failed_total` не уменьшает; новый
окончательный отказ после возврата посчитается снова. Тело стирается по сроку от приёма при любом статусе: сообщение,
возвращённое незадолго до конца `INBOX_PAYLOAD_RETENTION`, может потерять тело посреди лестницы повторов и будет
отклонено с причиной «тело сообщения стёрто по сроку хранения».

Найти отклонённые сообщения (без тел):

```sql
select message_id, correlation_id, event_type, attempts, error_message, received_at
  from inbox_messages
 where status = 'FAILED'
 order by received_at;
```

### Полисы ЛМ, ждущие ответа 1С:УСК

Ожидание считается от перехода полиса в «передан в 1С:УСК» (`updated_at` полиса в `SUBMITTED`):

```sql
select p.id, p.individual_request_id, p.updated_at as submitted_at, o.message_id as request_message_id, o.status
  from lm_policies p
  left join outbox_messages o on o.aggregate_type = 'LM_POLICY' and o.aggregate_id = p.id
 where p.status = 'SUBMITTED'
 order by p.updated_at;
```

### Договоры КМ, ждущие ответа 1С:УСК

Ожидание считается от перехода договора в «передан в 1С:УСК» (`updated_at` договора в `SUBMITTED`):

```sql
select c.id, c.number, c.individual_request_id, c.updated_at as submitted_at, o.message_id as submission_message_id,
       o.status
  from contracts c
  left join outbox_messages o on o.aggregate_type = 'CONTRACT' and o.aggregate_id = c.id
 where c.status = 'SUBMITTED'
 order by c.updated_at;
```

### Возврат договора КМ, не переданного в 1С:УСК, в оплаченные

Передача оплаченного договора КМ, отклонённая журналом исходящих окончательно (нет очереди у 1С:УСК, исчерпана лестница
повторов, стёрто тело), переводит договор в ERROR с кодом
`KM_CONTRACT_SUBMISSION_UNDELIVERED`. Новой записи по такому договору задача сервиса Заявок не заводит: деньги по нему
уже заплачены. Это правило действует для любого оплаченного договора в ERROR, какой бы ни был код ошибки, — в том
числе для `KM_CONTRACT_SUBMISSION_PREPARATION_FAILED` (раздел ниже). Изменения из следующих задач к нему не применяются — в журнале сервиса WARN «договор КМ оплачен,
изменения из задачи версии N не применены», договор остаётся в ошибке с прежним кодом. Если задача исключила участника
из поездки или у него исчезла доплата, договор прекращается (CANCELLED, причина OTHER), и вернуть его этой процедурой
нельзя. Когда причина устранена — очередь у брокера 1С:УСК восстановлена, объект справки на месте, — дежурный
возвращает договор в оплаченные одним запросом по его идентификатору:

```sql
update contracts
   set status = 'PAID', error_code = null, error_message = null, entity_version = entity_version + 1,
       updated_at = now()
 where id = '<contract-id>'
   and status = 'ERROR'
   and error_code in ('KM_CONTRACT_SUBMISSION_UNDELIVERED', 'KM_CONTRACT_SUBMISSION_PREPARATION_FAILED');
```

Ближайший проход подготовки передач берёт договор как оплаченный и пишет новую передачу с новым `message_id` и
новой версией договора; отклонённая запись журнала исходящих остаётся в истории. Запрос трогает только договор в ERROR
с одним из этих двух кодов: договор, который 1С:УСК отклонила ответом (код ошибки 1С:УСК), и договор в любом другом
состоянии он не меняет — `update` сообщит `0` строк. Сервис Заявок о возврате не узнаёт (оплаченный и переданный договор наружу не
публикуются) и получит следующий снимок по заявке, когда 1С:УСК ответит. Найти такие договоры:

```sql
select c.id, c.number, c.individual_request_id, c.updated_at, o.message_id, o.error_message
  from contracts c
  left join outbox_messages o on o.aggregate_type = 'CONTRACT' and o.aggregate_id = c.id and o.status = 'FAILED'
 where c.status = 'ERROR' and c.error_code = 'KM_CONTRACT_SUBMISSION_UNDELIVERED'
 order by c.updated_at;
```

### Договоры КМ и полисы ЛМ, передачу которых не удалось подготовить

Запрос из раздела «Возврат договора КМ, не переданного в 1С:УСК, в оплаченные» возвращает в оплаченные и договор КМ,
передачу которого сервис не смог подготовить из-за внутренней ошибки: код `KM_CONTRACT_SUBMISSION_PREPARATION_FAILED`,
в журнале сервиса — запись уровня ERROR «передача договора КМ не
подготовлена из-за внутренней ошибки, договор переведён в ERROR» с идентификаторами договора, участника и заявки, типом
отказа и SQLSTATE, а счётчик `contracts_usk_preparation_failed_total{event_type="KmContractSubmitted"}` растёт. Записи в
журнале исходящих у такого договора нет. Тип отказа подсказывает причину: данные договора неполны (нет записи акцепта,
снимка стороны, момента оплаты) или тип содержимого справки убран из `ATTACHMENT_CONTENT_TYPES`. Сначала устраняют
причину — иначе ближайший проход снова переведёт договор в ERROR, — затем выполняют запрос возврата. Повторная задача сервиса Заявок новой записи по оплаченному договору в ERROR не
заводит, поэтому второго договора участника рядом с ним нет. Исключение — договоры, по которым новая запись была
открыта прежней версией сервиса: тогда запрос упадёт на уникальном индексе `uq_contracts_active_insured_participant`, а
не вернёт `0` строк, и договор не возвращают, а разбирают вместе с владельцем данных. Найти такие договоры:

```sql
select c.id, c.number, c.individual_request_id, c.insured_participant_id, c.updated_at
  from contracts c
 where c.status = 'ERROR' and c.error_code = 'KM_CONTRACT_SUBMISSION_PREPARATION_FAILED'
 order by c.updated_at;
```

Полис ЛМ с той же ошибкой (`LM_POLICY_REQUEST_PREPARATION_FAILED`, счётчик с `event_type="LmPolicyRequested"`) дежурный не
возвращает: после устранения причины новый запрос уходит по новой записи, которую создаёт следующая задача сервиса Заявок
с большей версией, как после ошибки справочника.

### Договор КМ, файла справки которого нет в хранилище

Перед записью передачи сервис проверяет, что файл каждой справки застрахованного есть в хранилище. Файла нет — договор
переходит в ERROR с кодом `KM_CONTRACT_SUBMISSION_PREPARATION_FAILED`, сервис Заявок получает ошибку по участнику, растёт
`contracts_usk_preparation_failed_total{event_type="KmContractSubmitted"}`, а в журнале сервиса — запись уровня ERROR
«передача договора КМ не подготовлена: файла справки нет в хранилище, договор переведён в ERROR» с идентификаторами
договора, участника и заявки и типом отказа `ru.projectx.contracts.exception.CertificateMissingException`. Ключи объектов
справок договора:

```sql
select d.id, d.attachment_id, d.file_key, d.created_at
  from contracts c
  join contract_documents d on d.individual_request_id = c.individual_request_id
                           and d.participant_id = c.insured_participant_id
 where c.id = '<contract-id>' and d.doc_type = 'MEDICAL_CERTIFICATE'
 order by d.created_at, d.id;
```

Объект ищут в бакете `S3_BUCKET` по ключу `file_key`. Сначала его восстанавливают по тому же ключу (из резервной копии
хранилища или загрузкой того же файла администратором хранилища) — иначе ближайший проход снова переведёт договор в
ERROR, — затем возвращают договор в оплаченные запросом из раздела «Возврат договора КМ, не переданного в 1С:УСК, в
оплаченные». Если пропал не один объект, а весь бакет (клиент хранилища отвечает «объекта нет» и тогда), его заводят
заново и восстанавливают объекты до возврата договоров.

### Предупреждение о таймаутах базы при старте

После старта сервис читает у сеанса пула `lock_timeout`, `statement_timeout` и `idle_in_transaction_session_timeout`
и сверяет их с `DB_LOCK_TIMEOUT`, `DB_STATEMENT_TIMEOUT` и `DB_IDLE_IN_TRANSACTION_TIMEOUT`. Расхождение даёт WARN
«таймаут сеанса PostgreSQL расходится с настройкой» с параметром, ожидаемым и фактическим значением; старт при этом не
останавливается. Обычные причины: значение переменной без единицы PostgreSQL (читается как миллисекунды) или пулер
соединений между сервисом и базой, который выбросил стартовый параметр `options`. Проверить вручную — `show
lock_timeout;` под пользователем сервиса через тот же адрес, что в `DB_URL`. Без таймаутов чужая блокировка или зависший запрос держат соединение пула
без срока, и сервис перестаёт отвечать. WARN «настройка … не разобрана» значит, что значение переменной задано в
форме, которую проверка не понимает (например, дробное число): параметр не проверен, его сверяют вручную. WARN «сеанс
пула не прочитан» — база была недоступна на старте; проверка не повторяется, сверить вручную.

## Документация

- [CHANGELOG.md](../CHANGELOG.md) — версии, что нужно для установки каждой.
- `src/main/resources/application.yml` — все настройки; почему они такие — [design.md](design.md).
- [code-style.md](code-style.md) — как пишем код: размеры, слои, исключения, транзакции, персональные данные, тесты.
- `.env.example` — шаблон переменных для `docker-compose.yml`.
- `src/test/resources/data-reference/examples/` — примеры ответов сервиса справочных данных, на которых проверяется
  клиент справочников; это копии файлов его стенда, и при изменении примеров у него копии обновляются вручную.
- `src/main/resources/db/changelog/` — миграции схемы: перечисления, договоры КМ, полисы ЛМ, стороны договора, журнал
  входящих, журнал исходящих, заявки на выпуск с составом участников, печатные формы, справки 070/у
  участников заявок, акцепты договоров КМ, момент оплаты договора КМ.
- «Точки интеграций сервис Договоров и Заявок», «Структура данных (Сервис договоров)», «Сервис Договоров. Синхронные
  эндпоинты» — контракты сервиса.
