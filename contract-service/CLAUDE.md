# CLAUDE.md

Инструкции для Claude Code по работе с сервисом Договоров. Файл живёт только во внешнем контуре (облако Claude Code и
GitHub) и в рабочий контур не переносится. По процессу, веткам, гейтам и источникам документации главный —
`gauntlet/CLAUDE.md`; этот файл главный по предметной области и правилам кода сервиса Договоров. План серии —
`docs/gauntlet-plan-contract-service.md`.

## О сервисе

`contract-service` — сервис Договоров контура РВЛ ОНЛАЙН, он же бэкенд личного кабинета застрахованного. Имя — как в
документах контура: `contract-service` (в ТЗ — `RVL-CONTRACTS`), пакет `ru.projectx.contracts`,
`spring.application.name=contract-service`, база и учётные данные `contract_service`.

Что он делает:

- по задаче сервиса Заявок разбирает состав поездки и решает, что выпускается по каждому участнику: застрахованное лицо
  без доплаты — ничего; застрахованное лицо с доплатой — договор КМ; родственник без доплаты — полис ЛМ; родственник с
  доплатой — договор КМ. Правило живёт здесь, в контракт оно не выносится;
- ведёт договоры КМ: номер, снимок сторон, акцепт оферты по версии договора, оплата через Ordering Service, передача
  оплаченного договора в 1С:УСК и получение полиса и постоянных ссылок на документы (печатные формы делает 1С:УСК);
- запрашивает у 1С:УСК полисы ЛМ родственникам без доплаты;
- принимает от сервиса Заявок справки 070/у участников и хранит их в S3 контура (реестр — `contract_documents`), чтобы
  передать в 1С:УСК вместе с оплаченным договором;
- отдаёт сервису Заявок состояние выпуска: асинхронно (ДГ-03) и синхронно (состояние пакета СЭ-01, акцепт СЭ-03);
- читает справочники у `data-reference` по REST: программы, полисы, договоры страхования.

Собственного пользовательского интерфейса у сервиса нет. Фронтенд и BFF к нему не обращаются: всё, что застрахованное
лицо видит по договору и оплате, проходит через сервис Заявок.

Внутри контура сервис говорит с четырьмя собеседниками:

- **Сервис Заявок** (он же сервис HR): команды и ответы по межсервисному брокеру RabbitMQ (ДГ-01…ДГ-03), синхронные
  вызовы к нам (загрузка справок 070/у, СЭ-01…СЭ-03). Другой разработчик, свой репозиторий.
- **1С:УСК** — учётная система, брокер 1С: регистрация договоров КМ и выпуск полисов (ДГ-04…ДГ-07). В сторону 1С уходят
  персональные данные и печатные формы.
- **Дата-референс** (`data-reference`, этот же репозиторий): REST-чтение справочников, только чтение.
- **Ordering Service** — внутренний сервис оплаты: REST с токеном Keycloak к нему, события оплаты из брокера
  «Оплата» / маркетинга от него. Подключается последним (этап 7 плана).

Брокеров RabbitMQ у сервиса три: межсервисный, 1С:УСК и «Оплата». Это разные подключения со своими адресами и
учётными данными.

Терминология контура (КМ, ЛМ, ГП, 070/у, ЛПУ, ЦКЗ, СОБ) — раздел «Терминология» в `data-reference/CLAUDE.md`. Здесь
важно: **КМ** — договор на сумму доплаты застрахованного и выпускаемый по нему полис; **ЛМ** — полис родственнику без
доплаты по корпоративному договору страхователя, его выпускает 1С:УСК.

## Контракт с сервисом Заявок

Описан в «Точках интеграций» и «Синхронных эндпоинтах»; здесь — что из него следует для кода.

**Асинхронный обмен** — межсервисный брокер, очереди durable, сообщения persistent:

| Точка | Направление | Событие | Очередь |
|---|---|---|---|
| ДГ-01 | Заявки → Договоры | `ContractTaskUpserted` — задача на выпуск: полный состав участников, суммы, даты поездки, персональные данные | `rvl_requests_to_rvl_contracts_task-changes` |
| ДГ-02 | Заявки → Договоры | `ContractTaskCancelled` — прекращение работы по заявке | та же очередь |
| ДГ-03 | Договоры → Заявки | `ContractStatusChanged` — состояние выпуска по всем участникам заявки, обезличено | `rvl_contracts_to_rvl_requests_status-changes` |

- Конверт `meta` во всех сообщениях: `message_id` (ключ идемпотентности), `correlation_id` (GUID индивидуальной заявки),
  `topic`, `event_type`, `schema_version`, `created_at`, `entity_version`, `source` (`RVL-REQUESTS`, `RVL-CONTRACTS`,
  `1C-USK`).
- **Outbox при публикации, Inbox при потреблении.** Входящее сообщение сначала сохраняется в `inbox_messages` в одной
  транзакции с отметкой приёма, подтверждается брокеру только после фиксации и обрабатывается отдельным процессом:
  первая попытка и три повтора с паузой 1 / 5 / 15 минут (всего четыре, паузы — настройка `INBOX_RETRY_BACKOFF`),
  после исчерпания — FAILED и оповещение, вернуть в разбор можно процедурой дежурного (`docs/operations.md`). Дубль по
  `message_id` отсекается уникальным индексом. Сообщение с
  `entity_version` не выше обработанной по той же заявке (`correlation_id`) отбрасывается с причиной; это правило задач
  сервиса Заявок, результаты 1С:УСК по версии не упорядочиваются (`LmPolicyIssuedHandler` — `InboxOrdering.NONE`).
  Бизнес-ошибка — не сбой обработки: сообщение помечается обработанным, результат уходит ответным сообщением с
  `error_code` и `error_message`. Исходящее сообщение пишется в `outbox_messages` в одной транзакции с изменением данных
  и публикуется отдельным процессом с подтверждением брокера; вложения хранятся отдельно, тело собирается на публикации.
- ДГ-01 — один контракт на создание и изменение: участник, которого нет в `participants`, исключён из поездки, работа
  по нему прекращается (кроме выпущенного документа — см. «Статусы и события»). Единственное сообщение между сервисами с
  персональными данными.
- ДГ-03 самодостаточно: всегда полное состояние по всем участникам. Внутренние статусы наружу не транслируются —
  только `km_contract_state` (NOT_REQUIRED / DRAFTED / ISSUED / CANCELLED), `payment_status` (NOT_REQUIRED / PENDING /
  PAID), документы и ошибки по участнику; статус заявки IN_PROGRESS / COMPLETED / ERROR / CANCELLED.
- Идентификаторы договора страхования, полиса страхователя и программы в ДГ-01 — идентификаторы `data-reference`
  (так объявляет «Структура данных»); `external_id` для 1С подтягиваются у Дата-референса при формировании ДГ-04 и
  ДГ-06 и в наших таблицах не дублируются.

**Синхронные вызовы** — только от сервиса Заявок, базовый путь `/internal/v1`, JSON в snake_case, на внешнем периметре не
публикуются; аутентификации между сервисами нет (решение владельца: защита — сетевая политика контура, коды 401/403
из ТЗ не реализуются):

| Вызов | Назначение |
|---|---|
| `POST /requests/{individual_request_id}/participants/{participant_id}/attachments` (СЭ-04) | загрузка справки 070/у (multipart: `attachment_id`, `file`); идемпотентна по `attachment_id`: повтор — 200 и прежняя запись, другое содержимое или другой участник — 409 `ATTACHMENT_CONFLICT`; контракт согласован с разработчиком Заявок |
| `GET /requests/{individual_request_id}/package` (СЭ-01) | состояние пакета по заявке: по участнику — вид документа, номер, состояние, премия, `contract_version`, акцепт, оплата, итоговые формы 1С, ошибка; справок нет |
| `POST /contracts/{contract_id}/acceptance` (СЭ-03) | акцепт оферты по `contract_version` (без `document_id`/`document_hash`); идемпотентен по `contract_id`: повтор с той же версией — 200 и прежняя запись; другая версия после акцепта — 409 `ALREADY_ACCEPTED`; договор занят дольше `DB_LOCK_TIMEOUT` — 503 `SERVICE_UNAVAILABLE` |

Выдача содержимого документа (СЭ-02) не реализуется: проектов печатных форм у Договоров нет, справки в личный кабинет не
отдаются.

Формат ошибки — `error.code`, `error.message`, `error.details[]`, `error.request_id`; `X-Request-Id` сквозняком и в
ответе, принимается в формате `[A-Za-z0-9._-]{1,64}`, иначе выдаётся новый UUID. Коды — сводный перечень в ТЗ СЭ:
`VALIDATION_ERROR` 400, `*_NOT_FOUND` 404, `ALREADY_ACCEPTED`, `DOCUMENT_VERSION_MISMATCH`, `INVALID_STATE`,
`ATTACHMENT_CONFLICT` 409, `INTERNAL_ERROR` 500, `STORAGE_UNAVAILABLE`, `SERVICE_UNAVAILABLE`, `ORDERING_UNAVAILABLE`
(этап оплаты) 503; `REFERENCE_UNAVAILABLE` из ТЗ не используется — синхронные вызовы справочники не читают. Текст ошибки — для журнала, не для показа пользователю. Время ответа СЭ-01 и
СЭ-03 — до 1 с на 95 % запросов без учёта Ordering.
Общая основа — аннотация `@InternalApi`, фильтр `RequestIdFilter`, `ErrorResponse` и советники ошибок; новый вызов не
заводит своего формата ошибки и своего обработчика непредвиденных отказов.

## Контракт с 1С:УСК

Две независимые пары очередей на брокере 1С:УСК; очереди заводит 1С, сервис их не объявляет:

| Точка | Направление | Событие | Очередь |
|---|---|---|---|
| ДГ-04 | Договоры → 1С | `KmContractSubmitted` — оплаченный договор КМ со справками 070/у застрахованного в base64 | `rvl_contracts_to_1c-usk_km-contract-changes` |
| ДГ-05 | 1С → Договоры | `KmContractRegistered` — идентификаторы, полис, постоянные ссылки либо ошибка | `1c-usk_to_rvl_contracts_km-contract-changes` |
| ДГ-06 | Договоры → 1С | `LmPolicyRequested` — выпуск полиса ЛМ родственнику без доплаты | `rvl_contracts_to_1c-usk_lm-policy-changes` |
| ДГ-07 | 1С → Договоры | `LmPolicyIssued` — полис ЛМ и ссылки либо ошибка | `1c-usk_to_rvl_contracts_lm-policy-changes` |

- Обмен в один раунд: номер договора КМ присвоен у нас до печатных форм, в 1С уходит готовый документ, обратно
  приходят идентификаторы и постоянные ссылки. Ссылки 1С бессрочные, перезапрашивать их не нужно.
- В ДГ-04 и ДГ-06 уходят персональные данные; в ДГ-05 и ДГ-07 их нет.
- Выпущенный полис 1С возвращает своим GUID; наш `issued_policy_id` — первичный ключ `data-reference`, его сервис находит
  поиском `…/policies/contract-view?external_id=`. Полис может ещё не дойти до Дата-референса: 404 `POLICY_NOT_FOUND`
  в этом случае — не отказ, а повод повторить чтение ограниченное число раз с паузой.
- Коды ошибок `error_code` в ДГ-05 и ДГ-07 согласуются с 1С отдельно (ОВД-09); до ответа сервис хранит код и текст как
  пришли и переводит договор в ERROR.
- Запрос полиса ЛМ и передача договора КМ — один механизм `service/usk`, вид записи описывает значение `IssuanceKind`
  (`LmPolicyKind.KIND`, `KmContractKind.KIND`): проход по расписанию читает справочники вне транзакции и под блокировкой
  строки пишет запрос в Outbox и переводит запись в SUBMITTED; окончательный отказ публикации — ERROR `*_UNDELIVERED`;
  ответ 1С разбирает `UskResultParser` по раскладке вида (`UskResultLayout`). Новый вид выпуска — новое значение
  `IssuanceKind` и свои классы вида, а не копия потока.
- Тело ДГ-04 в Outbox — без `content_base64`: справки — строки `message_attachments`, содержимое публикатор читает из S3
  при отправке (`OutboundBodies`). Предел размера сообщения `KM_CONTRACT_MAX_MESSAGE_SIZE` проверяется до записи в Outbox
  (`KmContractMessageLimit`). Правила ДГ-04 и ДГ-05 — журнал решений, Д-13.

## Чтение справочников data-reference

Три вызова, все `GET /internal/v1/…`, все синхронные, в момент формирования исходящего сообщения и поиска выпущенного
полиса, без кэширования на нашей стороне (так требует ТЗ: справочники ведутся в Дата-референсе и там же меняются):

| Вызов | Что берётся |
|---|---|
| `/programs/{id}` | программа: наименование, `external_id`, перечень услуг |
| `/policies/{id}/contract-view` и `/policies/contract-view?external_id=` | полис без персональных данных: `id`, `external_id`, `number`, `begin_date`, `end_date`, `is_archive` |
| `/insurance-contracts/{id}` и `/insurance-contracts?external_id=` | договор страхования: номер, `external_id`, страхователь |

Правила клиента:

- Таймаут чтения — не меньше 7 с: при отказе базы Дата-референс отвечает 503 `SERVICE_UNAVAILABLE` в худшем случае
  около 5 с (ожидание соединения 2 с плюс чтение до 3 с), и клиент не должен обрывать запрос раньше ответа. Таймаут
  соединения — порядка 2 с. Значения — настройки, не литералы.
- Повторы ограниченные, стандартным механизмом Spring Framework (`RetryTemplate` из `org.springframework.core.retry`;
  аннотация `@Retryable` из `org.springframework.resilience.annotation` включается `@EnableResilientMethods`): на 503 —
  всегда; на 404 `POLICY_NOT_FOUND` — только у поиска полиса по `external_id` после ДГ-05 и ДГ-07. Исчерпание повторов —
  доменное исключение «справочник недоступен»: задача выпуска остаётся в текущем состоянии и повторяется по общим
  правилам, выпуск не отменяется.
- 404 по `id` программы, договора или полиса и ответ `is_archive = true` — ошибка выпуска по участнику (ERROR с кодом в
  ДГ-03), не повтор: договор по архивной программе или полису выпускать нельзя.
- `X-Request-Id` передаётся сквозняком: текущий из MDC (`requestId`) или новый UUID. `requestId` задают фильтр входящих
  вызовов REST (`RequestIdFilter`), разбор входящего сообщения (`InboxLogContext` — `message_id` сообщения) и подготовка
  запроса в 1С:УСК (`UskRequests` — идентификатор полиса ЛМ или договора КМ); остальные проходы его не задают — там
  запрос к справочнику получает новый UUID.
- `GET /policies/{id}` с персональными данными сервис Договоров не читает: снимок сторон он получает из ДГ-01.
- Клиент — `RestClient` из spring-web, собранный вручную (`RestClient.builder()` с `JdkClientHttpRequestFactory` и своими
  настройками таймаутов): автонастроенный бин `RestClient.Builder` Spring Boot живёт в отдельном модуле, которого нет
  в classpath через `spring-boot-starter-web`, а тянуть новый стартер ради одного бина не нужно (решение владельца).

Новый эндпоинт, поле или другой таймаут у Дата-референса — запрос владельцу, его ставит координатор data-reference.
Код `data-reference` из задач Договоров не меняется.

## Статусы и события

Договор КМ: NEW → DRAFT_READY → ACCEPTED → INVOICE_ISSUED → PAID → SUBMITTED → ISSUED; из любого незавершённого —
CANCELLED (причина REQUEST_CANCELLED / INSURED_REFUSED / EXPIRED / OTHER); ERROR — ошибка в данных участника, отказ
справочника, недоставка или ошибка регистрации в 1С. Полис ЛМ:
NEW → SUBMITTED → ISSUED, ERROR, CANCELLED. ДГ-03 публикуется на DRAFT_READY, INVOICE_ISSUED, ERROR, CANCELLED и когда
по всем участникам заявки работа завершена; ACCEPTED, PAID и SUBMITTED наружу не публикуются. Перечисления — нативные
типы PostgreSQL (`CREATE TYPE … AS ENUM`), как требует «Структура данных».

Оплаченный договор (PAID, момент оплаты — `contracts.paid_at`) новой записью не перевыпускается: деньги уже заплачены.
Договор в ERROR из-за недоставленного ДГ-04 возвращает в PAID дежурный (`docs/operations.md`, «Ручные операции»), и он
уходит в 1С заново. До этапа оплаты в PAID договор ставит только тестовая подготовка (`ContractPayments.markPaid`);
продовый путь — подтверждение оплаты от Ordering.

Акцепт оферты хранится неизменяемой записью (`contract_acceptances`, одна на договор) с версией данных договора, которую
видел застрахованный: печатных форм у Договоров нет, акцептуются данные договора. Акцепт выполняет застрахованный за
всех участников. После акцепта снимок сторон, премия и даты договора вслед за сервисом Заявок не обновляются: повторная
задача с изменениями по такому договору — WARN в журнале сервиса, договор не меняется, ответа сервису Заявок нет; смена
вида документа или исключение участника — прекращение, как обычно. Пока договор ещё проект (NEW, DRAFT_READY), повторная
задача с большей версией обновляет премию, даты и снимок сторон, и версия договора растёт (решения владельца 2026-10-12,
К3, и 2026-10-22, К6b). ДГ-03 по акцептованному договору не меняется — ACCEPTED не публикуется, личный кабинет показывает
состояние пакета.

Выпущенная запись (полис ЛМ или договор КМ в ISSUED) уже существует в 1С:УСК и не перевыпускается и не меняется: разбор
задачи сверяет задачу со всеми записями заявки, кроме ERROR и CANCELLED, по участнику — одна запись, выпущенная
предпочтительнее (`RequestIssuance`). Задача без изменений её не трогает; изменения, ошибка в данных, смена вида документа
и исключение участника к ней не применяются — WARN в журнале сервиса, новой записи и второго запроса в 1С:УСК нет
(`RecordIssuance`, `IssuedRecords`); прекращение работы по заявке ISSUED тоже не трогает. В составе заявки участник
остаётся с видом выпущенного документа — состав возвращает `IssuanceService.apply`. После ERROR и CANCELLED следующая
задача заводит новую запись, как раньше (решение владельца 2026-10-22, К6g).

## Стек

Java 21, Spring Boot 4.0.7, Spring MVC на виртуальных потоках (реактивный стек не используем), Spring AMQP, Spring Data
JPA, Liquibase, PostgreSQL, RabbitMQ. Тесты — JUnit, Testcontainers. Версии библиотек задаёт BOM Spring Boot; в
объявлениях зависимостей координаты пишутся без версий. Сборка — Gradle с Groovy DSL, версия зафиксирована обёрткой
(`./gradlew`, не системный `gradle`); версия Spring Boot — в `gradle.properties`, там же `version=` сервиса по
Semantic Versioning 2.0.0 (история — `CHANGELOG.md` по Keep a Changelog, рубрика «Перенос» — что нужно сделать на
контуре при установке версии). Проверка перед коммитом: `./gradlew build`.

MVC подключён стартером `spring-boot-starter-web`, а не `spring-boot-starter-webmvc`: Nexus контура отдаёт только
`starter-web`. По той же причине без `spring-boot-starter-webmvc-test` и без `spring-boot-starter-restclient`.
Каждая новая зависимость — только после проверки координат в Nexus владельцем и строки в «Источниках документации»
`gauntlet/CLAUDE.md`. В S3 контура хранятся справки 070/у (печатные формы формирует 1С:УСК, у сервиса — только их
ссылки); клиент — MinIO Java SDK `io.minio:minio`: его нет в BOM Spring Boot, поэтому версия — свойство `minioVersion`
в `gradle.properties`, а не литерал в `build.gradle`. Адрес, бакет, учётные данные, таймауты и доверие сертификату —
переменные `S3_*`.

Репозитории выбирает свойство `publicRepositories` в `settings.gradle`: по умолчанию — только Nexus контура, со
значением `true` — только публичные. Задаётся `-PpublicRepositories=true|false` или переменной
`ORG_GRADLE_PROJECT_publicRepositories`; вне контура её выставляют хуки набора проверок и CI. Central через прокси иногда
отвечает 429 на пачку новых артефактов: повторить сборку через 20–60 секунд, к коду это отношения не имеет.

Сборка, `application.yml`, `Dockerfile`, `docker-compose.yml`, `.env.example`, `README.md`, тестовая обвязка
(`@IntegrationTest`, `@AmqpIntegrationTest`, `PostgresTestcontainer`, `TestSupportConfig`, приёмка) берутся из
`data-reference` как образец и переписываются под Договоры. Класс с логикой без тестов не копируется: каждый
перенесённый класс получает свои unit-тесты в том шаге, где появляется.

## Структура пакетов

Архитектура слоистая, база — `ru.projectx.contracts`; политика — `gauntlet/config/contract-service/architecture.properties`
(после подключения к набору). Целевой вид:

```
ru.projectx.contracts
├── ContractServiceApplication
├── config/          — @Configuration и @ConfigurationProperties; про AMQP не знает
├── entity/          — JPA-сущности: договоры КМ, полисы ЛМ, стороны, документы, акцепты, заказы, outbox, inbox
├── exception/       — исключения домена; несут идентификаторы, не тексты чужих исключений и не ПДн
├── repository/      — Spring Data JPA
├── dto/             — тела ответов REST и единый формат ошибки
├── message/         — тела сообщений ДГ-01…ДГ-07 и конверт meta (record'ы)
├── service/         — бизнес-логика: разбор состава, статусы, печатные формы, акцепт, оплата
│   ├── inbox/       — приём и обработка входящих сообщений по расписанию
│   ├── outbox/      — запись и публикация исходящих
│   ├── usk/         — общий механизм обмена с 1С:УСК: подготовка запросов, недоставка, ожидание и запись ответов
│   ├── lm/          — запрос полиса ЛМ в 1С:УСК и запись выпуска (вид записи для `usk/`)
│   ├── km/          — передача оплаченного договора КМ в 1С:УСК и запись регистрации (вид записи для `usk/`)
│   ├── payment/     — оплата договора КМ (сейчас — переход в PAID)
│   ├── status/      — ответ сервису Заявок о состоянии выпуска (ДГ-03)
│   ├── retention/   — стирание тел сообщений по сроку
│   ├── reference/   — порт чтения справочников data-reference (узкие интерфейсы `*Reads`) и правила порта
│   ├── storage/     — приём справок 070/у, реестр справок и порт хранилища (`CertificateStore`)
│   ├── packages/    — чтение состояния пакета по заявке (`RequestPackageReads`) по снимку ДГ-03
│   ├── acceptance/  — акцепт оферты договора КМ: запись акцепта, идемпотентность, блокировка строки договора
│   └── integration/ — граница с внешними системами: слушатели очередей, фабрики подключений к брокерам, публикация
│                      (только здесь знают про AMQP), адаптер порта справочников на `RestClient` (только здесь знают
│                      про HTTP к data-reference) и адаптер хранилища на клиенте MinIO (только здесь знают про S3)
└── controller/      — приём справок, состояние пакета и акцепт под общей аннотацией внутреннего API, фильтр
                       X-Request-Id, советники ошибок
```

В корне `service` — выпуск по задаче (разбор состава, договоры КМ, полисы ЛМ, прекращение, снимок сторон) и классы,
общие для подпакетов. Новый класс кладётся в подпакет своей обязанности, общий для нескольких — в корень своего пакета;
тест лежит в том же подпакете, что его класс.

Правила слоёв — как у `data-reference`: контроллер только вызывает сервис чтения своего ресурса через узкий интерфейс
`*Reads` и отдаёт ответ; транзакция и сборка DTO — в сервисе (`open-in-view` выключен); зависимости идут сверху вниз и
не разворачиваются; `config` не ссылается на пакеты модуля; циклов нет ни между компонентами, ни между подпакетами.
Про AMQP знает только `service/integration`: дальше границы идут `message_id` и тело как строка. Новая очередь — новая
строка реестра очередей и свойство, а не новый метод с `@RabbitListener`. Про HTTP к data-reference тоже знает только
`service/integration`: прикладной слой зависит от порта `service/reference` и исключений домена, а не от `RestClient`
и кодов ответов; серверная часть web (MVC, биндинг, фильтры, servlet API) слою `service` запрещена политикой.

**У слушателя одно решение — что ответить брокеру.** Ручное подтверждение, один потребитель, prefetch 1,
`missing-queues-fatal`: нет очереди — значит, неверно имя или контур, лучше не стартовать. Ответ брокеру слушатель
отправляет сам и исключений контейнеру не отдаёт (`InboxQueueListener`). Исходы: принято или дубль — `ack`; любой отказ
записи в журнал (временный или постоянный, причина не разбирается) — пауза `INBOX_REQUEUE_DELAY` и возврат в очередь
(`nack` с `requeue`), прерванная остановкой пауза ответа не даёт — сообщение вернёт закрытый канал; нечитаемое тело,
непригодное поле конверта `meta` (`message_id`, `correlation_id`, `topic`, `event_type`, `entity_version`) и тело,
которое база не примет никогда (`UnstorableText`), — `ack`, ERROR в журнал без тела и `contracts_inbox_lost_total`.
Карантина нет.

## Как пишем код

Уровень — сеньорский. Код читают чаще, чем пишут, и здесь его будет читать архитектор на ревью. Ниже не пожелания, а
требования к принимаемому коду.

Этот файл в рабочий контур не переносится, поэтому выжимка правил для контура лежит в `docs/code-style.md` (с
2026-10-20, решение владельца «2) да»), отступы и концы строк — в `.editorconfig` и `.gitattributes` модуля. Меняя
правило здесь, меняйте его и в `docs/code-style.md`, без следов разработки. Выжимка несёт и общие правила кода из
`gauntlet/CLAUDE.md` (правила 2, 4, 5, 9, 11, 13, 14, 15), лимиты размеров и правила из `gauntlet/config/checkstyle.xml`
и `pmd-ruleset.xml`, которые в контуре никто не проверит (что не ловить и не бросать, кодировка, `Locale`, скобки,
`default` у `switch`, `System.out`, интерфейсы коллекций в сигнатурах): меняя их там, меняйте и выжимку.

**Ключевое требование: понятность.** Структура не переусложняется. Класс, который существует «на будущее», не пишется;
абстракция с одной реализацией и без второго кандидата не заводится. **Исключения — границы и подмены:** контроллер
зависит от узкого интерфейса чтения своего ресурса, даже если реализация одна (DIP и ISP, правило 11 gauntlet); порт к
внешней системе — чтение справочников (`*Reads` в `service/reference`), публикация исходящих (`OutboundPublisher` в
`service/outbox`) и запись справок в хранилище (`CertificateStore` в `service/storage`) — держит адаптер
`service/integration` по эту сторону слоёв; ожидание, которое unit-тест подменяет
(`Pauses`). Порт справочников и интерфейс контроллера — разные интерфейсы. В остальном внутри `service` и ниже правило
«одна реализация — без интерфейса» действует как прежде.

### Комментарии и Javadoc — их нет

Правило владельца от 2026-10-12, общее для обоих модулей; действует вместо прежнего правила «не длиннее трёх строк».
Код, написанный до него, приводится к правилу отдельной задачей без изменения поведения; до неё ревьюер отмечает
только новые комментарии.

- **В коде и конфигурации модуля нет комментариев и Javadoc**: Java в `src/main`, `src/test` и `src/acceptanceTest`,
  `application.yml`, `#`-комментарии changeSet'ов, `build.gradle`, `settings.gradle`, `Dockerfile`,
  `docker-compose.yml`, скрипты и SQL. Код объясняет себя именами: если без пояснения непонятно, метод переименовывается
  или разбивается.
- **Неочевидная причина решения** — ловушка, которую легко «упростить», ограничение фреймворка, правило 1С:УСК или
  сервиса Заявок, порядок, транзакция, персональные данные — записывается в `docs/design.md` модуля простым
  человеческим языком, без канцелярита, с именем класса. Задача, которая вводит такую причину, дописывает
  `docs/design.md` в том же PR. Процедуры эксплуатации (сборка, запуск, все переменные окружения, метрики, разбор
  сбоев) — в `docs/operations.md`.
- **README модуля** короткий (до 3500 символов) и его пишет только координатор (правило владельца 2026-10-17,
  `gauntlet/CLAUDE.md`, «README модуля»). Сессия шага `README.md` не правит: если изменение делает README неверным
  (новая очередь, таймаут, переменная, таблица), это пункт отчёта «переслать координатору».
- **Исключения**: шапки фич (`src/acceptanceTest/resources/features/`) — спецификация с метками источников; поля
  `comment:` в changeSet'ах — история миграций, она хранится в базе; строка `#!` в скриптах; шаблон `.env.example` и
  `.gitignore` (не код); Gradle Wrapper (`gradlew`, `gradlew.bat`, `gradle/wrapper/`) — его генерирует Gradle; в
  `settings.gradle` и `build.gradle` — шапка переключателя `publicRepositories` и закомментированный вариант «только
  Nexus», готовая инструкция для контура (решение владельца 2026-10-12: остальные комментарии сборки, в том числе о
  подключении набора проверок, убраны).
- **Никаких следов разработки вне рабочего контура** (правило владельца от 2026-10-05) — это касается и `README.md`,
  `CHANGELOG.md`, `docs/` модуля и документов, которые уходят в контур: не упоминаются PR и их номера, GitHub, ветки, gauntlet и его
  гейты, сессии и роли, «решение владельца», номера шагов (К…) и решений (Р…, РК…), открытые вопросы (ОВД-…, ОВС-…).
  Причина правила пишется словами. Фичи и `src/acceptanceTest/` в контур не уходят, метки источников в них остаются.
- **Слова предметной области вместо идентификаторов документов** — в именах, README, `docs/` и CHANGELOG: «задача на выпуск»
  вместо «ДГ-01», «акцепт оферты» вместо «СЭ-03»; сокращение расшифровывается при первом употреблении (ПДн, ЛПУ, КМ).
- **Тесты**: имя теста читается как утверждение о поведении.
- Гейты правило не проверяют — его проверяет ревьюер.

### Размер и ответственность

- **Метод — не длиннее 25 строк кода, класс — не больше 12 методов, файл — не длиннее 300 строк** (лимиты набора
  проверок строже прежнего правила «40 строк» и действуют вместо него). Вышли за предел — в методе или классе больше
  одной ответственности.
- **Класс отвечает за одно.** Слушатель не разбирает бизнес-правила, публикатор не решает, что публиковать, сущность не
  знает про JSON сообщения, генератор печатной формы не ходит в хранилище.
- **Инъекция через конструктор, поля `final`.** Полевой `@Autowired` не используем.

### Никаких магических значений

1. **`@ConfigurationProperties`-запись с `@Validated`** — всё, что может отличаться между dev, stage и prod: таймауты,
   лестница повторов, размеры пачек, адреса, имена очередей, учётные данные, сроки хранения.
2. **`private static final`** — только действительно неизменное: имена полей JSON, коды ошибок, топики событий.
3. **Литерал в коде** — `0`, `1`, пустая строка. Всё остальное нет.

`@Value("${...}")` россыпью по классам не используем: конфигурация перестаёт быть видимой в одном месте и не проверяется
на старте. Единственное допустимое исключение — плейсхолдер `${…}` в атрибуте аннотации, когда у Spring нет другого
способа взять значение из свойства (`fixedDelayString` у `@Scheduled`). Выключатель `projectx.scheduling.enabled` —
только для тестов: в рабочем окружении его не меняют, других запусков проходов у сервиса нет.

### Декларативность

- Преобразования коллекций — Stream API; **стрим без побочных эффектов**: `forEach`, который пишет в базу, — это цикл,
  пишите цикл. Ранний выход и сложное ветвление — обычный цикл или цепочка `Optional`.
- **Стрим поверх JPA-сущностей — источник N+1.** Проекция выбирается запросом.
- `Optional` — тип возврата, не поля и не параметра; `orElseThrow` с доменным исключением вместо `get()`.
- `record` для DTO, тел сообщений и разобранных строк. Неизменяемость по умолчанию. `var` — где тип очевиден из правой
  части.
- Деньги — `BigDecimal`, не `double`.

### Без Lombok

Не используем. `record` закрывает боль, ради которой обычно тянут `@Value`/`@Data`. Сущности JPA не анемичные:
приватный конструктор за статической фабрикой (конструктор без параметров — `protected`, его требует JPA), мутация
только через именованные переходы (сейчас `offerDraft`, `revise`, `submit`, `markIssued`; дальше по тому же правилу —
`accept`, `markPaid`, `cancel`) — сеттеров нет ни одного. По той же причине **не
`@CreationTimestamp`/`@UpdateTimestamp`**: везде, где нужно «сейчас», инъецируется `java.time.Clock` — им тесты
управляют временем без `Thread.sleep`.

### Надёжность и исключения

Главное правило: **исключение либо обрабатывается осмысленно, либо летит дальше.** `catch` с логированием и
продолжением запрещён — он превращает сбой в тихое расхождение данных.

| Ситуация | Что делаем |
|---|---|
| Ошибка **временная** (сеть, таймаут, недоступная база, 503 соседа) | повтор по лестнице: обработка Inbox — первая попытка и три повтора через 1 / 5 / 15 мин; клиент справочников — ограниченные повторы из настроек |
| Ошибка **постоянная** (невалидное сообщение, тело не по контракту, архивная программа) | повторять бессмысленно: терминальный статус с причиной, ответ соседу с `error_code`, оповещение |
| Бизнес-ошибка по участнику | это не сбой обработки: сообщение обработано, участник — в ERROR с кодом и текстом в ДГ-03 |
| `InterruptedException` | восстановить флаг `Thread.currentThread().interrupt()` и выйти |

- Ловим конкретные типы. `catch (Exception e)` — только на верхней границе слушателя, планировщика и внешнего клиента, и
  там оно обязано классифицировать, а не подавлять. Никаких `e.printStackTrace()` и пустых `catch {}`.
- Исключение несёт контекст: `message_id`, заявка, договор. На время обработки сообщения и запроса контекст лежит в MDC
  (идентификаторы заявки, договора, сообщения, `requestId`); журнал пишется в структурном формате ECS
  (`logging.structured.format.console: ecs`), и все ключи MDC уходят в запись целиком — поэтому в MDC только
  идентификаторы, никаких персональных данных. Исключение к записи журнала не прикладывается: пишется тип отказа и
  SQLSTATE.
- **Таймаут задаётся на каждый внешний вызов** — к Дата-референсу, Ordering, S3, брокерам. Вызов без таймаута — дефект.
- **Таймауты базы — на пуле приложения, у миграций их нет.** `lock_timeout` 5 с, `statement_timeout` 30 с,
  `idle_in_transaction_session_timeout` 1 мин (стартовый `options` драйвера), `socketTimeout` 60 с, ожидание соединения
  2 с, `logServerErrorDetail=false`; значения — в настройках, те же переменные `DB_*`, что у `data-reference`. У
  Liquibase своё соединение без таймаутов; параметры драйвера, нужные и пулу, и миграциям (`sslmode` и т. п.), — только
  в `DB_URL`. Отказ по таймауту — временная ошибка.
- Ошибку не маскируем значением по умолчанию: пустой список вместо упавшего запроса — тихая неправда.

### Транзакции

- **Внешних вызовов внутри `@Transactional` нет** — ни HTTP к Дата-референсу, Ordering и S3, ни publish в брокер. Чтение
  справочников делается до транзакции, публикация — из Outbox отдельным процессом, объект справки в S3 пишется до
  транзакции записи в реестр.
- Границы транзакции — на прикладном сервисе, не на репозитории. `readOnly = true` на чтении.
- Запись в Outbox — в одной транзакции с изменением данных; запись в Inbox — в одной транзакции с отметкой приёма.
- Подтверждение брокеру (`ack`) уходит только после того, как исход зафиксирован в базе.
- Идемпотентность: повторная доставка сообщения — дубль по `message_id`; повторный акцепт с той же `contract_version` —
  прежняя запись; повторный ДГ-05 или ДГ-07 — состояние не меняется.
- Строку полиса ЛМ и договора КМ каждый путь записи берёт с блокировкой и решает по состоянию под блокировкой: одну
  запись — `findLockedById` (`@Lock(PESSIMISTIC_WRITE)`), записи заявки — `IssuanceRepositoryLocking.lockFresh`
  (`refresh` с блокировкой: сначала договоры, потом полисы, в каждой таблице по возрастанию `id` — один порядок на всех
  многострочных путях, чтобы не было взаимной блокировки). Ожидание ограничено `DB_LOCK_TIMEOUT`; отказ по таймауту и
  взаимная блокировка (40P01) — временная ошибка по правилам прохода. Hibernate пишет строку целиком, поэтому без
  блокировки последняя фиксация затирает чужой переход.

### Персональные данные

ПДн в сервисе: снимок сторон договора (`contract_persons`: ФИО, дата рождения, пол, документ, адрес), тела ДГ-01 в Inbox,
тела ДГ-04 и ДГ-06 в Outbox (в `message_attachments` — только ссылки на файлы), печатные формы в хранилище, свободный
комментарий прекращения (`cancel_comment` в `contracts` и `lm_policies`) и медицинские данные — справки 070/у в S3.
Справка и имя её файла не попадают ни в журнал, ни в метрики, ни в ответы; имя файла не хранится.

- **ПДн не пишутся в лог, метрики, health и тексты исключений.** В ошибке называется поле, но не значение; текст чужого
  исключения не идёт ни в лог, ни в `error_message` таблиц. Соединения открываются с `logServerErrorDetail=false`.
- **Тела сообщений стираются по сроку:** `payload` в `inbox_messages` — по сроку от приёма при любом исходе, в
  `outbox_messages` — по сроку от создания и только у PUBLISHED и FAILED; запись остаётся ради истории и
  идемпотентности. Срок — настройка (умолчание 30 суток, как у
  `data-reference`), окончательное значение согласуется с ИБ (ОВД-05). Стирание — SQL-запросом пачками.
- **Срок хранения снимка сторон и печатных форм после завершения поездки** — вопрос ИБ; до ответа данные не стираются,
  но код готов к стиранию по сроку из настройки.
- В тестах, фичах и примерах — только вымышленные значения.
- Разбор проблемных сообщений делается без выгрузки содержимого наружу.

### Тесты

- Testcontainers для PostgreSQL и RabbitMQ; без Docker — адреса `TEST_POSTGRES_URL` и `TEST_RABBITMQ_URL`. Mockito в
  unit-тестах подменяет соседние классы, репозитории и канал брокера, но не инфраструктуру тестов с контекстом. Ответы
  Дата-референса в тестах — `MockRestServiceServer` из spring-test на примерах стенда `data-reference` (копия в тестовых
  ресурсах); расхождение с сервисом ловит тест стенда на его стороне.
- Тесты, поднимающие приложение, помечаются одной аннотацией `@IntegrationTest`: настоящий PostgreSQL, остановленные
  часы (`FixedClockConfig`) и никакого брокера — слушатели не стартуют (`listener-auto-startup=false`), здоровье
  брокеров выключено (`management.health.brokers.enabled=false`) и расписания выключены
  (`projectx.scheduling.enabled=false`, как в приёмке). База приходит в контекст
  свойствами `spring.datasource.*` (`PostgresTestcontainer`), как в контуре, а не через `@ServiceConnection`;
  `@ServiceConnection` остаётся только у приёмки.
- Тестам с брокерами — `@AmqpIntegrationTest`; очереди в нём объявляет тест: на контуре их заводят соседи и 1С.
  Расписания в нём тоже выключены.
- Хранилища S3 в обеих аннотациях нет, его настройки — заглушки; тесты хранилища поднимают свой контейнер MinIO
  (`TestStorage`, образ — `TEST_MINIO_IMAGE`), приёмка — свой (`StandStorage`).
- Обе аннотации несут `@Tag("no-mutate")`: мутационное тестирование эти тесты не исполняет, код, покрытый только ими,
  считается непокрытым. Логика покрывается unit-тестами.
- Без Docker такие тесты **падают**, а не пропускаются. **`Thread.sleep` в тестах запрещён** — Awaitility с внятным
  условием. Имя теста говорит, что проверяется: `duplicateMessageId_isNotStoredTwice`, а не `test2`.
