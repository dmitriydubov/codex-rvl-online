# contract-service — сервис Договоров РВЛ ОНЛАЙН

**РВЛ ОНЛАЙН** — контур сервисов, через которые застрахованные по ДМС получают восстановительное лечение в
санаториях (ЛПУ): сервис Заявок ведёт заявки на лечение и их согласование, сервис Договоров — договоры, полисы
и личный кабинет застрахованного, сервис справочных данных (data-reference) — справочники и полисы из учётной
системы страховщика 1С:УСК.

**contract-service** по задаче сервиса Заявок решает, что выпускается по каждому участнику поездки, ведёт договоры КМ
(договор на сумму доплаты застрахованного: печатные формы, акцепт оферты, оплата, регистрация в 1С:УСК) и запрашивает
у 1С:УСК полисы ЛМ родственникам без доплаты. Он же бэкенд личного кабинета застрахованного. Собственного
пользовательского интерфейса у сервиса нет, наружу, за пределы контура, он не публикуется.

Сейчас это каркас с подключениями: приложение поднимается, подключается к базе и проходит миграции, держит
подключения к двум брокерам RabbitMQ — межсервисному брокеру контура (сервис Заявок) и брокеру 1С:УСК, — а договоров,
слушателей очередей и REST в нём ещё нет.

Версия — в `gradle.properties` (`version=`), история изменений — в [CHANGELOG.md](CHANGELOG.md).

## Стек

Java 21, Spring Boot 4.0.7 (Spring Framework 7.0.8, Spring Data JPA 4.0.6, Spring AMQP 4.0.4), Hibernate ORM 7.2.19,
Liquibase 5.0.3, PostgreSQL 16 (драйвер 42.7.11, пул HikariCP 7.0.2), RabbitMQ 4.1 (клиент 5.27.1), Jackson 3.1.4,
Micrometer 1.16.6 с реестром Prometheus, встроенный Tomcat 11.0.22, сборка Gradle 8.14.3. Версии библиотек задаёт BOM
Spring Boot.

## Порты

- `8080` — API сервиса и пробы `/livez`, `/readyz`.
- `8081` (`MANAGEMENT_PORT`) — `/actuator/health`, `/actuator/info` (версия сервиса), `/actuator/prometheus`.
- Локальный контур (`docker-compose.yml`): база `5432`; межсервисный брокер `5672`, его панель `15672`; брокер 1С:УСК
  `5673`, его панель `15673`.

## Переменные окружения

Обязательные, без умолчания, — пароли: `DB_PASSWORD`, `RABBITMQ_INTERNAL_PASSWORD`, `RABBITMQ_ONEC_PASSWORD`. Остальные
необязательны: умолчания ведут на локальные базу и брокеры из `docker-compose.yml` или заданы под рабочий режим.

| Переменная | Умолчание | Что задаёт |
|---|---|---|
| `DB_URL` | `jdbc:postgresql://localhost:5432/contract_service?logServerErrorDetail=false` | адрес базы; параметры драйвера, общие для пула и миграций, — только здесь |
| `DB_USERNAME` | `contract_service` | пользователь базы |
| `DB_PASSWORD` | — | пароль базы |
| `DB_CONNECTION_TIMEOUT_MS` | `2000` | ожидание свободного соединения пула, миллисекунды |
| `DB_SOCKET_TIMEOUT_SECONDS` | `60` | таймаут чтения сокета драйвером, секунды |
| `DB_LOCK_TIMEOUT` | `5s` | `lock_timeout` сеанса пула |
| `DB_STATEMENT_TIMEOUT` | `30s` | `statement_timeout` сеанса пула |
| `DB_IDLE_IN_TRANSACTION_TIMEOUT` | `1min` | `idle_in_transaction_session_timeout` сеанса пула |
| `MANAGEMENT_PORT` | `8081` | порт актуатора |

Брокеры настраиваются одинаково, у каждого свой префикс: `RABBITMQ_INTERNAL_*` — межсервисный брокер контура,
`RABBITMQ_ONEC_*` — брокер 1С:УСК.

| Переменная (`*` = `INTERNAL` или `ONEC`) | Умолчание | Что задаёт |
|---|---|---|
| `RABBITMQ_*_HOST` | `localhost` | хост брокера |
| `RABBITMQ_*_PORT` | `5672` у межсервисного, `5673` у 1С:УСК | порт брокера; с TLS в контуре — `5671` |
| `RABBITMQ_*_VHOST` | `/` | виртуальный хост |
| `RABBITMQ_*_USERNAME` | `contract_service` | логин брокера |
| `RABBITMQ_*_PASSWORD` | — | пароль брокера |
| `RABBITMQ_*_SSL_ENABLED` | `false` | TLS к брокеру |
| `RABBITMQ_*_SSL_VALIDATE_CERTIFICATE` | `true` | проверка сертификата брокера (центр сертификации — в `certs/`) |
| `RABBITMQ_*_SSL_VERIFY_HOSTNAME` | `true` | проверка имени хоста в сертификате; действует только вместе с проверкой сертификата |
| `RABBITMQ_*_LISTENER_AUTO_STARTUP` | `true` | запускать ли слушателей очередей этого брокера на старте |

Имена очередей заданы в `application.yml` значениями из документа «Точки интеграций сервис Договоров и Заявок» и
переопределяются переменными `INTERNAL_QUEUE_TASK_CHANGES`, `INTERNAL_QUEUE_STATUS_CHANGES`,
`ONEC_QUEUE_KM_CONTRACT_SUBMISSIONS`, `ONEC_QUEUE_KM_CONTRACT_REGISTRATIONS`, `ONEC_QUEUE_LM_POLICY_REQUESTS`,
`ONEC_QUEUE_LM_POLICY_ISSUES`; на новом контуре их сверяют со списком очередей брокера. Два свойства с одним именем
очереди или пустое имя не дают сервису запуститься.

Таймауты сеанса пишутся с единицами PostgreSQL (`ms`, `s`, `min`): число без единицы PostgreSQL читает как
миллисекунды. Подробности у каждой настройки — в `src/main/resources/application.yml` и шаблоне `.env.example`.

## Сборка и локальный запуск

Нужны JDK 21 и Docker: тесты поднимают PostgreSQL и RabbitMQ в контейнерах. Без Docker тесты берут базу из
`TEST_POSTGRES_URL` и брокер из `TEST_RABBITMQ_URL` (`amqp://логин:пароль@хост:порт/vhost`, отдельный тестовый брокер,
не рабочий); без Docker и без адресов они падают, а не пропускаются.

```shell
./gradlew build          # сборка и тесты
./gradlew bootJar        # только jar: build/libs/contract-service-<версия>.jar
```

Вне рабочего контура сборке нужны публичные репозитории: `./gradlew -PpublicRepositories=true …` или переменная
`ORG_GRADLE_PROJECT_publicRepositories=true`. По умолчанию сборка берёт зависимости только из Nexus контура.

Локально база и оба брокера поднимаются из `docker-compose.yml`, пароли — локального контура:

```shell
docker compose up -d
DB_PASSWORD=contract_service RABBITMQ_INTERNAL_PASSWORD=contract_service RABBITMQ_ONEC_PASSWORD=contract_service \
  LOGGING_STRUCTURED_FORMAT_CONSOLE= ./gradlew bootRun
curl http://localhost:8081/actuator/health
```

Пустая `LOGGING_STRUCTURED_FORMAT_CONSOLE` переключает журнал с JSON на обычный текст. Очередей соседей в локальных
брокерах нет: их заводят вручную в панелях брокеров, а пока их нет, слушателей выключают
(`RABBITMQ_INTERNAL_LISTENER_AUTO_STARTUP=false`, `RABBITMQ_ONEC_LISTENER_AUTO_STARTUP=false`; профиль `app` делает это
сам). Сервис в контейнере — `docker compose --profile app up -d --build`. Пароли локального контура известны всем,
поэтому порты по умолчанию открыты только на 127.0.0.1; открыть API и базу для других машин можно переменными
`SERVICE_BIND_ADDRESS` и `POSTGRES_BIND_ADDRESS` в `.env` (шаблон `.env.example`), брокеры и актуатор остаются
на 127.0.0.1.

### Образ

Образ собирается из `Dockerfile` модуля (нужен BuildKit). Откуда взять jar, задаёт аргумент `JAR_SOURCE`:

- `build` — собрать внутри образа, так собирает CI. Нужна сеть до Nexus и дистрибутива Gradle. Вне контура задайте
  `PUBLIC_REPOSITORIES=true`, чтобы зависимости брались из Maven Central.
- `host` — взять собранный на машине, когда у сборки нет сети:
  `./gradlew bootJar && docker build --build-arg JAR_SOURCE=host .`

В сети без выхода наружу базовые образы и Gradle берутся из зеркала Nexus (аргументы `JDK_IMAGE`, `JRE_IMAGE`,
`GRADLE_DISTRIBUTION_URL`). Сертификаты корпоративного центра сертификации кладутся в `certs/`: без них JVM не
доверяет Nexus при сборке. В слои образа они не попадают. Тесты при сборке образа не запускаются: им нужен Docker,
их прогоняет CI до сборки образа.

## Почему так устроено

**Таймауты базы — у пула, у миграций их нет.** Пул приложения открывает каждое соединение с `lock_timeout`,
`statement_timeout` и `idle_in_transaction_session_timeout` (параметр драйвера `options`) и с таймаутом чтения сокета:
запрос не висит на чужой блокировке или оборванной сети и не держит поток. Liquibase получает своё соединение
(`spring.liquibase.url`, `user`, `password`), без пула и его таймаутов, чтобы долгую миграцию на живой базе ничто не
оборвало. Поэтому параметры драйвера, нужные и пулу, и миграциям (`sslmode` и подобные), задаются только в `DB_URL`.

**Текст ошибки базы — без значений строки.** Драйвер PostgreSQL по умолчанию дописывает в текст ошибки подробности
сервера, а там бывают значения строки, то есть персональные данные сторон договора. `logServerErrorDetail=false` задан
пулу и стоит в умолчании `DB_URL`; тот, кто задаёт свой `DB_URL`, сохраняет его там, иначе ошибка миграции попадёт в
журнал вместе со значениями.

**В тестах у PostgreSQL нет `@ServiceConnection`.** Адрес контейнера приходит свойствами `spring.datasource.*`, как на
рабочем стенде. С `@ServiceConnection` Liquibase получил бы данные контейнера в обход `application.yml`, и тесты не
видели бы, с какими настройками на самом деле идут миграции. Без Docker тесты берут базу из `TEST_POSTGRES_URL`
(отдельную, не рабочую); без Docker и без адреса они падают, а не пропускаются.

**Два брокера — два подключения, и ни одно не «по умолчанию».** Сервис Заявок и 1С:УСК живут на разных брокерах с
разными адресами и учётными данными, поэтому у каждого брокера свои настройки (`projectx.brokers.internal`,
`projectx.brokers.onec`) и свои бины: подключение, шаблон публикации и фабрика контейнеров слушателей, помеченные
квалификаторами `@InternalBroker` и `@OneCBroker`. Автонастройка AMQP Spring Boot выключена: она строит одно подключение
из `spring.rabbitmq.*` и с двумя фабриками не поднимается, а главное — завела бы «подключение по умолчанию», в которое
слушатель или публикатор попал бы молча. Теперь бин без квалификатора не создаётся: кандидатов два, и Spring требует
назвать брокер. Свойства `spring.rabbitmq.*` в этом сервисе не действуют.

**Подтверждения издателя включены на каждом подключении.** Исходящие сообщения уходят через Outbox: запись считается
доставленной только после подтверждения брокера, иначе сбой брокера или сети терял бы сообщение молча. Подключения
созданы с подтверждениями с привязкой к сообщению (`CORRELATED`): публикатор получает подтверждение или отказ по
каждому сообщению через `CorrelationData`, не завися от общего обработчика шаблона.

**Недоступный брокер не роняет сервис, а виден в health.** Подключение открывается при первом обращении, поэтому старт
без брокера проходит, а компоненты `internalBroker` и `onecBroker` в `/actuator/health` показывают UP при открытом
соединении и DOWN с типом отказа и адресом брокера — без логина и пароля. Проверка сама открывает соединение, так что
после восстановления брокера она же его и возвращает. Пробы `/livez` и `/readyz` от брокеров не зависят: синхронные
вызовы сервиса Заявок работают и без них. Штатный компонент `rabbit` Spring Boot выключен (он показал бы оба брокера
под одним именем); в контексте без брокеров компоненты подключений выключают свойством
`management.health.brokers.enabled=false`. Метрики подключений (`rabbitmq_*`) помечены брокером: `name="internalBroker"`,
`name="onecBroker"`.

**Очереди сервис не объявляет.** В контуре их заводят сервис Заявок и 1С:УСК. Объявление очереди с другими параметрами
закрыло бы канал, а точных параметров чужой очереди сервис не знает. Поэтому в контексте нет `RabbitAdmin`, а имена
очередей — настройки без умолчаний в коде: опечатка роняет запуск (`missing-queues-fatal`), а не выглядит как
«сообщений нет». В тестах очереди объявляет сам тест, а оба брокера изображает один контейнер RabbitMQ с двумя
виртуальными хостами: подключения, очереди и права в них раздельные, как у разных брокеров.

**Время — только через бин `Clock`.** Везде, где нужно «сейчас», внедряются часы, а тесты подменяют их остановленными.
По той же причине в сущностях не будет `@CreationTimestamp`: Hibernate ставит их по системным часам мимо этого бина.

**Сборка Gradle.** Сборка одномодульная и общих артефактов с соседями не имеет. Тесты разрешают зависимости строго по
версиям рабочего classpath (`shouldResolveConsistentlyWith`), чтобы проверялся тот же набор библиотек, что уйдёт в
работу. Агент Mockito подключается явно через `-javaagent`: на ходу его подключает сам Mockito, а JDK уже предупреждает,
что однажды это запретит.
