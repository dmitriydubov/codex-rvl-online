# data-reference в нескольких репликах — анализ

2026-10-20, координатор data-reference. Повод — решение владельца «закладываем сразу, что будет нужна» работа в нескольких
репликах (2026-10-20). Кода в этом анализе нет: перечень мест, где сервис рассчитан на одну реплику, варианты с ценой,
рекомендация и план шагов. Состояние кода — `main` после Ш78 (подпакеты), сверка документации — раздел «Источники».

## Коротко

- Нагрузка многорепличности не требует: один экземпляр с 1 CPU держит около 800 RPS смешанной нагрузки
  (`data-reference/docs/load-testing.md`). Смысл — доступность: выкатка и перезапуск пода без простоя.
- На одной реплике держатся две вещи с риском для данных: **порядок приёма** (один потребитель на очередь, время приёма —
  по часам пода) и **разбор сырья** (выборка без блокировки: две реплики возьмут одни и те же строки и применят два
  сообщения одного потока параллельно, старое ляжет поверх нового). Остальное — двойная работа, двойной журнал и
  отставание кэша.
- **Рекомендация: один активный экземпляр для фоновой работы (лидер) и REST на всех репликах.** Приём из 1С, разбор и все
  проходы по расписанию идут только у лидера, поэтому все нынешние гарантии порядка сохраняются без переделки разбора.
  Лидера выбирает стандартный механизм Spring Integration (`LockRegistryLeaderInitiator` поверх `JdbcLockRegistry` в той
  же базе); если зависимости нет в Nexus — своя блокировка PostgreSQL на уровне сеанса. Кэш на всех репликах сбрасывается
  уведомлением PostgreSQL (`LISTEN`/`NOTIFY`), срок жизни 10 минут остаётся страховкой.
- План — 4 шага, 19–27 ч: лидер фоновой работы (Ш81), сброс кэша на всех репликах (Ш82), время приёма по часам базы
  (Ш83, может войти в Ш81), выкатка в две реплики на стенде (Ш84). До Ш84 желателен прогрев после старта (Ш80).

## Варианты для фоновой работы (пункты 1–4, 6–8, 10, 11)

**А. Лидер: фоновая работа только у одного экземпляра, REST — у всех.** Приём (контейнеры очередей стартуют, когда
экземпляр получил лидерство, и останавливаются, когда потерял), проход разбора, стирание, тревоги и снимок метрик —
только у лидера. Остальные отвечают на REST. Все гарантии одного потребителя и одного разбора сохраняются как есть.

- А1. **Spring Integration** — `LockRegistryLeaderInitiator` поверх `JdbcLockRegistry` (`DefaultLockRepository`, таблица
  блокировок в нашей базе — миграцией Liquibase). События `OnGrantedEvent`/`OnRevokedEvent` включают и выключают
  фоновую работу. Плюсы: стандартный механизм Spring (правило 13), не нужен доступ к API Kubernetes. Минусы: новые
  зависимости `org.springframework.integration:spring-integration-jdbc` и `spring-integration-core` 7.0.5 (версия из BOM
  Spring Boot 4.0.7) — проверить в Nexus; при смене лидера есть короткий период без лидера (срок блокировки и задержка
  `busyWaitMillis`).
- А2. **Своя блокировка PostgreSQL на уровне сеанса** (`pg_try_advisory_lock`) на выделенном соединении вне пула: лидер —
  кто держит блокировку; если процесс умер, сеанс закрывается и блокировка снимается. Плюсы: без зависимостей. Минусы:
  самописный механизм, своё соединение и своя обработка его обрыва.
- А3. Kubernetes Lease — нужны доступ к API кластера и права RBAC, привязка к Kubernetes. Не рекомендую.

**Б. Фоновая работа на всех экземплярах с защитой по потоку.** Приём — эксклюзивный потребитель Spring AMQP (`exclusive`)
или single active consumer у очереди; разбор — блокировка потока на время транзакции сообщения
(`pg_try_advisory_xact_lock` по потоку) с перепроверкой головы потока под блокировкой; каждое расписание — со своей
защитой. Минусы перевешивают: флаг `exclusive` работает только на классических очередях (кворумные его игнорируют),
single active consumer включается только аргументом при объявлении очереди и не включается политикой — а очереди
объявляет 1С:УСК; мест для ошибок больше, а пропускная способность приёма при нашей нагрузке не нужна.

**Рекомендация: А1, если `spring-integration-jdbc` есть в Nexus; иначе А2.** Пункт 11 (здоровье) решается в том же
шаге: нелидер не ждёт потребителей, лидер ждёт их у всех своих очередей.

## Варианты для кэша (пункт 9)

- В1. **`LISTEN`/`NOTIFY` PostgreSQL.** Разбор после фиксации шлёт `NOTIFY` с именем потока (уведомление доставляется
  слушателям только после фиксации транзакции), каждая реплика слушает на выделенном соединении
  (`PGConnection.getNotifications` в pgjdbc) и сбрасывает кэши этого потока той же таблицей зависимостей
  (`ReferenceCacheDependencies`). При обрыве соединения уведомления теряются — страховка: сброс всех кэшей при
  переподключении и прежний срок жизни 10 мин.
- В2. **Только срок жизни**, укороченный до минуты: без кода, но больше обращений к базе и отставание до минуты на всех
  репликах, кроме лидера.
- В3. Spring Integration `PostgresChannelMessageTableSubscriber` — то же `LISTEN`/`NOTIFY`, но через таблицу сообщений
  канала и триггер: для сброса кэша тяжело.

**Рекомендация: В1** (если владельцу достаточно отставания до минуты — В2, тогда без шага).

## Время приёма (пункт 2)

При лидере потребитель один, но после смены лидера время приёма ставят часы другого пода. Если часы разошлись, новое
сообщение может получить момент раньше уже записанного и при разборе встать перед ним. Варианты: время базы при записи
(`clock_timestamp()` в том же `INSERT`) или последовательность для порядка разбора. Рекомендую время базы — порядок
и время в одном столбце, без новой колонки. Тесты сейчас управляют временем через `Clock` — их придётся перевести на
время базы или сравнение порядка; поэтому шаг отдельный, хотя может войти в Ш81.

## Решения владельца (2026-10-20)

«1) да 2) а) 3) да 4) сразу 5) максимум 3 реплики, стратегии выкатки пока не знаю, берём стандартные 6) да»:

- вариант **А** (лидер), механизм **А1** — `spring-integration-jdbc` и `spring-integration-core` 7.0.5 есть в Nexus;
- кэш — **сброс сразу** (В1, шаг Ш82);
- **до 3 реплик**, выкатка — стандартная `RollingUpdate` Kubernetes: по умолчанию `maxUnavailable` 25 % с округлением
  вниз и `maxSurge` 25 % с округлением вверх, то есть на 3 репликах — 0 недоступных и 1 лишний под; во время выкатки
  работают до 4 подов двух версий, лидер — один;
- соединений с базой при 4 подах — до 4 × (10 + 5 + 1) = 64, плюс по одному на миграции при старте; умолчание PostgreSQL
  `max_connections` — 100, значение базы контура уточнить до Ш84;
- план Ш81 → Ш83 → Ш82 → Ш84 утверждён; после выпуска `1.0.0-rc.2` `main` возвращается к `1.0.0-SNAPSHOT`.

После остановки спецификации Ш81 — «пока 2-я реплика включаться не будет как минимум до прода», «доработки лучше сделать
заранее», «1) да 2) а)»:

- Ш81 → Ш83 → Ш82 → Ш80 делаются заранее, по готовности; **Ш84 — при подготовке к проду**, до него стенд работает в одной
  реплике со стратегией `Recreate`;
- после мержа Ш81 смена лидера проверяется на стенде вручную: временно две реплики, удалить под лидера, убедиться, что
  роль перешла, вернуть одну реплику.

## Источники

- RabbitMQ 4.1, «Consumers»: исключительность потребителя — только для классических очередей, кворумные игнорируют флаг
  `exclusive`; single active consumer включается аргументом `x-single-active-consumer` при объявлении очереди и не
  включается политикой → raw.githubusercontent.com/rabbitmq/rabbitmq-website/main/versioned_docs/version-4.1/consumers.md.
- Spring AMQP 4.0 (метатег 4.0.5, в сборке 4.0.4), «Message Listener Container Configuration»: `exclusive` — единственный
