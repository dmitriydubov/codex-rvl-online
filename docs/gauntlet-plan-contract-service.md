### 2.2. Сверка шагов с документами и текущим кодом (2026-10-07)

Что изменилось против разделов 3.9–3.10 общего плана и почему:

1. **Таймауты клиента К2a пересчитаны.** С Ш64 и Ш69 (2026-10-07) ожидание соединения в пулах data-reference — 2 с, лимит
   REST-чтения — 3 с, сетевой тайм-аут пула REST — 5 с: худший ответ ≈ 5 с, таймаут чтения клиента Договоров — от 7 с.
   Прежняя карточка К2a (connectionTimeout 30 с, socketTimeout 60 с) устарела. Значения — ответ О8 (раздел 6).
2. **`RestClient` без новых зависимостей — только вручную.** По `./gradlew dependencies --configuration runtimeClasspath`
   data-reference (2026-10-07) в classpath Boot 4.0.7 через `spring-boot-starter-web` нет модуля `spring-boot-restclient`:
   автонастроенный бин `RestClient.Builder` и свойства `spring.http.clients.*` (connect-timeout, read-timeout) даёт
   `spring-boot-starter-restclient` (есть в BOM 4.0.7; в Nexus контура не проверялся). Сам класс `RestClient` — в
   `spring-web` (Spring Framework 7.0). Выбор — РК1 (раздел 7): (а) `RestClient.builder()` из spring-web с
   `JdkClientHttpRequestFactory` и своими `@ConfigurationProperties` таймаутов, без новой зависимости; (б) новая зависимость
   `org.springframework.boot:spring-boot-starter-restclient:4.0.7` после проверки в Nexus. Рекомендация — (а): правило
   «Nexus отдаёт не все модули Boot 4» уже стоило отказа от webmvc-стартеров.
3. **Ретраи К2a — средствами Spring Framework 7.0.** `@Retryable` / `RetryTemplate` (`org.springframework.resilience`,
   включается `@EnableResilientMethods`): по умолчанию 3 повтора с паузой 1 с, перечень исключений — `includes`/`excludes`,
   `MethodRetryPredicate` для «повторять только на 503 и на 404 ещё не пришедшего полиса». Источник —
   docs.spring.io/spring-framework/reference/core/resilience.html (метатег версии 7.0.9 при сборке 7.0.8). Spring Retry как
   отдельная зависимость не нужен.
4. **Второй брокер в Boot 4.0.** Boot автонастраивает одну `CachingConnectionFactory` из `spring.rabbitmq.*`; второй брокер —
   свои бины `CachingConnectionFactory`, `RabbitTemplate` и `SimpleRabbitListenerContainerFactory` на своих
   `@ConfigurationProperties`, либо `SimpleRoutingConnectionFactory` (Spring AMQP 4.0, «Routing Connection Factory»).
   Выбор — РК2 (раздел 7); рекомендация — отдельные фабрики на брокер, без маршрутизации по thread-bound ключу: у
   слушателей и публикаций разные брокеры статически.
5. **Стартеры OAuth2 в Boot 4 переименованы.** В BOM 4.0.7 есть и `spring-boot-starter-oauth2-client`, и

### 4.3. Условные и отложенные (вне итога)

- **К1b** — красное каркаса по итогам О11.
- **Пауза потребителей при недоступной базе** и **карантин нечитаемых тел** по образцу data-reference (Ш30, Ш31) — если
  specifier К3 не включит их в объём, остаток записывается сюда и ставится отдельным шагом до переноса в контур.
- **Кэш справочников на стороне Договоров** — ТЗ СЭ его исключает; только по решению владельца (правило 14).
- **Распределённый сброс кэша и SKIP LOCKED** — при нескольких репликах (общее с data-reference).
- **Возвраты (ОВД-08)**, **перевыпуск при изменении ПДн после акцепта (ОВД-10)** — по ответам владельца.
- **`.gitlab-ci.yml`** — когда владелец назовёт версию GitLab контура и реестр (общее правило версий, Ш71).
- **Пауза потребителей при недоступной базе и карантин нечитаемых тел — остаток К3** (specifier К3 не включил, 2026-10-12):
  сценарий К3 закрепляет только «сообщение остаётся в очереди и принимается после восстановления» (возврат в очередь после
  паузы `INBOX_REQUEUE_DELAY` 5 с, без паузы потребителя); то единственное, что база не примет никогда (нулевой символ,
  непарный суррогат), отсекает парсер конверта — сообщение теряется с ERROR, карантинной таблицы нет (решение владельца по
  п. 5 отчёта К3). Отдельный шаг по образцу Ш30/Ш31 до переноса в контур, после ответа контура о типе очереди (quorum,
  `delivery-limit`). Туда же — `SKIP LOCKED` при нескольких репликах (проход обработчика Inbox сейчас без него).
- **Несколько экземпляров Договоров — остаток К4** (отчёт PR #163, 2026-10-13): проход публикатора исходящих (`findDue`)
  тоже без `SKIP LOCKED` — при двух экземплярах возможна двойная отправка (получатель отбросит по `message_id`); «последняя
  запись участника» в снимке ДГ-03 выбирается по наибольшему UUID версии 7, монотонному только внутри одной JVM; подтверждение
  брокера, пришедшее после `OUTBOX_CONFIRM_TIMEOUT`, не учитывается — повтор с тем же `message_id`. Один шаг вместе с
  `SKIP LOCKED` Inbox, когда владелец решит про реплики.
- **Поиск выпущенного полиса в справочнике — остаток К5** (решение по п. 13 остановки, 2026-10-13): ДГ-07, не дождавшийся
  полиса в data-reference после лестницы 1/5/15 мин, — FAILED, полис остаётся SUBMITTED, возврат вручную по журналу и
  счётчику. Если 1С → data-reference отстаёт дольше ~20 минут, нужна отдельная (длинная) лестница для поиска полиса или
  сверка по расписанию «SUBMITTED без полиса» — отдельный шаг после опыта стенда. Туда же — отзыв запроса ДГ-06 при
  прекращении заявки, если 1С:УСК даст такой контракт (раздел 6).
- **Ответ ДГ-03 на исправленную ошибку полиса ЛМ рядом с договором в DRAFT_READY — остаток К6a** (п. 5 остановки,
  2026-10-13): правило К4 публикует снимок только на новое остановленное состояние записи, поэтому полис ЛМ, вышедший из
  ERROR в новую запись при договоре КМ в DRAFT_READY, ответа сервису Заявок не даёт (до К6a это скрывал отложенный
  снимок). Отдельное правило «снимок на выход участника из ошибки» — отдельный шаг вместе с ответом Заявок по ДК-06.

### 8.0. Задача для Jira — К3 (утверждена 2026-10-12 «1) да», сделана: PR #161)

**Тема.** contract-service: приём задачи на выпуск от сервиса Заявок и прекращение работы по заявке.

**Что и зачем.** Сервис Договоров начинает делать свою основную работу: принимать из очереди сервиса Заявок задачу на
выпуск по заявке и решать, что выпускается по каждому участнику поездки. Для этого в сервисе появляются таблицы

работы все договоры и полисы заявки переводятся в «прекращено» с причиной, история сохраняется. Ответы сервису Заявок о
статусах в этом шаге не отправляются (их добавит следующий шаг с исходящей очередью). Попутно адрес сервиса справочных
данных становится обязательной настройкой без умолчания, а один класс клиента справочников переименовывается по итогам

  проверки пройдены.
- Сообщение подтверждается брокеру только после записи в базу; при недоступной базе сообщение остаётся в очереди.
- Персональные данные участников не попадают в журнал и тексты ошибок; срок обезличивания входящих сообщений — настройка.
- Расписание обработки и число попыток — настройки с умолчаниями; переменные — в README и `.env.example`.
- Схема базы — миграциями Liquibase; таблицы и индексы — по документу «Структура данных (Сервис договоров)».
- В коде нет комментариев; причины решений — в README; следов внешней разработки нет.

КМ; что делать при изменении данных после акцепта и после фиксации сумм; срок обезличивания входящих сообщений
