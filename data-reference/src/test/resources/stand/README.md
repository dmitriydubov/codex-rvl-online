# Стенд потребителя для сервиса Договоров

Живой `data-reference` с синтетическими данными 1С:УСК — чтобы проверять клиент сервиса Договоров
на трёх `GET`: `/internal/v1/policies/{id}`, `/internal/v1/insurance-contracts/{id}`,
`/internal/v1/programs/{id}`. Как поднять и сбросить — шапка `data-reference/docker-compose.yml`
(профиль `stand`).

| Файл | Что это |
|---|---|
| `seed.sql` | сырьё 1С в `inbound_message`: ТЗ-3 (санаторий, страхователь) → ТЗ-2 (договор ДМС) → ТЗ-6 (программа) → ТЗ-1 (полис), статус `NEW`; разбирает планировщик сервиса |
| `seed.sh` | одноразовая закладка для compose: ждёт схему, которую накатывает сервис, и выполняет `seed.sql` |
| `examples/*.json` | запросы и ответы сервиса на этих данных, по порядку имён |

Все данные вымышлены: GUID сгенерированы, почта — на `example.com`.

Полис сегодня отдаётся целиком, вместе с полями застрахованного (ФИО, дата рождения, пол, e-mail).
Сервису Договоров на них не опираться: ему нужны номер, `external_id` и период действия, а ПДн
из его ответа уходят по решению Р20 (шаг Ш39) — тогда же поменяются примеры 01 и 03.

## Примеры

Каждый файл — один запрос и ответ:

```json
{
  "description": "что показывает пример",
  "placeholders": { "policy_id": "что за значение и откуда оно берётся" },
  "request":  { "method": "GET", "path": "/internal/v1/policies/{policy_id}", "headers": { "X-Request-Id": "stand-03" } },
  "response": { "status": 200, "headers": { "X-Request-Id": "stand-03" }, "body": { } }
}
```

`id` записей генерирует сервис при разборе сырья, поэтому в примерах на их месте плейсхолдеры
вида `{policy_id}` — UUID, свой на каждом стенде. Первые примеры находят записи по `external_id`
(GUID 1С из `seed.sql`) и выдают эти `id`, следующие ими пользуются. То же с `X-Request-Id`:
присланный возвращается как есть, не присланный сервис выдаёт сам (UUID, `{issued_request_id}`).

На живом стенде пример выполняется подстановкой значений, например:

```sh
curl -s -H 'X-Request-Id: stand-01' \
  'http://localhost:8080/internal/v1/policies?external_id=9e6ee30d-2275-417d-a44c-039d3b8c2ac5'
```

Примеры — часть контракта: тест `ConsumerStandTest` выполняет их по порядку на тех же файлах
и падает, если ответ сервиса разошёлся с примером хоть одним полем. Изменение ответа правит
пример в том же PR.
