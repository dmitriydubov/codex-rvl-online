# Стенд потребителя для сервиса Договоров

Живой `data-reference` с синтетическими данными 1С:УСК — чтобы проверять клиент сервиса Договоров
на его `GET`: полис без персональных данных `/internal/v1/policies/{id}/contract-view` (и по GUID 1С —
`/internal/v1/policies/contract-view?external_id=…`), `/internal/v1/insurance-contracts/{id}`,
`/internal/v1/programs/{id}`. Как поднять и сбросить — шапка `data-reference/docker-compose.yml`
(профиль `stand`).

| Файл | Что это |
|---|---|
| `seed.sql` | сырьё 1С в `inbound_message`: ТЗ-3 (санаторий, страхователь) → ТЗ-2 (договор ДМС) → ТЗ-6 (программа) → ТЗ-1 (полис), статус `NEW`; разбирает планировщик сервиса |
| `seed.sh` | одноразовая закладка для compose: ждёт схему, которую накатывает сервис, и выполняет `seed.sql` |
| `examples/*.json` | запросы и ответы сервиса на этих данных, по порядку имён |

Все данные вымышлены: GUID сгенерированы, почта — на `example.com`.

Полис по `/internal/v1/policies/{id}` (полис для сервиса Заявок, примеры 01 и 03) отдаётся целиком, вместе с полями
застрахованного (ФИО, дата рождения, пол, e-mail): так его читает сервис Заявок. Сервису Договоров
нужны номер, `external_id` и период действия. Персональные данные (ПДн) он получает от сервиса Заявок,
поэтому полис читает без них — `…/contract-view`, примеры 09 и 10.

ФИО, дата рождения и e-mail хранятся в полисе, пока он действует, и ещё запас после окончания срока или
перевода в архив (`POLICY_PERSONAL_DATA_GRACE`, по умолчанию 30 суток). Потом они стираются: полис для сервиса Заявок отдаёт их
пустыми (`null`) с признаком `personal_data_erased: true`, у остальных полисов признак `false`. Полис стенда
действует до 2030 года, поэтому в примерах признак `false`.

## Примеры

Каждый файл — один запрос и ответ:

```json
{
  "description": "что показывает пример",
  "placeholders": { "policy_id": "что за значение и откуда оно берётся" },
  "condition": { "locked_table": "только у примера 503: что держит базу" },
  "request":  { "method": "GET", "path": "/internal/v1/policies/{policy_id}", "headers": { "X-Request-Id": "stand-03" } },
  "response": { "status": 200, "headers": { "X-Request-Id": "stand-03" }, "body": { } }
}
```

`id` записей генерирует сервис при разборе сырья, поэтому в примерах на их месте плейсхолдеры
вида `{policy_id}` — UUID, свой на каждом стенде. Первые примеры находят записи по `external_id`
(GUID 1С из `seed.sql`) и выдают эти `id`, следующие ими пользуются; сервису Договоров `id` полиса
без ПДн выдаёт пример 09. То же с `X-Request-Id`:
присланный возвращается как есть, не присланный сервис выдаёт сам (UUID, `{issued_request_id}`).

Пример 12 показывает 503 `SERVICE_UNAVAILABLE`: база не ответила вовремя. Сам по себе стенд
503 не отдаёт — раздел `condition` примера говорит, при каком состоянии базы он верен
(`locked_table` — таблица, которую на время запроса держит под `ACCESS EXCLUSIVE` другой сеанс). На живом
стенде: в `psql` к базе стенда `BEGIN; LOCK TABLE policies IN ACCESS EXCLUSIVE MODE;`, затем запрос,
затем `ROLLBACK`. Такой ответ сервис Договоров повторяет позже.

`/actuator/health` (порт актуатора: `http://localhost:8081/actuator/health`) отвечает `UP`,
как только сервис поднят, — раньше, чем данные заложены и разобраны. Данные готовы, когда пример 09 отвечает `200`.

На живом стенде пример выполняется подстановкой значений, например:

```sh
curl -s -H 'X-Request-Id: stand-09' \
  'http://localhost:8080/internal/v1/policies/contract-view?external_id=9e6ee30d-2275-417d-a44c-039d3b8c2ac5'
```

Примеры — часть контракта: тест `ConsumerStandTest` выполняет их по порядку на тех же файлах
и падает, если ответ сервиса разошёлся с примером хоть одним полем. Изменение ответа правит
пример в том же изменении кода.
