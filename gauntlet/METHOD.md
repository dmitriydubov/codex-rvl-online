# Метод Gauntlet: инструкция к бандлу стартера

Ревизия бандла 3, 2026-10-04 (эталон — репозиторий `rvl-online`, набор после PR #28 и PR #29). Этот файл
прикрепляется к первой сессии нового проекта вместе с бандлом `gauntlet-starter-<дата>.tar.gz`. Он описывает,
что лежит в бандле, какие протоколы запускаются словом в чате и какие правила работы владелец принял в
эталонном проекте. Правила для агентов живут в `gauntlet/CLAUDE.md` бандла; здесь — порядок действий человека.

## 1. Что в бандле

```
gauntlet/
  CLAUDE.md        процесс и правила для агентов (импортируется корневым CLAUDE.md проекта)
  README.md        как метод выглядит для владельца, состав набора, лазейки и чем они закрыты
  INSTALL.md       подключение модуля (Gradle-сборки) к набору
  METHOD.md        этот файл
  install.sh       механическая часть установки: переносит claude/ и ci/ на их места, дописывает импорт в CLAUDE.md
  gauntlet.gradle  все гейты одним скрипт-плагином
  config/          пороги, политика архитектуры, Checkstyle, PMD, allowlist'ы (integrity, CRAP, RUN_ERROR мутанты PIT);
                   config/<module>/ — пример оверлея модуля (из эталона: data-reference)
  tools/           IntegrityCheck, CrapGate, DryGate, GherkinMutator, PitSummary (single-file Java 21)
  archtest/        ArchUnit-тест по config/architecture.properties
  hooks/           guard.py (PreToolUse), stop_gate.py (Stop и SubagentStop hardener'а), session_start.sh, selftest.py
  templates/       конфигурация Cucumber + Spring и пример фичи на русском
  claude/          .claude/settings.json (хуки и права) и роли specifier, hardener, reviewer — install.sh переносит в .claude/
  ci/              gauntlet.yml — install.sh переносит в .github/workflows/
```

Что в бандле от эталонного проекта и подлежит замене при установке: таблица «Репозиторий» и раздел «Правила владельца»
в `gauntlet/CLAUDE.md` (модули, рабочий контур, Nexus), раздел «Источники документации» (версии стека эталона: Spring Boot
4.0.7, Hibernate 7.2.19, RabbitMQ 4.1, PostgreSQL 16), `config/<module>/` (пакет, исключения из мутаций, политика
архитектуры), `config/pit-runerror-allowlist.txt` (строки эталона удалить), шаблон фичи. Пороги гейтов в
`config/gauntlet.properties` — метод, менять их не надо.

## 2. Протоколы

Каждый протокол — одна облачная сессия Claude Code на целевом репозитории. К сессии прикрепляют этот файл (и бандл
или план, где сказано) и пишут слово протокола.

| Слово | Окружение | Что делает сессия | Что получает владелец |
|---|---|---|---|
| `start` | без guard (набора ещё нет), режим Accept edits | задаёт вопросы о репозитории, модулях, стеке, документации и рабочем контуре; распаковывает бандл, адаптирует `gauntlet/CLAUDE.md`, `config/`, источники документации; встраивает `gauntlet.gradle` в сборку; добивается зелёного `./gradlew gauntlet` на текущем коде; запускает `install.sh` последним; открывает один PR | PR с отчётом: что адаптировано, что в коде красное при касании, решения владельца нумерованным списком |
| `scan` | gauntlet-admin | читатели по направлениям (сборка, гейты, код, тесты, хуки и CI, сеть, конфигурация, ПДн, документы) и скептики, которые пытаются опровергнуть каждую находку зондами; критик проверяет план | инструкция по настройке окружения (`docs/gauntlet-setup-<проект>.md`), список модулей для Nexus, план серии задач ревизии 1 с решениями владельца по очередям |
| `coordinate` | gauntlet-admin (guard off) | длинная сессия координатора: открывает сессии шагов, следит за их PR и Grok, проверяет результат после мержа, ведёт план и Инструкцию, правит набор по решениям владельца | задачи для Jira на апрув, решения нумерованным списком, PR документов и набора, отчёты проверок |
| `contract <ревизия прода>` | Default | сверяет внешний контракт сервиса (REST, сообщения) с кодом названной ревизии и документами контура | отчёт расхождений и предложения шагов |

Шаги плана идут отдельными сессиями в окружении Default (guard on): одна задача — одна сессия, одна ветка, один PR.

## 3. Правила владельца эталонного проекта (приняты 2026-09-30 … 2026-10-04)

Записаны в `gauntlet/CLAUDE.md`, «Правила владельца»; новый проект принимает их или меняет на `start`.

1. **Задача для Jira — до старта шага.** Координатор пишет её владельцу простым языком (тема, что и зачем, критерии
   приёмки, трудозатраты). После «да» открывается сессия с отдельным описанием для сессии; задачу она не переписывает.
2. **Рекомендация модели и уровня рассуждений при каждом старте сессии.** Умолчание для сессии шага — Opus 5.5, xhigh, без
   ультракода (процесс уже многоагентный: specifier, hardener, reviewer, хуки). Шаги с тонкой семантикой фреймворка
   (транзакции, Hibernate, AMQP, таймауты) — Fable 5.1 xhigh. Координатор — Fable 5.1 max без ультракода; воркфлоу из многих
   агентов (adversarial-проверка PR, параллельная сверка плана) — только по явному запросу владельца. При создании сессии
   задаётся только модель; уровень и ультракод владелец выставляет в настройках сессии сам.
3. **Адресация вопросов.** К каждому пункту списка решений сессия ставит «ответьте здесь» или «переслать координатору».
   Координатору — всё, что меняет план за пределами шага, набор gauntlet и его файлы, контракты с соседями, дефекты вне файлов
   шага, модель и лимиты, другие сессии. Владелец отвечает сам на выбор варианта спецификации, бизнес-правила шага,
   утверждение, остаточные риски и замечания Grok против спецификации.
4. **Независимый ревьюер Grok AI** комментирует каждый PR. Автор PR проверяет каждое замечание: прав — правка и пуш,
   не прав — ответ в том же треде со ссылкой на код или документацию, начиная строкой «Ответ Claude Code на комментарий
   Grok AI». Молчать нельзя.
5. **Комментарии и Javadoc простым языком** для читателя, у которого нет плана, ТЗ и gauntlet: первое предложение — что это
   и для чего, слова предметной области вместо кодов документов, полные предложения, без истории правок. Переход
   постепенный: новый код по правилу, старые комментарии приводятся в файлах, которые задача меняет (файл целиком); шапки
   фич спецификации правило не затрагивает. Проверяет reviewer (пункт 10 чек-листа).
6. **Решения человека — нумерованным списком** в любой остановке и в отчёте; ответ «1) да 2) нет …» записывается в
   описание PR и в раздел решений плана.
7. **Лимит токенов.** При предупреждении о 99 % лимита или слове «пауза» сессия коммитит, пушит и пишет статус; красный
   гейт на паузе не чинится.
8. **Рабочий контур** без интернета и Claude: зависимости из корпоративного Nexus, перенос PR за PR вручную; набор в контур
   не переносится; каждая новая зависимость и переменная окружения — в отчёт PR.
9. **Проверка после мержа.** Координатор сверяет код с описанием PR, прогоняет гейты на `main`, разбирает остатки,
   записывает итог в план и архивирует сессию. Полная adversarial-проверка воркфлоу — по запросу владельца на PR с тонкой
   семантикой.

## 4. Что нового в ревизии 3 относительно эталона 2026-09-30

- `mutationGate` не засчитывает убитыми мутанты RUN_ERROR (падение JVM тестов на `redefineClasses`, обычно на record):
  `PitSummary.java` печатает их строкой `UNVERIFIED`, а RUN_ERROR вне `config/pit-runerror-allowlist.txt` валит гейт.
  Формат строки allowlist — `Class#method Mutator # тест, который убивает`; строки заносит человек, прочитав тесты.
- `guard.py`: закрыт обход через ключевые слова shell (`for … do rm`, `then git push --force`) и сняты ложные срабатывания на
  `build/gauntlet/` и `./gradlew gauntlet > build/…`; `selftest.py` — 574 проверки.
- Stop-хук возвращает агенту строки RUN_ERROR и `mutationGate: …`; роль hardener знает, что делать с RUN_ERROR.
- `.claude/settings.json`: SubagentStop-хук hardener'а на уровне settings (frontmatter в облаке не срабатывает).
- Правила владельца 1–5, 9 выше; роль reviewer — пункт 10 (комментарии простым языком).
- `gauntlet/CLAUDE.md`, «Источники документации»: запасные пути по тегам для закрытых из облака сайтов (RabbitMQ, JUnit,
  Docker, Git), грамматики Cucumber Expressions и Gherkin, правило «страница с major.minor в пути может расходиться с
  кодом — прав код нужной версии».

## 5. Ловушки облака, известные на эталоне

Подробно — в Инструкции эталона (`docs/gauntlet-setup-rvl-online.md`, разделы 1 и 6). Коротко:
- Docker Hub отвечает 429 на анонимный pull: `TESTCONTAINERS_HUB_IMAGE_NAME_PREFIX=mirror.gcr.io/` в окружении и
  предзагрузка образов в setup script; `dockerd` поднимает SessionStart-хук (`service docker start` падает на ulimit).
- В VM нет `poppler-utils`: без него Read не открывает PDF предметной области — ставить в setup script.
- Maven Central на холодном кэше отвечает 429: повторить через 30–60 с.
- `gh` в VM нет, GraphQL закрыт: PR открывается MCP-инструментом `create_pull_request` или кнопкой.
- Сессия, созданная другой сессией без явного окружения, наследует окружение создавшей: координатор задаёт `environment_id`
  Default явно.
- Переменные `DB_*`, `RABBITMQ_*`, `TEST_*` и лимиты вроде `API_READ_TIMEOUT_SECONDS` в окружения облака не класть: тесты
  читают очереди контура и сверяют умолчания.
